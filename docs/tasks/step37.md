# Step 37: Web members, invitations, and roles UI

## Meta
- **Type**: ui
- **Components**: web
- **Wave**: 5 (parallel group — all steps of the same wave can run concurrently)
- **Depends on**: Step 10: Playwright E2E harness + seeded compose test stack + LLM stub | Step 16: Web persistent sidebar chat layout | Step 21: Server: room invitations | Step 22: Server: member management, leave, role change, ownership transfer
- **Unlocks**: Step 46: Web group management UI | Step 56: E2E regression: auth, OAuth/Hydra, rooms, members, invitations, groups
- **Size**: 1 PR (a few hours for one AI agent)

## Context
`phases.md` Phase 3 ("Invitations + Member Management") and Phase 4/11 ("Basic RBAC" / "Full RBAC") require a Web Frontend that lets room members see who else is in a room, invite new people by username or shareable link, accept/reject invitations they've received, change another member's role, leave a room, and transfer ownership — with every one of those controls gated by the caller's own 5-tier role. Step 21 and Step 22 land the full server-side API surface for this (`room_invitations` CRUD + accept/reject, `GET/DELETE/PATCH /rooms/:roomId/members*`, `PATCH /rooms/:roomId/owner`), and Step 13 (already merged by this step's wave) adds a `role` field to `RoomResponse` and a typed 5-tier `room.Role` server-side, but nothing in `web/` consumes any of it yet: `web/src/features/messages/components/ChatRoom.tsx`'s header only has a placeholder `MoreVertical` button (no member list, no invite entry point), and there is no `members` feature module at all. This step builds that module end to end, following the per-feature `types.ts` / `api/` / `hooks/` / `components/` pattern Step 9 established for `features/{auth,rooms,messages}`, and docks its entry points into the header region of `ChatRoom.tsx` and the persistent top bar Step 16 introduced, without disturbing the regions those two files reserve for other same-wave/later steps.

## Goal
After this PR, every room view has a member avatar stack in its header that opens a full member-list side panel showing each member's role badge; users with `admin`/`master` can invite a new member by exact username (with a role picker) or generate a copyable, reusable invite link, and can change any non-owner member's role from that panel; the top bar gains an invitations-bell entry point where any user can see and accept/reject their own pending invitations across all rooms; a new `/invite/[code]` landing page lets an invite link resolve and be accepted/rejected by a logged-in user; any member can leave a room they don't own, and the current owner can transfer ownership to another existing member. All of this is gated end to end by the 5-tier role carried on `Room.role`: readers never see the message input, guests see it but never see "Send with AI", and only admin/master see member-management controls (invite, role picker, transfer ownership). A new Playwright spec exercises the full invite → accept → role-change → transfer-ownership lifecycle (plus the reader/guest gating) against the Step 10 E2E harness.

**Server response shapes this step's `api/` layer must match exactly** (from Step 21/Step 22's server contracts):
```
GET  /rooms/:roomId/members                        -> 200 { "members": [{ "id", "room_id", "user_id", "username", "role", "joined_at" }] }
DELETE /rooms/:roomId/members/:userId               -> 204 (self-leave only; 409 if the caller is the current owner)
PATCH /rooms/:roomId/members/:userId/role           -> 200 { "id", "room_id", "user_id", "role", "joined_at" }   body: { "role": "reader"|"guest"|"member"|"admin" }
PATCH /rooms/:roomId/owner                          -> 200 <RoomResponse incl. "role">                          body: { "new_owner_id": "<uuid>" }
POST /rooms/:roomId/invitations                     -> 201 { "id","room_id","inviter_id","invitee_id","invite_code","role","status","expires_at","created_at" }  body: { "invitee_username"?, "role", "expires_in_hours"? }
GET  /rooms/:roomId/invitations                     -> 200 { "invitations": [...] }
GET  /invitations                                   -> 200 { "invitations": [...] }   (pending, for the caller)
GET  /invitations/by-code/:code                     -> 200 <Invitation> | 404
POST /invitations/:invitationId/accept              -> 200 { "id","room_id","user_id","role","joined_at" }       (RoomMembershipResponse; 403/409/410 on error)
POST /invitations/:invitationId/reject              -> 204                                                       (400 if the invitation is a link invitation)
```
Map HTTP error bodies (`{ "message": "..." }`) the same way the existing `httpClient`/proxy layer already normalizes them elsewhere — do not add a bespoke error-parsing path in this feature's `api/` modules.

**Why the `MessageInput.tsx` prop is the right approach, not a workaround**: `MessageInput.tsx` (as it exists prior to this step) always renders its "Send with AI" `Button` unconditionally in the button row and only conditionally renders the adjacent `ModelSelector` when `models.length > 0`; simply passing an empty `models` array from `ChatRoom.tsx` would leave a dead "Send with AI" button visible that silently no-ops (since `handleSendWithAI` early-returns when `selectedModel` is `null`), which fails the "guest hides AI invoke" requirement in spirit (the control must not be visible, not just inert). The plan's cross-step convention rotates *ownership* of `MessageList.tsx`/`MessageInput.tsx` restructuring across message-feature steps so two same-wave steps don't collide on a rewrite; this step makes no structural change to `MessageInput.tsx` — it adds exactly one optional, default-`true` boolean prop gating one existing `Button`'s visibility, which cannot conflict with any other step's edits to the same file (a two-line diff: the prop in the signature, and wrapping the "Send with AI" `Button` in `{canInvokeAI && (...)}`).

**Username display (read before implementing `MemberListItem`)**: Step 22's member-list endpoint (`GET /rooms/:roomId/members`) returns a `username` on every `MemberResponse` row (server-side JOIN with `users`) — add `username: string` to this step's `Member` type and render each row's identity as `Avatar.Fallback name={member.username}` (Chakra derives initials from the string) plus the username as the row's primary text, with the `user_id` optionally in small `fontFamily="mono"` muted text (matching the existing `color="fg.muted"` convention in `RoomList.tsx`) as a secondary line. For the viewer's own row, append a "You" tag (`useSession()`'s `id` identifies which row is the viewer). Fall back to rendering `user_id` only if `username` is empty (responses from non-JOINed endpoints like role-change return `""` — after a role-change mutation, invalidate/refetch the member-list query rather than patching the cache with the username-less response).
