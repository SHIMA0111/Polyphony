# Step 58: E2E regression: summarization, streaming, private mode, images/Vision

## Meta
- **Type**: testing
- **Components**: web, infra
- **Wave**: 8 (parallel group — all steps of the same wave can run concurrently)
- **Depends on**: Step 10: Playwright E2E harness + seeded compose test stack + LLM stub | Step 45: Web: image upload + attachment UI + Vision send | Step 47: Web: private AI mode UI | Step 50: Server: context summarization with cached summaries | Step 54: Web: streaming AI rendering
- **Unlocks**: Step 60: Final E2E gate + docs/progress sync
- **Size**: 1 PR (a few hours for one AI agent)

## Context
By wave 8, four separate AI-surface features have each landed with their own narrow, single-feature Playwright spec: Step 45 (image attach → Vision), Step 47 (private AI mode), Step 50 (server-side context summarization, Phase 18 of `phases.md`), and Step 54 (streaming AI rendering, Phase 19). None of those specs exercises the scenario each feature actually exists for — a *long-lived* room whose history is large enough to force summarization, a stream that is watched incrementally rather than just awaited, a private exchange checked from a genuinely independent second client, and a Vision send verified end-to-end including persistence after reload. This step is one of four disjoint wave-7/8 regression suites (56: identity/collaboration; 57: realtime AI core; 58: this step, the "advanced AI surface"; 59: billing/fork) that together prove the whole AI-adjacent feature set still works when driven end-to-end against the real (isolated) compose stack, with a fix mandate strictly bounded to whatever these specs themselves surface — this step does not implement or re-implement any of the four features it tests.

## Goal
After this PR, `web/e2e/support/seed-long-history.ts` provides a reusable helper that any spec (in this suite or a future one) can call to deterministically build a room whose accumulated context exceeds Step 50's summarization trigger threshold, without needing dozens of real LLM round-trips. Four new Playwright spec files under `web/e2e/regression/advanced-ai/` exercise: (1) a long-history room actually triggering server-side summarization and the client rendering a "summary in use" indicator for it; (2) an AI reply that streams in visibly distinct incremental steps before settling into its final, stable state; (3) a private AI exchange that is genuinely invisible to a second, independently-authenticated user sharing the same room, including after both clients reload; (4) an image attached to a message, sent through the Vision path, rendering as a thumbnail in the transcript and surviving a page reload. `task test:e2e` runs all four specs green alongside the existing suite. Any defect these specs surface in the already-shipped Step 45/47/50/54 code is fixed in this PR, scoped strictly to what a failing assertion in one of these four specs requires — no adjacent feature work.

## Implementation notes
- **Directory convention**: this step's spec files live under a new `web/e2e/regression/advanced-ai/` directory (four files: `summarization.spec.ts`, `streaming.spec.ts`, `private-mode.spec.ts`, `vision-attachments.spec.ts`), distinct from any per-feature spec files Steps 45/47/50/54 already added directly under `web/e2e/` (e.g. `web/e2e/private-mode.spec.ts`, `web/e2e/attachments.spec.ts`) — do not rename or modify those existing per-feature specs, this step's specs are additional, broader regression coverage, not replacements. Playwright's default `testDir: "./e2e"` config from Step 10 already picks up nested directories with no config change needed.
- **Read the actual merged code before wiring, every time.** This step sits at the end of four independently-developed steps (45/47/50/54); do not assume any field name, threshold, or file path stated here is exact — it is this step's job to `grep`/read the real merged server and web code and adapt:
  - Step 50's summarization trigger/threshold: `grep -rn "summar" server/internal/domain/ai server/internal/usecase/message server/internal/config 2>/dev/null` (case-insensitive: add `-i`), and check `server/schema.sql` for the `message_context_summaries` table shape.
  - Step 50/51's "summary used" signal on the API/WS payload: `grep -rn -i "summary" server/internal/interface/handler server/internal/domain/event 2>/dev/null` and the equivalent web-side type in `web/src/types/api.ts`/`web/src/features/messages/types*`.
  - Step 54's streaming WS event contract and cache-merge function: `grep -rln "token_chunk\|StreamChunk\|stream_chunk" server/ web/src` (per Step 54's own implementation notes) to confirm this suite's assertions align with the actual event shape/merge point, without re-implementing it.
  - Step 47's private-mode toggle/badge selectors and Step 41's `visibility` field name: reuse the exact selectors/field Step 47's own `web/e2e/private-mode.spec.ts` already asserts against, rather than re-deriving them independently (grep that file for the toggle/badge locators it uses).
  - Step 45's attachment chip/thumbnail/lightbox selectors: reuse the exact locators Step 45's own `web/e2e/attachments.spec.ts` already asserts against.
- **Server contract for the seed helper**: `POST /rooms/:roomId/messages` (plain send) is the existing, unchanged endpoint from Phase 1 (`server/internal/usecase/message/usecase.go`'s `SendMessage`); no AI call is made per seeded message, keeping the seed loop fast and free of LLM-stub round-trips until the one final AI-triggering send. `POST /tokens/estimate` is Step 27's endpoint (`{"model": "...", "messages": [...]}` → `{"model": "...", "estimated_tokens": <number>}`), reused here purely to self-verify the seed has crossed the discovered threshold — this mirrors how Step 38's web token meter already calls the same endpoint.
- **Chakra v3 conventions** (`.claude/rules/chakra-ui.md`): if the summarization-badge fix is needed, use `Badge`/`Tooltip` directly from `@chakra-ui/react` (`Badge`) and the existing `web/src/components/ui/tooltip.tsx` snippet (`Tooltip`) — do not add a new snippet or a new modal/drawer for this. Use `colorPalette` for tone rather than hard-coded colors.
- **LLM stub fixture format** (must match Step 10's existing framing exactly, `llm-stub/fixtures/stream/default.sse` as the template): each SSE frame is an OpenAI-style `data: {"id":"...","object":"chat.completion.chunk","choices":[{"delta":{"content":"..."},"index":0,"finish_reason":null}]}` line followed by a blank line, terminated by a final `data: [DONE]` line; construct `long-story.sse` with enough distinct `delta.content` fragments (assembling to a known, checkable final string) that the streaming spec can reliably observe 3+ strictly-growing intermediate snapshots even on a fast local run — pad with a short artificial delay only if the stub already supports one per-chunk (check `llm-stub/server.ts`'s streaming branch; if it has no delay mechanism, do not add one — rely on enough distinct chunks instead, since Playwright polling assertions do not require real-time pacing to observe sequential appended state).
- **Two-user/member setup for the private-mode spec**: reuse whichever invite/member-add mechanism the merged member-management step (a wave-3/4 step preceding this one) actually shipped by the time this step runs — grep `web/src/features/members` for the invite flow's API/UI and drive it the same way Step 47's own spec already does (do not re-derive a different mechanism).
- **Rate limiting awareness**: if the rate-limiting step (referenced in the plan-wide notes as part of Step 57's scope) has landed by the time this step is implemented, keep `seedLongHistoryRoom`'s message-send loop within whatever per-user rate limit exists (e.g. add a small delay between sends, or batch requests below the limit) so the seed helper does not itself trigger a 429 — this is a defensive implementation detail, not new rate-limiting logic.
- **English-only code/comments** per `CLAUDE.md`; keep new/edited files `"use client"` where they touch React/browser APIs, consistent with the rest of `web/src/features/messages/`.
- **Conflict notes**: this step's only touches outside test/fixture files are the narrowly-scoped, spec-failure-driven fixes described above (most likely: a small summarization-badge addition to `MessageList.tsx` or its wave-8 successor). It shares wave 8 with Step 59 (billing/fork regression), which operates on billing/fork-specific files and a disjoint spec directory (`web/e2e/regression/billing-fork/` or equivalent) — no expected file overlap. It has no expected overlap with Step 56/57 (wave 7, already merged by the time this step runs). `docker-compose.yml`/`Taskfile.yml` are untouched.
