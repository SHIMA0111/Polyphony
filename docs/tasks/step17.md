# Step 17: Web forms, toaster, and App Router error surfaces

## Meta
- **Type**: ui
- **Components**: web
- **Wave**: 3 (parallel group — all steps of the same wave can run concurrently)
- **Depends on**: Step 9: Web data layer migration: TanStack Query, RSC prefetch, per-feature API modules
- **Unlocks**: Step 30: Web: Kratos-driven login/registration + auth data-plane flip | Step 53: Web: plans, Stripe Checkout, subscription management, billing history UI
- **Size**: 1 PR (a few hours for one AI agent)

## Context
Today every form in `web/` (`web/src/features/auth/components/LoginForm.tsx`, `web/src/features/auth/components/RegisterForm.tsx`, `web/src/features/rooms/components/CreateRoomForm.tsx`) hand-rolls its own `useState` fields, submits via a raw `onSubmit`/`onClick` handler, and shows validation/submission failures (if at all) as an inline `<Box bg="red.50">` banner with no `role="alert"` — `CreateRoomForm.tsx:29-33` even swallows its `createRoom` failure with a bare `// TODO: show error toast` comment. The app also has no App Router error/loading/not-found surfaces: there is no `web/src/app/error.tsx`, `web/src/app/loading.tsx`, or a `not-found.tsx` for `web/src/app/(main)/rooms/[roomId]/`, so a thrown render error, a slow RSC fetch, or a room ID that doesn't exist all render as either a blank screen or Next.js's generic unstyled fallback. `web/src/components/ui/toaster.tsx` already defines a working `createToaster` instance and `<Toaster />` component (a stock Chakra v3 snippet) but it is never mounted anywhere in `web/src/app/layout.tsx`, so `toaster.create(...)` calls would currently render nothing. This step closes both gaps — form validation/submission UX and route-level failure UX — so that after Step 9 rewires data fetching onto TanStack Query, every failure path (query error, mutation error, validation error, render error, 404) has a concrete, accessible place to surface.

## Goal
After this PR: `<Toaster />` is mounted once in the root layout so `toaster.create/success/error(...)` works from anywhere in the app; the login, register, and create-room forms are rewritten on `react-hook-form` + `zod` with per-field `Field.Root invalid` + `Field.ErrorText` (carrying `role="alert"`) for validation errors, while submission-level failures (wrong credentials, duplicate email, network errors) are surfaced via `toaster.create({ type: "error", ... })` instead of silent `catch` blocks or ad-hoc banners; the register form validates the confirm-password field live as the user types and shows a password strength meter; and the root App Router tree has an `error.tsx` (render-error boundary with reset), a `loading.tsx` (route-transition skeleton), and `web/src/app/(main)/rooms/[roomId]/not-found.tsx` (invalid/deleted room ID).

## Implementation notes
- Toaster snippet is already correct at `web/src/components/ui/toaster.tsx` (stock Chakra v3 `createToaster`/`Toaster` composition per `.claude/rules/chakra-ui.md`'s snippet-import convention) — only mount it in `web/src/app/layout.tsx`, don't rewrite it.
- `Field` compound API (per `@chakra-ui/react` v3, confirmed via the Chakra MCP `get_component_props`/`get_component_example` tools): `Field.Root` takes an `invalid` boolean prop; `Field.ErrorText` is a plain `<span>`-backed component with **no built-in `role="alert"`** — you must pass `role="alert"` explicitly on every `Field.ErrorText` usage to satisfy the "role=alert on form errors" requirement (verified against `web/node_modules/@chakra-ui/react/dist/esm/components/field/field.js`, which sets no ARIA role). Example:
  ```tsx
  <Field.Root invalid={!!errors.email}>
    <Field.Label>Email</Field.Label>
    <Input type="email" {...register("email")} />
    {errors.email && <Field.ErrorText role="alert">{errors.email.message}</Field.ErrorText>}
  </Field.Root>
  ```
- `react-hook-form` + `zod` wiring pattern: `const { register, handleSubmit, watch, formState: { errors } } = useForm<LoginFormValues>({ resolver: zodResolver(loginSchema) })`, `import { zodResolver } from "@hookform/resolvers/zod"`. `onSubmit = handleSubmit(async (values) => { try { await loginMutation.mutateAsync(values) } catch (err) { toaster.create({ type: "error", title: "Sign in failed", description: err instanceof Error ? err.message : "Please try again." }) } })`.
- `toaster` import path is `import { toaster } from "@/components/ui/toaster"` (already used as `toaster.create(...)` / `.success(...)` / `.error(...)` per the Chakra MCP examples); this project's existing code has zero call sites today, so this step introduces the first ones.
- `PasswordStrengthMeter` is already implemented at `web/src/components/ui/password-input.tsx:117-148` and takes `value`/`max` props (`max` defaults to 4) — reuse it directly, do not reimplement.
- Current pre-Step-9 baseline being replaced (for reference, read before editing): `LoginForm.tsx` and `RegisterForm.tsx` both use local `useState` for every field plus `error`/`isSubmitting`, and call `useAuth()` (`web/src/hooks/use-auth.ts`) which wraps `apiClient.login`/`apiClient.register` (`web/src/lib/api.ts`) and calls `router.push("/rooms")` on success. `CreateRoomForm.tsx` calls `apiClient.createRoom(name, description)` directly inside a `Dialog.Root`.
