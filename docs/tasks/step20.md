# Step 20: Server: Kratos session auth swap + identity migration

## Meta
- **Type**: feature
- **Components**: server
- **Wave**: 3 (parallel group — all steps of the same wave can run concurrently)
- **Depends on**: Step 1: Go server foundation: DI/router split, structured logging, lint, config | Step 2: Go test infrastructure: testcontainers helper + shared mocks | Step 11: Infra: Ory Kratos services in docker-compose
- **Unlocks**: Step 30: Web: Kratos-driven login/registration + auth data-plane flip | Step 33: Server: Redis rate limiting + Kratos session cache
- **Size**: 1 PR (a few hours for one AI agent)

## Context
Phase 9 of `phases.md` requires migrating auth from SimpleJWT to Ory Kratos. Step 11 already brought up a live, locally-runnable Kratos instance (public API on `4433`, admin API on `4434`, identity schema mirroring `users.email`/`users.username`) but touched no application code. This step lands the Go-side half of the swap: a second `domainauth.AuthService` implementation backed by Kratos's self-service and session-verification APIs, selectable via an `AUTH_MODE` environment flag, plus the `users.kratos_identity_id` column and a one-off backfill script that links pre-existing SimpleJWT users to newly-created Kratos identities. Per the plan's explicit auth data-plane sequencing, SimpleJWT remains the `docker-compose.yml` default through this wave — Step 30 owns flipping the compose default and rewriting the web BFF proxy to forward Kratos session cookies instead of Bearer JWTs.

## Goal
After this PR, `server/internal/interface/auth/kratos.go` provides a `KratosAuthService` that implements the existing `domainauth.AuthService` interface (`Register`, `Login`, `ValidateToken`) using Kratos's self-service registration/login API flows and the `/sessions/whoami` endpoint, with the caller's local `users.id` resolved through a new `users.kratos_identity_id` column. `server/internal/app/container.go` (from Step 1) picks `SimpleJWTService` or `KratosAuthService` based on a new `AUTH_MODE` config value (`simple_jwt` default, `kratos` opt-in) without changing any downstream usecase/handler code, since both implementations satisfy the same interface. The auth middleware accepts credentials from either an `Authorization: Bearer` header or a Kratos session cookie, and CORS is configured to allow credentialed cross-origin requests from the web origin. A `cmd/kratosmigrate` one-off tool backfills existing SimpleJWT users into Kratos identities via the Kratos Admin API and populates `kratos_identity_id`. `docker-compose.yml`'s `api` service still runs with `AUTH_MODE=simple_jwt` by default; running it with `AUTH_MODE=kratos` (and Step 11's Kratos services up) exercises the full Kratos-backed path end to end.

- [ ] `server/internal/interface/auth/kratos.go` (new file, sibling to `simple_jwt.go`): `KratosAuthService` implementing `domainauth.AuthService`, constructed via `NewKratosAuthService(userRepo user.UserRepository, publicURL, adminURL, cookieName string, httpClient *http.Client) *KratosAuthService`. Hand-roll the REST calls with `net/http` + `encoding/json` DTOs, following the existing pattern in `server/internal/interface/gateway/llm_client.go` (private DTO structs, a shared timeout-configured `http.Client`) rather than adding the full `ory/client-go` SDK dependency:
  - `Register(ctx, email, username, password)`: `GET {publicURL}/self-service/registration/api` (header `Accept: application/json`) to obtain a flow ID, then `POST {publicURL}/self-service/registration?flow=<id>` with `{"method":"password","password":password,"traits":{"email":email,"username":username}}`. On success, the native/API flow response body contains `identity.id` and a `session_token`. Create the local `users` row (new UUID `id`, `Email`/`Username` from the request, a placeholder unusable `PasswordHash` since Kratos now owns credential verification, `KratosIdentityID` set to `identity.id`) via `userRepo.Create`, then `userRepo.SetKratosIdentityID`. Return `&domainauth.TokenPair{AccessToken: session_token, TokenType: "Bearer"}`. Map a `4xx` response whose Kratos error body indicates an existing identifier conflict (registration UI node validation error) to `domain.ErrEmailAlreadyExists` / `domain.ErrUsernameAlreadyExists` to preserve the existing handler-level error mapping in `auth_handler.go`.
  - `Login(ctx, email, password)`: `GET {publicURL}/self-service/login/api`, then `POST {publicURL}/self-service/login?flow=<id>` with `{"method":"password","identifier":email,"password":password}`. On success, look up the local user via `userRepo.GetByKratosIdentityID(ctx, session.identity.id)`; if `domain.ErrNotFound` (identity exists in Kratos but has no local row yet — e.g. created directly via the Admin API rather than through this service), self-heal by creating the local row from `session.identity.traits` the same way `Register` does. Return `&domainauth.TokenPair{AccessToken: session_token, TokenType: "Bearer"}`. Map Kratos's `400`/incorrect-credentials UI error to `domain.ErrInvalidCredentials`.
  - `ValidateToken(ctx, token string)`: calls `GET {publicURL}/sessions/whoami`. Interpret `token` using this convention (documented in a GoDoc comment on the method, since it is the contract the auth middleware below must honor): if `token` has the prefix `"cookie:"`, strip it and set header `Cookie: {cookieName}=<rest>`; otherwise treat it as an opaque native session token and set header `X-Session-Token: <token>`. On a `200` response, extract `identity.id` from the body and resolve the local user via `userRepo.GetByKratosIdentityID`, returning `&domainauth.Claims{UserID: localUser.ID}`. On any non-200 or lookup failure, return `domain.ErrInvalidToken`.
  - GoDoc every exported symbol per `CLAUDE.md` (what/why/constraints/error behavior), including the `"cookie:"` prefix convention on `ValidateToken` and the self-healing behavior in `Login`.

## Out of scope
- Flipping `docker-compose.yml`'s `AUTH_MODE` default to `"kratos"` — Step 30 owns that, together with rewriting the web BFF proxy to forward the Kratos cookie and removing SimpleJWT/Bearer forwarding.
- Any change to `web/` — login/registration pages, the API client, or cookie handling on the frontend are entirely Step 30's scope; this step only makes the server capable of accepting a Kratos session, it does not change how the browser obtains one.
- Kratos self-service browser UI pages (`ui_url` targets configured in Step 11's `kratos.yml`) — those routes don't exist until Step 30/44.
- OIDC/social login (`selfservice.methods.oidc`), Ory Hydra, Dex — Step 44 and Step 55.
- Redis-backed session caching for Kratos `whoami` calls (avoiding a network round-trip per request) — Step 33, which explicitly builds on this step's `KratosAuthService`.
- RBAC/`room.Role` changes — Step 13, developed in parallel this same wave; this step's only middleware touch is `interface/middleware/auth.go` (authentication), never `interface/middleware/rbac.go` (authorization), so the two steps edit disjoint files.
- Rate limiting — Step 33.
- Rewriting `SimpleJWTService` or removing it — it remains the default implementation and is untouched except that it now must also populate `KratosIdentityID: nil` implicitly (its `Register` already only sets the fields it knows about; no code change needed there since the new struct field defaults to its zero value).

## Implementation notes

- **Kratos identity schema alignment**: Step 11's `ory/kratos/identity.schema.json` defines `traits.email` and `traits.username` — this step's `Register`/`Login`/`kratosmigrate` payloads must use exactly those trait names.
- **`domain.ErrKratosIdentityAlreadyLinked`**: add alongside the existing sentinel errors in `server/internal/domain/errors.go`, following the existing `var (...)` block style with a GoDoc comment; wire it into `handleAuthError`-equivalent mapping in `auth_handler.go` only if a new HTTP-facing path actually returns it (the `kratosmigrate` CLI logs-and-skips on this error rather than surfacing it through any HTTP handler, so no `auth_handler.go` change is strictly required — verify and only touch it if a code path needs it).
- **Interface contract, not a breaking change**: `domainauth.AuthService`'s three methods (`Register`, `Login`, `ValidateToken`) are unchanged in signature; `KratosAuthService` is a pure additional implementation, so `authusecase.AuthUsecase`, `auth_handler.go`, and every existing test against `SimpleJWTService` continue to compile and pass unmodified.
- **`"cookie:"` prefix convention**: this is an internal contract between `middleware/auth.go` and whichever `AuthService` is active — `SimpleJWTService.ValidateToken` never receives a `"cookie:"`-prefixed string in practice (browsers only get an `ory_kratos_session` cookie when `AUTH_MODE=kratos`, since SimpleJWT never sets any cookie), so no change to `simple_jwt.go` is needed, but note this explicitly in `kratos.go`'s GoDoc so a future reader understands why the prefix exists.
- **Conflict notes** (per skeleton): this step touches `server/internal/interface/middleware/auth.go` only; Step 13 (same wave) adds a new, separate `server/internal/interface/middleware/rbac.go` file that is chained *after* the auth middleware in route registration — no line-level overlap. If Step 13 lands first, its `RequireRole` middleware already expects `middleware.GetUserID(c)` to be populated by whatever runs first in the chain, which remains true regardless of which `AuthService` populated it. The `docker-compose.yml` edit here is additive-only within the existing `api:` service block (new `environment:` keys), consistent with the convention Step 1/6/11 established — no other same-wave step edits the `api:` block's existing lines.
- **`schema.sql`/migration convention**: edit `server/schema.sql`'s `users` table additively (only the new `kratos_identity_id` column + its unique constraint), then run `task migrate:generate -- add_users_kratos_identity_id` from the repo root; do not hand-write SQL under `server/migrations/` or edit `server/migrations/atlas.sum` by hand.
- English-only code/comments, GoDoc on every new exported symbol, per `CLAUDE.md`.
