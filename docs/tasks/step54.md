# Step 54: Web: streaming AI rendering

## Meta
- **Type**: ui
- **Components**: web
- **Wave**: 7 (parallel group — all steps of the same wave can run concurrently)
- **Depends on**: Step 10: Playwright E2E harness + seeded compose test stack + LLM stub; Step 35: Web WebSocket client + live cache merge; Step 51: Go: consume gateway stream + WS chunk forwarding

- **Size**: 1 PR (a few hours for one AI agent)

## Context

Phase 19 of `phases.md` ("Streaming AI Responses") requires that AI responses be displayed incrementally, token by token, rather than appearing all at once when the request completes. The gateway and Go layers of this capability are delivered by Step 51 (Rust SSE `stream()` port consumed by the Go API, chunks forwarded to clients as WebSocket events over the `domain/event.MessageHub` built in Step 51's dependency chain). Step 35 already wired the web WebSocket client into the TanStack Query cache as the single merge point for realtime events. This step is the last mile: teach the message cache and the AI message bubble in `web/src/features/messages/components/MessageList.tsx` to consume the new chunk events, render them live, finalize on completion, and fall back gracefully to the existing non-streaming request/response path when no chunk events arrive.

## Goal

When a user sends a message that triggers an AI response, the AI's message bubble in the room view starts as a "thinking" indicator and, as `token_chunk`-style WebSocket events for that message arrive, upgrades in place to a live-updating text bubble that grows incrementally (no bubble remount/flicker, no scroll-jump). When the terminating "completed" event (or the equivalent finalized `Message` payload) arrives, the in-flight streamed text is replaced by the authoritative final message from the cache/API response (fixing up id, sequence, `created_at`/`updated_at`, and status) so the streamed and non-streamed code paths converge on the same rendered state. If no chunk events are observed for the in-flight AI message (WebSocket unavailable, stream disabled server-side, or the gateway/provider does not support streaming for the resolved model), the UI falls back to today's behavior: the bubble stays in the "thinking" state until the existing non-streaming AI response resolves, with no error shown to the user. A Playwright spec proves the incremental-then-final behavior end-to-end against the canned SSE stream served by the Step 10 LLM stub.

## Implementation notes

- **Find the frozen contract first.** Before writing any code, grep the repository for what Steps 51 and 35 actually shipped, since this step must not redefine or guess at their event shapes:
  - `grep -rn "token_chunk\|StreamChunk\|stream_chunk\|CompletionChunk" server/ web/ llm-gateway/` to find the Go WS event type/name and any existing TS mirror of it.
  - Inspect the WS client/hook and cache-merge function Step 35 introduced (search `grep -rln "WebSocket\|useWebSocket\|ws-client" web/src`) to find the single merge point where WS events are folded into the TanStack Query cache for a room's messages — this step adds one more case/branch there, it does not create a second merge point.
  - Inspect `server/internal/domain/message`, `server/internal/usecase/message`, and the WebSocket/event interface package Step 51 added to (search `grep -rln "MessageHub\|event\." server/internal`) only to confirm the payload fields (e.g. `message_id`, `delta`, `sequence`, `done`/`event: "completed"`); do not modify server code in this step.
- **Current baseline to build on**: today `web/src/features/messages/components/ChatRoom.tsx` fetches messages once via `apiClient.listMessages` and appends the AI response synchronously after `apiClient.sendMessage`/the AI-send call resolves (see the `handleSend`/`handleSendWithAI` callbacks); `web/src/features/messages/components/MessageList.tsx` renders each `Message` from `web/src/types/api.ts` (`type: "human" | "ai"`, `status: "completed" | "failed"`) as a Chakra `Flex`/`Box` bubble keyed by `message.id`. By this step, Steps 4/9/35 will have replaced this with a TanStack Query-backed cache and a cookie/BFF auth flow, and Step 35 will already merge WS events into that cache — build strictly on top of whatever concrete hook/query-key names those steps landed, not on the current `useState` version, since it will already be gone.
- **In-flight message identity**: the in-flight AI message needs a stable client-side key before the server assigns a final id/sequence (chunks may start arriving before any HTTP response returns an id). Use whatever optimistic-placeholder convention the AI-send mutation from earlier waves already established (e.g. a temporary id/sequence marker); if none exists, key the in-flight entry by `room_id` + a monotonically increasing local counter and reconcile it by content-append until the finalize event supplies the real id. Do not introduce a second, competing notion of "current in-flight AI message" alongside whatever the send mutation already tracks.
- **Streaming status type**: extend the existing `MessageStatus` union in `web/src/features/messages/types.ts` (post-Step-29 it is `"completed" | "failed" | "sending"`, where `"sending"` is Step 29's client-only optimistic marker) with `"streaming"` — note Step 51's server-side placeholder message actually persists and returns `status: "streaming"` on the `202` response, so this is a wire value, not a client-only invention; the finalize event ultimately resolves to `"completed"` or `"failed"` exactly as today.
- **Chakra v3 conventions** (`.claude/rules/chakra-ui.md`): keep using `@chakra-ui/react` compound/style-prop patterns already used in `MessageList.tsx` (`Flex`, `Box`, `Text`, semantic tokens like `bg.subtle`/`fg.muted`). Any streaming-cursor affordance should be a small inline style-prop element (e.g. a `Box` with a CSS animation via `sx`/style props or a `keyframes` helper) — do not pull in a new animation library.
- **Fallback correctness**: the AI-send mutation's own `onSuccess`/response handling must remain the single source of truth for "did the AI response finish" — the chunk/finalize WS path is an enhancement overlaid on it, not a replacement request path. Structure the merge logic so applying the finalize event twice (once from WS, once from the mutation response, if both convey the final message) is a no-op the second time (compare by id/sequence, or last-write-wins on identical final content).
- **Conflict note**: Step 47 lands in the same wave and also touches `MessageList.tsx` (privacy badges + the private-AI-mode toggle). Keep this step's edits scoped to the AI-bubble content/status rendering path (the `Box` containing `message.content` and the surrounding status logic) and avoid reformatting or restructuring unrelated parts of the component (e.g. the avatar, sender-name row, regenerate button) so the two PRs diff cleanly against each other.
- **Playwright spec location and stub**: place the new spec alongside the other Playwright specs created from Step 10 onward (the E2E harness's spec directory) and reuse the seeded compose test stack and the LLM stub's canned SSE fixtures exactly as Step 10 exposes them (do not add a second stub or bypass it with a mocked `fetch`) — the compose test profile already points the gateway's `OPENAI_BASE_URL` at the stub.
