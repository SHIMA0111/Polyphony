# Step 26: Rust: Gemini provider adapter

## Meta
- **Type**: feature
- **Components**: llm-gateway
- **Wave**: 4 (parallel group — all steps of the same wave can run concurrently)
- **Depends on**: Step 8: Rust gateway operational hardening | Step 14: Rust gateway test harness: router oneshot + wiremock provider tests
- **Unlocks**: Step 34: Model metadata (token limits + pricing) across gateway/server/web | Step 39: Vision multimodal plumbing: gateway content-parts mapping + Go DTOs | Step 43: Rust: streaming SSE for all providers + stream endpoint
- **Size**: 1 PR (a few hours for one AI agent)

## Context
`phases.md` Phase 7 ("Multi-provider (Gemini) + Model Selection UI") requires a third LLM provider so the model-selection UI has something real to choose between. Today `llm-gateway` only has `adapters/outbound/openai.rs` (see `llm-gateway/src/adapters/outbound/openai.rs`) registered in `llm-gateway/src/main.rs`; the `LLMProvider` port (`llm-gateway/src/ports/outbound/provider.rs`) is deliberately provider-agnostic so "adding a provider = add a file in `adapters/outbound/` + register DI in `main.rs`" (per `phases.md`'s directory-structure principles). Step 8 moves per-provider HTTP tuning (timeouts, retries) and base URLs out of ad-hoc `std::env` reads into an explicit, injectable `Config`/`HttpClientConfig`/`ProviderConfig` plus a shared `send_with_retry` retry helper (`llm-gateway/src/adapters/outbound/http_retry.rs`) specifically so later provider adapters do not reinvent that plumbing. Step 14 lands the `wiremock`/`tower::oneshot` test harness (`llm-gateway/tests/openai_provider_test.rs`, `llm-gateway/tests/router_test.rs`) as "the canonical pattern later provider ... steps extend." This step is that extension for Gemini: it adds `GeminiProvider`, wires it into `CompletionService`, and proves the request/response mapping and error handling with the same no-network wiremock approach already established for OpenAI. It runs in parallel with the Anthropic adapter step (Step 25) — both are new, disjoint files that each add one line to `main.rs`'s DI assembly.

## Goal
After this PR, `llm-gateway` has a fully working `GeminiProvider` implementing the `LLMProvider` port against Google's Generative Language API (`generateContent`). It correctly maps the provider-agnostic domain model (`llm-gateway/src/domain/model.rs`) onto Gemini's `contents`/`parts` shape, pulls `Role::System` messages out into a top-level `system_instruction` field (Gemini does not accept a `"system"` role inside `contents`), maps `Role::Assistant` to Gemini's `"model"` role, and maps Gemini's response (`candidates`, `usageMetadata`) back to the domain `CompletionResponse`. The adapter reuses Step 8's `HttpClientConfig`/`ProviderConfig`/`send_with_retry` plumbing (no raw `std::env` reads, retries on `429`/`5xx` honoring `Retry-After`) and resolves its API key via the existing generic `EnvKeyStore` (`GEMINI_API_KEY`). `GeminiProvider` is registered in `main.rs` alongside `OpenAIProvider`, and its hardcoded model IDs are proven not to collide with any other registered provider's IDs. A new `llm-gateway/tests/gemini_provider_test.rs`, following the `openai_provider_test.rs` pattern from Step 14, exercises success, system-instruction extraction, multi-turn role mapping, safety-blocked responses, rate limiting, server errors, malformed bodies, and timeouts — all against a `wiremock::MockServer`, with zero real network calls.

For `id`, use `resp.response_id` if present; otherwise generate one via `uuid::Uuid::new_v4().to_string()` (the `uuid` dependency is already added in Step 8 for request-id middleware) and document this fallback in a doc-comment, since Gemini's `generateContent` response does not always include a stable response identifier.

- Gemini API shape (Google Generative Language API, `v1beta`): `POST {base_url}/v1beta/models/{model}:generateContent` with header `x-goog-api-key: {api_key}` and a JSON body of `{ "contents": [...], "systemInstruction": {...}, "generationConfig": {...} }`; the response is `{ "candidates": [{"content": {"role": "model", "parts": [{"text": "..."}]}, "finishReason": "STOP", "index": 0}], "usageMetadata": {"promptTokenCount": N, "candidatesTokenCount": N, "totalTokenCount": N} }`. Base URL is fully overridable via the injected `ProviderConfig` (never hardcoded), which is exactly what makes the `wiremock` tests and any future E2E stub possible per the plan's "per-adapter explicit config incl. base-URL overrides" note.
- `conflictNotes` (from the plan): this step is parallel to Step 25 (Anthropic). Both steps add a new provider subdirectory under `adapters/outbound/`, one new field to `Config` (`gemini` vs `anthropic`), and one new `Box::new(...)` line in `main.rs`'s provider vector plus one new `pub mod ...;` line in `adapters/outbound/mod.rs` — all of these are additive, same-shape edits on different lines, so rebasing against Step 25 (in either merge order) should be a trivial line-level merge, not a real conflict. Do not restructure `main.rs`'s DI block or `config.rs`'s struct layout beyond adding your own field/line.
- No `schema.sql` / Atlas changes — this step touches no database tables (`dbChanges` is empty).
- Env var naming follows the existing `{PROVIDER}_API_KEY` / `{PROVIDER}_BASE_URL` convention already used for `OPENAI_API_KEY`/`OPENAI_BASE_URL` (see Step 8's notes and `llm-gateway/src/adapters/outbound/env_key.rs`).
- All code, comments, doc-comments, and test names in English, per `CLAUDE.md`.
