# Step 19: gRPC contract: proto definitions + Rust tonic inbound adapter

## Meta
- **Type**: feature
- **Components**: llm-gateway, server
- **Wave**: 3 (parallel group — all steps of the same wave can run concurrently)
- **Depends on**: Step 3: Rust gateway domain/ports reshape (streaming+multimodal-ready) | Step 8: Rust gateway operational hardening
- **Unlocks**: Step 28: Go: gRPC LLM client swap + retry + health
- **Size**: 1 PR (a few hours for one AI agent)

## Context
`phases.md` Phase 8 ("gRPC + LLM Gateway Hardening") calls for switching Go API ↔ LLM Gateway communication to gRPC, backed by shared proto definitions and model metadata (token limits, pricing). Today the gateway only speaks REST/JSON: `llm-gateway/src/adapters/inbound/rest/router.rs` wires `GET /health`, `GET /models`, `POST /completions` onto a `CompletionUseCase` trait object (`llm-gateway/src/ports/inbound/completion.rs`), and the Go side only has a REST implementation (`server/internal/interface/gateway/llm_client.go`) behind the `ai.LLMGateway` interface (`server/internal/domain/ai/gateway.go`) — the documented Phase-8 swap point. This step lands the shared `.proto` contract and a tonic-based gRPC inbound adapter in the gateway that serves the exact same `CompletionUseCase` the REST router already uses, so REST and gRPC coexist behind one domain service. The Go client swap itself (`ai.LLMGateway` gRPC implementation, retries, health polling) is deliberately deferred to Step 28, which depends on this step for the compiled contract.

## Goal
After this PR, `server/proto/llmgateway/v1/` contains the canonical `.proto` contract for completions and model listing (including `context_window`/`pricing` model-metadata fields), `llm-gateway` compiles those protos via `tonic-build` in a new `build.rs`, and the gateway binary serves both the existing REST router on `LLM_GATEWAY_PORT` (default 8081) and a new gRPC server on `LLM_GATEWAY_GRPC_PORT` (default 50051) concurrently from the same `Arc<dyn CompletionUseCase>` instance. The gRPC server exposes `CompletionService/Complete`, `ModelsService/ListModels`, and the standard `grpc.health.v1.Health` service. `docker-compose.yml`'s `llm-gateway` build stage gains `protoc` so the image still builds. Nothing on the Go side changes beyond adding the `.proto` files — no Go stubs are generated and `ai.LLMGateway`/`LLMClient` are untouched; that lands in Step 28.

## Implementation notes
- **Reuse, don't duplicate**: the domain service being served is `CompletionService` in `llm-gateway/src/domain/service.rs`, injected into both `adapters::inbound::rest::router::build_router` and the new `adapters::inbound::grpc::server::serve_grpc` as the *same* `Arc<dyn CompletionUseCase>` constructed once in `main.rs` — do not construct a second `CompletionService` instance for gRPC.
- **Proto location rationale**: protos live under `server/proto/` (not `llm-gateway/proto/`) because `phases.md`'s server directory tree already lists `proto/ # Added in Phase 8` as a top-level server directory, and Step 28 (Go client) needs to generate Go stubs from the same files without reaching into `llm-gateway/`. The Rust build only *reads* these files via a relative include path (`../server/proto`) from `llm-gateway/build.rs` — it does not copy or vendor them.
- **`tonic-build` invocation shape** (adjust exact method names to the pinned crate version's docs — `tonic-build` has renamed its compile entry point across versions, e.g. `compile` vs `compile_protos`):
  ```rust
  fn main() -> Result<(), Box<dyn std::error::Error>> {
      tonic_build::configure()
          .build_server(true)
          .build_client(false)
          .compile_protos(
              &[
                  "../server/proto/llmgateway/v1/completion.proto",
                  "../server/proto/llmgateway/v1/models.proto",
              ],
              &["../server/proto"],
          )?;
      Ok(())
  }
  ```
- **Error-mapping parity**: `convert.rs`'s `domain_error_to_status` must be kept in lockstep with `llm-gateway/src/adapters/inbound/rest/handlers.rs`'s `AppError::into_response` match — both are the canonical error-transport mapping for the same `DomainError` enum; if Step 3 renamed or added variants (e.g. `RateLimited`), read the real `llm-gateway/src/domain/error.rs` before writing either match arm list so REST and gRPC never silently diverge on a variant.
- **`CompletionUseCase` signature caution**: as of the pre-Step-3 code, `complete` returns `Pin<Box<dyn Future<Output = Result<CompletionResponse, DomainError>>> + Send + '_>` (directly awaitable with `.await`) and `list_models` is a plain synchronous `fn(&self) -> Vec<ModelInfo>`. Step 3 may change either signature (see `llm-gateway/src/ports/inbound/completion.rs` post-Step-3) — read the actual trait before writing `completion_service.rs`/`models_service.rs` and adapt `.await` usage accordingly; do not assume the pre-Step-3 shape still holds verbatim.
- **Health service semantics**: mirror the existing REST `GET /health` liveness-only philosophy (`llm-gateway/src/adapters/inbound/rest/handlers.rs`'s `health()` always returns `{"status":"ok"}`) — mark both gRPC services `Serving` unconditionally at startup via `tonic-health`; do not wire deep dependency checks (e.g. probing OpenAI) into the health status in this step. If Step 8 added a REST `/ready` endpoint with real readiness semantics, this step's gRPC health check does **not** need to replicate that logic — it only needs to prove the gRPC server itself is reachable and serving, matching the liveness bar of `/health`.
- **Conflict notes** (carried from the plan): `llm-gateway/src/main.rs` edits in this step are additive server-startup lines only (build the gRPC server, run it alongside the REST server) — do not restructure the existing DI-assembly block above it. On the Go side, this step touches only new files under `server/proto/`; it does not create, modify, or generate any `.go` file, so it cannot conflict with any other same-wave step touching `server/`.
- **Conventions**: all new Rust code needs rustdoc (`///`) on public symbols per `CLAUDE.md`; all `.proto` comments and Rust doc comments are English-only. No Chakra UI / web rules apply (this step touches only `llm-gateway/` and `server/proto/`).
