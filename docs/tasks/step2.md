# Step 2: Go test infrastructure: testcontainers helper + shared mocks

## Meta
- **Type**: testing
- **Components**: server
- **Wave**: 1 (parallel group — all steps of the same wave can run concurrently)
- **Depends on**: None
- **Unlocks**: Step 7: Go event-driven messaging core: MessageHub, atomic sequences, response linkage | Step 12: Server: MinIO object storage + attachments + presigned upload endpoints | Step 13: Go 5-tier RBAC domain + authorization middleware + ModelUsecase | Step 20: Server: Kratos session auth swap + identity migration
- **Size**: 1 PR (a few hours for one AI agent)

## Context
The Go server currently has zero integration tests against a real PostgreSQL instance — `server/internal/interface/repository/postgres/*.go` (room, message, user repositories) are exercised only indirectly through hand-written in-memory mocks duplicated across usecase and handler test files. `phases.md`'s "Web complete version" scope adds several PRs (RBAC, MinIO attachments, event-driven MessageHub, Kratos auth) that all need to add or extend repositories and rely on trustworthy concurrency/constraint behavior (atomic sequence allocation, unique-violation mapping, transactional rollback) that only a real database can verify. This step builds the shared foundation — a testcontainers-backed PostgreSQL harness and one canonical mocks package — so every later step reuses it instead of re-inventing container setup or copy-pasting another mock.

## Goal
After this PR, `server/internal/testutil/postgres` provides a reusable helper that starts a `postgres:17-alpine` testcontainer, applies all SQL files under `server/migrations/` in order, and hands back a ready `*pgxpool.Pool` plus a cleanup function; `server/internal/testutil/mocks` provides one configurable in-memory implementation each of `room.RoomRepository`, `message.MessageRepository`, `user.UserRepository`, `auth.AuthService`, and `ai.LLMGateway`, replacing the 8 duplicated hand-written mocks currently spread across `usecase/room`, `usecase/message`, `usecase/auth`, `interface/handler`, and `interface/middleware` test files. New `*_integration_test.go` files under `interface/repository/postgres` prove the harness works by exercising real repository code against the real database for sequence-allocation concurrency, room-create rollback, and unique-constraint error mapping. `task test:server:integration` runs these against Docker; plain `task test:server` (and CI-safe `go test ./...`) remains fast and container-free via a build tag.

## Out of scope
- Any change to production repository code, domain interfaces, or `schema.sql` (this step is test-only; `dbChanges` is empty).
- Adding integration tests for every repository method — only the three concurrency/rollback/constraint scenarios named above are required; broader repository coverage is left to later steps that touch those repositories (e.g. Step 7, Step 12, Step 13).
- CI pipeline wiring (GitHub Actions) — excluded per the binding decision to skip Phases 21-23 (deploy/CI-CD); `task test:server:integration` only needs to be runnable locally via Docker.
- Adding `testify` or any assertion library — the codebase's existing convention is plain `testing` with manual `t.Fatalf` checks; keep new tests consistent with that style.
- Redis, WebSocket/MessageHub, RBAC, MinIO, or Kratos test infrastructure — those are introduced by their own steps (7, 12, 13, 20) which will extend `server/internal/testutil` additively.

## Implementation notes
- **Existing patterns to reuse**: `server/internal/infrastructure/database/postgres.go`'s `NewPool(ctx, databaseURL)` already builds a pool with ping-verified connectivity — call it from the testcontainers helper rather than duplicating pool construction logic.
- **Repository interfaces to mock/implement against** (do not change their signatures):
  - `server/internal/domain/room/repository.go` — `RoomRepository` (`Create`, `GetByID`, `ListByUserID`, `Update`, `Delete`, `AddMember`, `GetMember`, `ListMembers`, `RemoveMember`).
  - `server/internal/domain/message/repository.go` — `MessageRepository` (`Create`, `GetByID`, `ListByRoom`, `ListByRoomUpTo`, `GetNextInRoom`, `UpdateAIResponse`, `Delete`, `GetNextSequence`).
  - `server/internal/domain/user/repository.go` — `UserRepository` (`Create`, `GetByID`, `GetByEmail`, `GetByUsername`, `Update`, `Delete`).
  - `server/internal/domain/auth/service.go` — `AuthService` (`Register`, `Login`, `ValidateToken`).
  - `server/internal/domain/ai/gateway.go` — `LLMGateway` (`Complete`, `ListModels`).
  - Shared sentinel errors live in `server/internal/domain/errors.go` (`ErrNotFound`, `ErrEmailAlreadyExists`, `ErrUsernameAlreadyExists`, `ErrInvalidCredentials`, `ErrInvalidToken`, `ErrLLMGateway`, etc.) — mocks and integration assertions must use these, not ad hoc errors.
  - Concrete implementations to test against: `server/internal/interface/repository/postgres/room_repository.go`, `message_repository.go`, `user_repository.go` — read them before writing integration tests so assertions match actual SQL/constraint names (e.g. constraint names `users_email_unique` / `users_username_unique` used in `user_repository.go`'s `pgerrcode.UniqueViolation` mapping).
- **Migration source of truth**: `server/migrations/` contains Atlas-generated plain SQL files (currently just `20260220060722_initial.sql`) plus `atlas.sum` (not SQL — must be excluded when the helper globs `*.sql`). `server/atlas.hcl` and `server/schema.sql` define the declarative schema but the testcontainers helper should apply the versioned migration files directly (via `pgx`/`pgxpool` `Exec`), not invoke the `atlas` CLI, to keep the test harness dependency-free of the Atlas binary. Because there is currently only one migration file, this step's helper must still glob and sort by filename (not hardcode the single filename) so it keeps working once later steps (7, 12, 13, 20, and others per the schema.sql conflict convention) add new migrations.
- **Module/package layout**: new packages go under `server/internal/testutil/` (a new top-level directory alongside `domain/`, `usecase/`, `interface/`, `infrastructure/`, `cmd/`) — `server/internal/testutil/postgres/` and `server/internal/testutil/mocks/`. Both are internal-only (already enforced by Go's `internal/` visibility) and intended purely for `_test.go` consumption; nothing in non-test code should import them.
- **Build tag discipline**: only `server/internal/testutil/postgres/*.go` and the new `*_integration_test.go` files under `interface/repository/postgres/` carry `//go:build integration`. `server/internal/testutil/mocks/*.go` must NOT carry the tag — it needs to compile for ordinary `go test ./...` runs since it replaces mocks used by non-integration usecase/handler tests.
- **GoDoc**: every exported symbol in both new packages needs a GoDoc comment describing what it does, why (test isolation/reuse), and any constraints (e.g. "container is torn down via t.Cleanup; do not call Close on the returned pool directly") per `CLAUDE.md`'s Go docstring convention.
- **Taskfile edit**: `Taskfile.yml`'s existing `test:` task has `deps: [test:server, test:gateway]` and `test:server` runs `go test ./...` in `dir: server`. Add `test:server:integration` as a sibling task (do not fold it into `test:server` or `test`), following the same `dir: server` / `cmds:` shape already used.
- **go.mod additions are additive**: this step only adds new `require` entries (testcontainers-go + postgres module + their transitive deps); it does not touch any existing dependency version, so it cannot conflict with other same-wave steps' `go.mod` edits (per `conflictNotes`).
- **Chakra UI / web rules do not apply** — this step touches only `server/`.
