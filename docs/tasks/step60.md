# Step 60: Final E2E gate + docs/progress sync

## Meta
- **Type**: testing
- **Components**: web, infra, docs, server, llm-gateway
- **Wave**: 9 (parallel group — all steps of the same wave can run concurrently)
- **Depends on**: Step 56: E2E regression: auth, OAuth/Hydra, rooms, members, invitations, groups | Step 57: E2E regression: realtime AI core — send, model select, context controls, rate limiting | Step 58: E2E regression: summarization, streaming, private mode, images/Vision | Step 59: E2E regression: billing and room fork
- **Unlocks**: None
- **Size**: 1 PR (a few hours for one AI agent)

## Context
Steps 56-59 each add a Playwright regression suite scoped to its own area (identity/collaboration, realtime AI core, advanced AI, billing/fork) and each step's fix mandate is bounded to failures inside its own spec files. Nothing in the plan has ever run *all four* suites together in one clean-slate pass, so cross-area interactions — shared fixture users colliding across suites, a room created by one suite's global setup leaking into another suite's assertions, timing/order dependencies between specs that pass individually but flake when run back-to-back — are still unverified. Separately, `phases.md`'s Phase 2-20 checklist boxes, `.ai_progress/phase1.md`-style per-phase trackers, `README.md`/`README-ja.md`, `.env.example`, and `CLAUDE.md`'s Interface Swap Points table still describe the Phase-1-only state of the repo (SimpleJWT-only auth, `InProcessHub`, REST-only `LLMClient`, no rate limiting) even after the "Web complete version" scope (Phases 2-20) has been implemented across the preceding 59 steps. This step is the thin final gate that makes the whole E2E suite green from a single clean `docker compose up` and brings every piece of project documentation into agreement with what was actually built, recording the small number of deliberate deviations the plan already anticipated (5-tier RBAC delivered in one merged step instead of split Basic/Full phases, dex mock OIDC standing in for real Google/GitHub credentials, Hydra shipped with a first-party demo client rather than external third-party consumers).

## Goal
After this PR, running the Step 10 E2E harness end to end from a completely clean state — `task test:e2e:down` (if anything is left running) followed by `task test:e2e:up` and `task test:e2e` — executes the full Playwright suite (the Step 10 smoke spec, every feature-area spec shipped by steps 30/37/38/44/45/47/48/52/53/54, and all four regression suites from steps 56-59) in a single run with zero failures and zero flaky retries needed. Any cross-suite ordering/isolation bug uncovered by running everything together, and any narrowly-scoped functional bug in server/llm-gateway/web code that only surfaces under the full-suite run (not visible when a single area suite runs alone), is fixed in this PR. `README.md`, `README-ja.md`, `phases.md`, every `.ai_progress/phaseX.md` file for Phases 2-20, `.env.example`, and `CLAUDE.md`'s Interface Swap Points table are updated to reflect the final implemented architecture, with the three anticipated deviations documented explicitly rather than silently left inconsistent. The `.ai_progress` checklists across all 20 phases are reconciled so every checkbox state matches actually-merged code.

## Implementation notes

### Running the gate
Use the exact Taskfile tasks Step 10 defines (`Taskfile.yml`): `task test:e2e:up` (start the test-profile compose stack on alternate ports — `db-e2e:5433`, `api-e2e:8090`, `llm-gateway-e2e:8091`, `llm-stub:8092`, `web-e2e:3001`), `task test:e2e` (ensures the stack is up, then runs `bunx playwright test` from `web/`, seeding via `globalSetup`), and `task test:e2e:down` (tears down the test profile including volumes). Do not invent new Taskfile tasks for this step — reuse these verbatim; if a fix requires a small addition (e.g. a `--workers=1` flag to deflake a specific ordering issue), make it inside `web/playwright.config.ts`'s config object, not a new task.

### Where regression specs live
Steps 56-59 each add their own spec files under `web/e2e/` (e.g. `web/e2e/regression/auth.spec.ts`, `web/e2e/regression/realtime-ai.spec.ts`, `web/e2e/regression/advanced-ai.spec.ts`, `web/e2e/regression/billing-fork.spec.ts` — inspect the actual filenames those steps land, since exact naming is each step's own choice) alongside every area spec from steps 30/37/38/44/45/47/48/52/53/54. When diagnosing a full-run-only failure, first re-run the single suspect spec file in isolation (`bunx playwright test path/to/spec.ts`) to confirm whether it is a genuine isolation bug (passes alone, fails in the full run) versus a pre-existing bug in that suite that steps 56-59 already should have caught (fix in place either way, since this step's fix mandate covers "cross-area integration fixes bounded to failures in the full run" — a spec that only fails when run after another suite's fixtures exist is squarely in scope even if the root cause traces back to an earlier step's code).

### Seed/fixture hygiene pattern
`web/e2e/support/fixtures.ts` (Step 10) exports the shared fixture user/room constants that the smoke spec and, likely, several area specs reuse. If the full run reveals that two suites both mutate or depend on the exact same fixture room/user in conflicting ways (e.g. one suite archives the fixture room via room-fork, breaking another suite's later assumption that it is active), the fix is to have the offending suite create its own dedicated room/user (with a suite-specific name/email prefix) instead of overloading the single shared fixture — follow whatever naming convention the other area specs already established rather than inventing a new one.
