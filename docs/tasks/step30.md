## Context
Step 20 landed `KratosAuthService` on the Go side and taught `server/internal/interface/middleware/auth.go` to accept credentials from *either* an `Authorization: Bearer` header (used by its own native-flow `Register`/`Login` calls and by `web/e2e/seed/seed.ts`) *or* a named session cookie (default `ory_kratos_session`, via the `"cookie:"`-prefixed `ValidateToken` path) — but explicitly left the cookie path unexercised end to end and kept `docker-compose.yml`'s `AUTH_MODE` default at `simple_jwt`, deferring the flip to this step. Meanwhile the web app (post Step 4/Step 9/Step 17) still authenticates through a JWT-shaped BFF: `app/api/auth/{login,register,logout}/route.ts` forward plain email/password bodies to Go's `/auth/{login,register}`, mint an httpOnly `access_token` cookie, and the catch-all `app/api/proxy/[...path]/route.ts` reads that cookie and re-attaches it as `Authorization: Bearer <token>` on every proxied call. This step is the explicit "no dead zone" flip called out in the plan-wide auth data-plane notes: the web app switches to driving Kratos's browser self-service login/registration flows (rendering the `ui.nodes` Kratos returns, per the plan's flow-based UI requirement), the BFF proxy stops minting/attaching a Bearer token and instead forwards the browser's Kratos session cookie straight through to the Go API, and `AUTH_MODE=kratos` becomes the `docker-compose.yml` default — closing the gap Step 20 deliberately left open.

## Goal
After this PR, `docker-compose.yml`'s `api` (and `api-e2e`) service defaults to `AUTH_MODE=kratos`; the browser never obtains or reads any bespoke `access_token` cookie set by the Next.js app. Instead, `web/src/features/auth/components/LoginForm.tsx` and `RegisterForm.tsx` fetch a Kratos browser self-service flow through a new `web/src/app/api/kratos/[...path]/route.ts` proxy, render its `ui.nodes` as Chakra `Field.Root` fields driven by `react-hook-form` + `zod`, and submit back to Kratos through the same proxy; a successful submission causes Kratos to set its own `ory_kratos_session` cookie on the app's origin (because the proxy round-trips through `/api/kratos/*`, keeping it first-party). `web/src/app/api/proxy/[...path]/route.ts` no longer reads or attaches any bespoke token — it forwards the incoming request's raw `Cookie` header verbatim to the Go API, which resolves the session via Step 20's cookie fallback path. `web/src/middleware.ts` gates `(main)`/`(auth)` routes on the presence of the `ory_kratos_session` cookie instead of `access_token`. The old JWT-issuing `app/api/auth/{login,register,logout}/route.ts` handlers and the now-meaningless `authRequest` helper are deleted. Logout drives Kratos's self-service logout flow through the same proxy. The Playwright suite gains a dedicated auth spec exercising registration, login, session persistence across reload, and logout against the real Kratos container, and the auth feature's MSW handlers are rewritten to mock Kratos flow responses instead of the retired JWT endpoints.

- **Server-side contract this step consumes (do not change)**: `server/internal/interface/auth/kratos.go`'s `ValidateToken` accepts a bare token as `X-Session-Token` (used by the native-flow path) or a `"cookie:"`-prefixed value which it turns into a `Cookie: <cookieName>=<value>` header for `GET {KRATOS_PUBLIC_URL}/sessions/whoami`; `server/internal/interface/middleware/auth.go` falls back to reading the named cookie (default `ory_kratos_session`, `KRATOS_COOKIE_NAME` env) only when no `Authorization` header is present. This step's rewritten `app/api/proxy/[...path]/route.ts` must therefore *not* set any `Authorization` header itself — forwarding the raw `Cookie` header is sufficient and is exactly what the middleware expects.
- **Kratos AJAX/SPA contract**: every request this step's new `/api/kratos/[...path]` proxy makes to Kratos must include `Accept: application/json` — without it, `self-service/{login,registration}/browser` and flow submission endpoints respond with `302`/`303` HTML redirects intended for full-page browser navigation instead of returning/accepting JSON, which `fetch`-based code cannot follow into a same-origin cookie write. `redirect: "manual"` is not needed once `Accept: application/json` is set correctly — Kratos's own SPA support returns the flow/session JSON directly on `200`, or the validation-failed flow JSON directly on `400`.
- **Cookie passthrough on `Set-Cookie`**: browser `fetch`/`Response` objects can carry multiple `Set-Cookie` headers (Kratos may set more than one, e.g. session + CSRF cookies); `Headers.get("set-cookie")` only returns one. Use `response.headers.getSetCookie()` (available in the Next.js/Node fetch implementation this project runs on) and append each value individually to the outgoing `NextResponse`'s headers, or construct the response via `new Response(body, { headers })` and push each cookie with `headers.append("set-cookie", value)` — a single `set()` call overwrites all but the last cookie.
- **CSRF token**: Kratos includes a `csrf_token` hidden input node in every flow's `ui.nodes`; the login/registration submit body must include it verbatim (read via `getNodeMessages`/a small `getNodeValue(nodes, "csrf_token")` helper alongside the ones described in Scope) or Kratos rejects the submission with a `400` CSRF-mismatch flow. Because the CSRF cookie is itself set by the `GET .../browser` call and must be present on the follow-up `POST`, both calls must go through the same-origin `/api/kratos/*` proxy (never bypassed) so the browser attaches that cookie automatically.
- **`AUTH_MODE` flip rationale**: Step 20 intentionally kept `docker-compose.yml`'s default at `simple_jwt` so its own PR was verifiable without depending on cookie-based browser flows; this step is the one place in the plan authorized to change that default, per the plan-wide "AUTH DATA-PLANE PLAN" notes. `simple_jwt` remains a fully supported opt-out (`AUTH_MODE=simple_jwt docker compose up`), but with this step's web changes, a running instance under `AUTH_MODE=simple_jwt` would no longer have a working login UI (the web app now only speaks Kratos flows) — this is an accepted, documented tradeoff of the flip, not a regression to fix here.
- **Chakra UI v3 conventions**: follow `.claude/rules/chakra-ui.md` — keep `Field.Root`/`Field.Label`/`Field.ErrorText` compound usage and `PasswordInput`/`PasswordStrengthMeter` snippets exactly as Step 17 established; do not introduce any new UI library. `role="alert"` must still be set explicitly on every `Field.ErrorText` per Step 17's finding that the component itself sets no ARIA role.
- **Conflict notes**: this step is the sole owner of `web/src/app/api/kratos/[...path]/route.ts` (new), and rewrites `web/src/app/api/proxy/[...path]/route.ts`, `web/src/middleware.ts`, `web/src/lib/http-client.ts`, `web/src/lib/auth-cookie.ts` (deleted) / `web/src/lib/kratos-cookie.ts` (new), and every file under `web/src/features/auth/`. No same-wave web step (chat UI work per the skeleton's conflict note) touches these files, so there is no line-level overlap. `docker-compose.yml`/`Taskfile.yml` edits here are additive lines within the existing `api`/`api-e2e`/`web`/`web-e2e` blocks only (per the project's alphabetized-additive convention) — no new service blocks, no reordering.
