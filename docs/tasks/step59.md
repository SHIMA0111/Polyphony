# Step 59: E2E regression: billing and room fork

## Meta
- **Type**: testing
- **Components**: web, infra
- **Wave**: 8 (parallel group — all steps of the same wave can run concurrently)
- **Depends on**: Step 10: Playwright E2E harness + seeded compose test stack + LLM stub | Step 48: Web: token balance + usage history UI | Step 52: Web room fork UI | Step 53: Web: plans, Stripe Checkout, subscription management, billing history UI
- **Unlocks**: Step 60: Final E2E gate + docs/progress sync
- **Size**: 1 PR (a few hours for one AI agent)

## Context
`phases.md` Phases 16, 17, and 20 ("Token Balance Management", "Stripe Billing", "Room Fork") are each covered by a single feature step with its own narrow, happy-path Playwright spec: Step 48's `web/e2e/billing.spec.ts` proves a balance is visible and drives one exhausted-balance run into the 402 error path; Step 52's `web/e2e/room-fork.spec.ts` proves one fork run reaches `completed` and the destination room becomes usable; Step 53's own spec (once it lands) is expected to cover only initiating a Stripe Checkout redirect, not a full round-trip through Stripe's real test-mode Checkout UI, a stripe-cli-forwarded webhook, and the resulting subscription-state change reflected back in the app. None of the three feature steps is required to prove that balance display, usage history, Checkout, subscription management, and room fork all keep working together once every wave-5/6/7 UI change (top-bar insertions, `RoomSettingsDrawer` sections, `ChatRoom.tsx` conditionals) has landed on top of them. Per the plan's four-suite regression split (56: identity/collaboration, 57: realtime AI core, 58: advanced AI, 59: this step), this step is the dedicated billing/fork regression suite: it exercises the complete billing and room-fork user journeys end-to-end in fresh spec files, and fixes only the failures those specs actually surface — it is not a general hardening or refactor pass.

## Goal
After this PR, two new Playwright spec files exist under `web/e2e/regression/` — `billing.spec.ts` and `room-fork.spec.ts` — run automatically by the existing `task test:e2e` command (Playwright's `testDir: "./e2e"` from Step 10 picks up every spec recursively, so no new Taskfile task is required). `billing.spec.ts` proves the full billing journey in one seeded browser session: balance visible in the top bar, usage history reachable and paginable, an AI send correctly rejected with a 402 once the balance is exhausted (with the plain "Send" path still working), a real Stripe test-mode Checkout completed via the browser and confirmed via a stripe-cli-forwarded webhook, and the resulting subscription reflected as the current plan with a working cancel/manage action. `room-fork.spec.ts` proves the full fork journey — trigger, live progress, archived-room read-only treatment for a viewer who navigates to the destination room mid-copy, completion, and the new room being fully usable afterward — plus an RBAC regression check that a non-admin/master room member never sees the fork trigger. Any concrete defect either spec uncovers in the already-merged Step 48/52/53 code is fixed in this same PR, scoped strictly to what the failing spec shows; no unrelated cleanup is performed.

## Implementation notes
- **Harness reuse**: follow `web/e2e/smoke.spec.ts`'s registration pattern and `web/e2e/support/fixtures.ts`'s exported constants (Step 10) for any seeded-user/room needs; `web/playwright.config.ts`'s `testDir: "./e2e"` already picks up every `*.spec.ts` file recursively, so placing specs under `web/e2e/regression/` requires no config change. Run against the Step 10 isolated test compose profile (`task test:e2e:up`, alternate ports — API at `http://localhost:8090`, web at `http://localhost:3001`), never the developer's own dev stack.
- **Assumed contracts from Step 48** (as shipped; adapt to the actual merged shapes if they differ slightly): `GET /billing/balance -> { user_id, balance, updated_at }`; `GET /billing/transactions?cursor=&limit= -> { transactions: [...], next_cursor }`; `BalanceBadge` in the `(main)` top bar links to `/billing/usage`; a 402 from the AI-send endpoint surfaces as an inline error in `MessageInput` reading roughly "Insufficient token balance…".
- **Assumed contracts from Step 52** (as shipped; adapt to the actual merged shapes if they differ slightly): `POST /rooms/:roomId/fork -> 202 { job: ForkJobResponse, new_room: RoomResponse }`; `GET /rooms/:roomId/fork-jobs/:jobId -> 200 ForkJobResponse { id, source_room_id, new_room_id, status: "pending"|"running"|"completed"|"failed", total_messages, copied_messages, error_message, created_at, updated_at }`; the "Fork this room" trigger lives in `RoomSettingsDrawer`'s admin/master-gated section; a room with `is_archived: true` renders read-only in `ChatRoom.tsx` (no `MessageInput`, an explanatory banner).
- **Contracts from Steps 49/53** (pinned by those step documents — confirm against the merged code): a plan-selection surface at `web/src/app/(main)/billing/plans/page.tsx` backed by `GET /billing/plans -> { plans: [{ code, name, description, price_cents, currency, interval: "month"|"one_time", token_allowance }] }`; "Subscribe"/"Buy tokens" actions calling `POST /billing/checkout-session -> 201 { checkout_url }` (body `{ type: "subscription"|"token_purchase", plan_code?, package_code? }`) that the browser is redirected to; a current-plan/subscription-status surface at `web/src/app/(main)/billing/subscription/page.tsx` backed by `GET /billing/subscription -> 200 { status, plan_code, monthly_token_allocation, current_period_start, current_period_end, cancel_at_period_end, canceled_at } | 204` (mapped client-side to `status: "none"`); a cancel/manage action calling `POST /billing/subscription/cancel`; a billing-history view at `/billing/history` backed by `GET /billing/payments -> { payments: [{ id, kind, amount_cents, currency, tokens_credited, status, created_at }], next_cursor }`. Locate the actual page routes and button labels in the merged codebase (`grep -rn "checkout\|subscription\|billing/plans" web/src/app web/src/features`) before writing selectors, and prefer `getByRole`/`getByText` locators over inventing `data-testid`s, matching the convention established in `web/e2e/smoke.spec.ts`.
- **Driving real Stripe Checkout from Playwright**: Stripe's hosted Checkout page (redirect mode, not an embedded iframe) is a normal cross-origin page Playwright can interact with directly after `page.waitForURL(/checkout\.stripe\.com/)`. Fill the email field and the card element's stable test selectors (`#cardNumber`, `#cardExpiry`, `#cardCvc`, plus name/postal fields as Stripe's test Checkout form requires) with Stripe's documented test values (`4242 4242 4242 4242`, any future MM/YY, any 3-digit CVC), submit, then `page.waitForURL()` back to the app's success route. This requires `STRIPE_SECRET_KEY` (a real `sk_test_...` test-mode key) to be configured for `api-e2e` in the Step 10 test compose profile — confirm this env var is already wired (it is a transitive Step-53-server dependency) via `docker compose --profile test config | grep -i stripe`; do not hardcode a key into the spec.
- **Webhook confirmation**: the assertion that matters is not "Checkout redirected successfully" but "the subscription record in the database actually updated" — this only happens once stripe-cli (or an equivalent forwarding mechanism) delivers the `checkout.session.completed`/`customer.subscription.*` webhook to the API. Poll the subscription-status endpoint/page with a bounded wait after the redirect rather than asserting immediately; if the webhook never arrives (forwarding not configured), the spec will time out here, and the correct action per this step's scope is to document the missing forwarding infra (see Scope) rather than paper over it with a longer timeout or a mocked assertion.
- **RBAC regression selector for `room-fork.spec.ts`**: reuse whatever invitation/role-assignment UI Steps 13/36/37 shipped to add a second user to the room as `member` (not `admin`/`master`); if no such UI exists yet in the merged codebase at implementation time, seed the membership directly via the API (`POST` to whatever member-invitation endpoint those steps expose) from within the spec's setup rather than through the UI, and note that shortcut in a spec comment.
- **English-only** code/comments per `CLAUDE.md`; both new spec files are TypeScript Playwright tests, no server/gateway code changes expected unless a genuine defect requires one.
- **No `schema.sql`/Atlas changes** — this step is Playwright specs plus, at most, small targeted bug fixes in already-shipped `web/` (or, only if strictly necessary to fix a demonstrated defect, `server/`/`llm-gateway/`) code.
- **Conflict notes**: this step's only files are `web/e2e/regression/billing.spec.ts`, `web/e2e/regression/room-fork.spec.ts`, and (if added) `web/e2e/regression/README.md` — disjoint from whatever spec files Steps 56/57/58 add to the same `web/e2e/regression/` directory in the same wave; never edit another regression step's spec file. Any bug-fix edits this step makes to already-merged Step 48/52/53 source files must be the minimal diff that resolves a failure one of this step's own specs demonstrates — do not restructure `RoomSettingsDrawer.tsx`, `ChatRoom.tsx`, or the `billing`/`rooms` feature modules beyond that.
