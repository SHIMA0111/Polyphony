# Step 32: Server: room fork (async batch copy)

## Meta
- **Type**: feature
- **Components**: server
- **Wave**: 6 (parallel group — all steps of the same wave can run concurrently)
- **Depends on**: Step 7: Go event-driven messaging core: MessageHub, atomic sequences, response linkage; Step 13: Go 5-tier RBAC domain + authorization middleware + ModelUsecase; Step 24: Server: per-room AI provider/model settings
- **Unlocks**: Step 52: Web room fork UI
- **Size**: 1 PR (a few hours for one AI agent)

## Context
Phase 20 of `phases.md` ("Room Fork") calls for copying a room's entire conversation into a new room to create a branch, without blocking the API request on however long that copy takes — `phases.md` explicitly specifies an async batch job (1000 messages/batch), sequence renumbering in the new room, and `is_archived=true` on the destination room until the copy finishes. Today `rooms` has no archival concept and `domain/room.RoomRepository`/`domain/message.MessageRepository` have no bulk-copy or ascending-cursor primitives — messages can only be read newest-first (`ListByRoom`, `ListByRoomUpTo`) or written one at a time (`Create`). This step adds the missing schema, repository primitives, and a goroutine-based worker that copies a source room's messages into a freshly created destination room in ordered batches, re-linking AI response pairs and re-allocating sequence numbers via the atomic `ReserveSequenceRange` primitive Step 7 introduced, while giving callers a job resource they can poll for progress.

## Goal
`POST /rooms/:roomId/fork` (admin/master only, via Step 13's RBAC primitives) synchronously creates a new room — `is_archived=true`, `forked_from_room_id` pointing at the source, `ai_provider`/`ai_model` copied from the source room, owned by the caller — plus a `room_fork_jobs` row in `pending` status, and returns both immediately (HTTP 202). A background goroutine then copies every message from the source room into the new room in batches of up to 1000, oldest-first, reserving a contiguous sequence range per batch via `MessageRepository.ReserveSequenceRange`, preserving sender/content/type/status and remapping `in_response_to_message_id` to the corresponding copied message's new ID (so human+AI pairs stay linked even when a pair straddles a batch boundary), and updating `room_fork_jobs.copied_messages` after each batch. On completion the job is marked `completed` and the new room's `is_archived` flips to `false`, unblocking new posts into it; on any error the job is marked `failed` with an error message and the new room stays archived. `GET /rooms/:roomId/fork-jobs/:jobId` lets any member of the source or destination room poll job status/progress at any time. While a room is archived, `MessageUsecase.SendMessage`/`SendAIMessage` reject new posts into it with a new `domain.ErrArchivedRoom` (mapped to HTTP 409).

## Out of scope
- Web Frontend fork button / progress UI (Step 52 consumes the endpoints this step ships).
- Any change to `ai.LLMGateway`, context building, model resolution beyond reusing the room already loaded by Step 24's changes, or streaming (Phases 18/19, other steps).

- Filtering copied messages by AI-context concerns (`exclude_from_ai`, cutoff, soft-delete) — a fork is a structural branch of the full conversation, independent of AI-context filtering rules owned by other steps; every message in the source room is copied regardless of any such flags.
- Deleting/cleaning up a fork job row or the archived room if the fork is abandoned; no retry/resume of a `failed` job (a failed fork's new room simply stays archived and empty/partial — operators can delete it manually via the existing `DELETE /rooms/:roomId`).
- Copying room membership beyond the caller (the caller becomes the new room's sole member/master via the normal `RoomRepository.Create` behavior); inviting the source room's other members to the fork is not part of this step.
- Blocking `RegenerateAIMessage` on an archived room — only `SendMessage`/`SendAIMessage` (which create new rows) are guarded; regenerating an existing message's content is left untouched.
- Any change to `docker-compose.yml`/`Taskfile.yml`.

## Implementation notes
- **conflictNotes**: Step 24 is a merge-order dependency only, for `rooms` table schema edits (Step 24 adds `ai_provider`/`ai_model`; this step adds `forked_from_room_id`/`is_archived`) — rebase onto Step 24's merged `schema.sql` before running `task migrate:generate` so the two Atlas migrations apply in sequence and `atlas.sum` doesn't diverge. This is the only wave-6 step touching the `rooms` table; do not expect or resolve conflicts with any other wave-6 step on that table. The new `room_fork_jobs` table and the new repository methods on `MessageRepository`/`RoomRepository` are pure additions (new table, new interface methods) and touch no schema owned by other steps.
- Follow Clean Architecture layering per `CLAUDE.md`: `server/internal/domain/roomfork/` has zero non-stdlib imports (like `domain/room`, `domain/message`); `server/internal/usecase/room/fork.go` is the only place that orchestrates `domainroom.RoomRepository` + `domainmessage.MessageRepository` + `domainroomfork.ForkJobRepository` together — the domain packages themselves never import each other beyond what already exists (`domain/event` importing `domain/message` from Step 7 is the only such exception, and this step does not need a similar one: `roomfork.Job` only stores plain strings for room/job IDs, no cross-domain struct embedding).
- Reuse existing patterns instead of inventing new ones:
  - `RoomRepository.Create` (`server/internal/interface/repository/postgres/room_repository.go`) already does "insert room + init `room_sequences` + add owner as master member" atomically in one transaction — call it unchanged for the new room; do not duplicate that logic in `fork.go`.
  - `MessageRepository.ReserveSequenceRange` (Step 7, `server/internal/interface/repository/postgres/message_repository.go`) is the exact primitive for atomic per-batch sequence allocation in the new room — call it once per batch with `count = len(batch)`, never per-message.
  - `middleware.Authorize`/`domainroom.ActionManageRoom` (Step 13) is the same rule Step 24's `UpdateSettings` already uses for "admin and master only, not member/guest/reader" — reuse it verbatim rather than adding a new rule or action.
  - `handleRoomError`/`handleMessageError` (`room_handler.go`/`message_handler.go`) already map `domain.ErrForbidden`→403 and `domain.ErrNotFound`→404; only `handleMessageError` needs a new branch, for `domain.ErrArchivedRoom`→409.
  - `scanMessage`/`messageColumns` (`message_repository.go`) must be reused (not duplicated) by `ListByRoomAfter`.
- DB migration: `schema.sql` is Atlas-declarative (see `server/atlas.hcl`); edit `schema.sql` only, then run `task migrate:generate -- add_room_fork` from the repo root (shells into `server/`, runs `atlas migrate diff <name> --env local` per `Taskfile.yml`), committing the generated file(s) under `server/migrations/` plus the updated `atlas.sum`. Do not hand-edit `atlas.sum`.
- Goroutine lifecycle: `ForkRoom` launches `runForkJob` with `context.Background()` (a fresh, unbound context), not the HTTP request's context — the job must keep running after the request completes and the request's context is canceled. This mirrors the fire-and-forget philosophy Step 7 established for `MessageHub.Publish` (background work must never block or be tied to the triggering request's lifecycle), though unlike `Publish` this background work is durable (its state lives in `room_fork_jobs`, pollable after the goroutine exits or the process restarts mid-job — a job stuck in `running` after a crash is a known limitation, not handled by this step).
- Testability: keep `runForkJob` unexported but call it directly (synchronously, no `go`) from `fork_test.go`, which lives in the same `room` package — this lets the required ">1 batch" unit test drive the exact multi-batch/boundary-remapping logic deterministically without sleeping/polling a real goroutine. Reserve the sleep/poll pattern (`GetForkJobStatus` in a bounded retry loop) for the testcontainers end-to-end test only, where the real asynchronous path (including the actual `go` launch from `ForkRoom`) must be exercised at least once.
- Sequence/ID remapping correctness is the crux of this step: because messages are read via `ListByRoomAfter` in strictly ascending source-sequence order, and Step 7 guarantees a human message's sequence is always less than its AI response's, the `map[oldID]newID` built incrementally across the whole job (not reset per batch) is guaranteed to already contain an AI message's human counterpart's new ID by the time that AI message is copied — even when the human message was in a previous batch. If `InResponseToMessageID` is non-nil but not yet in the map (should not happen given the sequence invariant, but guard defensively), leave the copied field `nil` rather than erroring the whole job.
- `CreateBatch`'s transaction should roll back entirely on any single insert failure within the batch (no partial batch persisted), so `copied_messages` progress only ever advances by whole, successfully-committed batches.
- New room naming: `Name = src.Name + " (Fork)"` is a simple, deterministic default — no uniqueness enforcement needed (multiple forks of the same room are allowed and will each get the same suffixed name; `phases.md` does not require de-duplication).
- All new/changed exported Go symbols need GoDoc comments describing what/why/constraints/error behavior, per `CLAUDE.md`; give the unexported `runForkJob` a doc comment too since it is the step's most complex piece of logic.
