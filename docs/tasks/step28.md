# Step 28: Go: gRPC LLM client swap + retry + health

## Meta
- **Type**: feature
- **Components**: server
- **Wave**: 4 (parallel group — all steps of the same wave can run concurrently)
- **Depends on**: Step 1: Go server foundation: DI/router split, structured logging, lint, config | Step 19: gRPC contract: proto definitions + Rust tonic inbound adapter
- **Unlocks**: Step 34: Model metadata (token limits + pricing) across gateway/server/web
- **Size**: 1 PR (a few hours for one AI agent)

## Context
Phase 8 of `phases.md` calls for swapping the Go API's LLM Gateway communication from REST to gRPC, adding retries and health checks (`phases.md` lines 424-435), and `CLAUDE.md`'s Interface Swap Points table lists `LLMClient` as REST-initially / gRPC-in-Phase-8. Today `server/internal/interface/gateway/llm_client.go` is the sole `ai.LLMGateway` implementation, calling the gateway's REST endpoints (`POST /completions`, `GET /models`) with a plain `*http.Client` and no retry logic. Step 19 lands the shared `.proto` contract and a Rust tonic inbound adapter on the gateway side; this step adds the Go-side gRPC client so the two transports can coexist behind an environment flag, per the plan-wide architecture note "`LLMGateway` interface with REST and gRPC implementations behind an env flag."

## Goal
The Go server can talk to the LLM Gateway over gRPC through a new `interface/gateway/grpc_client.go` that implements `ai.LLMGateway` using the generated stubs from the shared proto contract, with exponential-backoff retry on transient gRPC status codes and a gRPC health check performed via the standard `grpc.health.v1.Health` service. Which transport is used (REST or gRPC) is selected purely by an environment variable read in `server/internal/infrastructure/config/config.go` and wired in `server/internal/app/container.go`; the existing REST `LLMClient` is left untouched and remains the default, so no existing deployment behavior changes unless the new flag is set.

- [ ] Generate the Go client stubs (`protoc`/`buf` with `protoc-gen-go` and `protoc-gen-go-grpc`, both available on `PATH`) into `server/internal/interface/gateway/grpc/llmgatewaypb/` (`completion.pb.go`/`completion_grpc.pb.go`, `models.pb.go`/`models_grpc.pb.go`). Add a `server/buf.gen.yaml` (and `server/buf.yaml` pointing at `../proto` as the module root, or a `Makefile`/`Taskfile` snippet using raw `protoc` — pick one and document the exact command in a comment at the top of the generated-code directory or in this PR's description) so regeneration is reproducible; commit the generated files (this repo has no existing codegen pipeline to hook into).
- [ ] Add `google.golang.org/grpc` and `google.golang.org/protobuf` to `server/go.mod` (`go get google.golang.org/grpc google.golang.org/protobuf` from `server/`), plus `google.golang.org/grpc/health` / `google.golang.org/grpc/health/grpc_health_v1` (part of the `google.golang.org/grpc` module) for the standard health-check client.
- [ ] Create `server/internal/interface/gateway/grpc_client.go` (package `gateway`, alongside the existing `llm_client.go`) implementing `ai.LLMGateway`:
  - `type GRPCClient struct` holding a `*grpc.ClientConn`, the generated `llmgatewaypb.CompletionServiceClient` and `llmgatewaypb.ModelsServiceClient`, a `grpc_health_v1.HealthClient`, and retry configuration (`maxRetries int`, `baseBackoff time.Duration`).
  - `func NewGRPCClient(target string, maxRetries int, baseBackoff time.Duration) (*GRPCClient, error)`: dials with `grpc.NewClient(target, grpc.WithTransportCredentials(insecure.NewCredentials()))` (plaintext gRPC inside the Docker network, matching the REST client's unauthenticated intra-network call today), constructs both clients, and returns the `*GRPCClient`. Does not block on connection establishment (matches `grpc.NewClient` semantics) — connection/health failures surface on first RPC call instead of at construction time.
  - `func (c *GRPCClient) Complete(ctx context.Context, req *ai.CompletionRequest) (*ai.CompletionResponse, error)`: maps `ai.CompletionRequest` → `llmgatewaypb.CompletionRequest`, invokes `c.callWithRetry` around `c.client.Complete`, maps the response back to `*ai.CompletionResponse`, wrapping any final error in `domain.ErrLLMGateway` (mirroring `llm_client.go`'s error-wrapping style).
  - `func (c *GRPCClient) ListModels(ctx context.Context) ([]ai.ModelInfo, error)`: same pattern via `c.client.ListModels`.
  - `func (c *GRPCClient) Close() error`: closes the underlying `*grpc.ClientConn`.
  - A private `callWithRetry(ctx context.Context, fn func(context.Context) error) error` helper implementing exponential backoff (`baseBackoff * 2^attempt`, capped at a fixed max delay, e.g. 2s, with a small jitter) that retries only when `status.Code(err)` is one of `codes.Unavailable`, `codes.ResourceExhausted`, or `codes.DeadlineExceeded`, up to `maxRetries` attempts, and returns immediately (no retry) for any other code. Respects `ctx.Done()` between attempts.
  - A private `checkHealth(ctx context.Context) error` method calling `c.healthClient.Check(ctx, &grpc_health_v1.HealthCheckRequest{})` (empty `Service` field checks overall server health per the standard protocol) and returning an error if the response status is not `SERVING`; call this once during `app.NewContainer` construction (see below) to fail fast/log a warning if gRPC transport is selected but the gateway isn't reachable — do not gate every `Complete`/`ListModels` call on a health check (that would double request latency).
- [ ] Extend `server/internal/infrastructure/config/config.go`'s `Config` struct and `Load()` with:
  - `LLMGatewayTransport` (env `LLM_GATEWAY_TRANSPORT`, values `"rest"` or `"grpc"`, default `"rest"`; any other value falls back to `"rest"` with a `slog.Default().Warn(...)`, following the same tolerant-fallback pattern Step 1 introduces for the duration fields).
  - `LLMGatewayGRPCAddr` (env `LLM_GATEWAY_GRPC_ADDR`, default `"llm-gateway:50051"`).
  - `LLMGatewayGRPCMaxRetries` (env `LLM_GATEWAY_GRPC_MAX_RETRIES`, parsed as int, default `3`, falls back to default on parse failure).
  - `LLMGatewayGRPCBaseBackoff` (env `LLM_GATEWAY_GRPC_BASE_BACKOFF`, parsed via `time.ParseDuration`, default `100ms`, falls back to default on parse failure — same pattern as Step 1's `DBMaxConnLifetime` etc.).
  `Load()`'s error behavior for the two existing required vars (`DATABASE_URL`, `JWT_SECRET`) is unchanged.
- [ ] Wire the transport switch in `server/internal/app/container.go`'s `NewContainer` (added by Step 1): after building the REST `gateway.NewLLMClient(cfg.LLMGatewayURL)` reference, branch on `cfg.LLMGatewayTransport` — if `"grpc"`, construct a `gateway.NewGRPCClient(cfg.LLMGatewayGRPCAddr, cfg.LLMGatewayGRPCMaxRetries, cfg.LLMGatewayGRPCBaseBackoff)` instead, call its health check once and log the outcome (`Info` if healthy, `Warn` if not — do not fail container construction on an unhealthy/unreachable gateway, since the gateway container may start after the API in Compose), and assign whichever client to the `Container`'s `LLMGateway` field (the field the REST client currently occupies) so every downstream usecase/handler that already depends on `ai.LLMGateway` needs zero changes. ## Implementation notes
- Existing REST client for reference/parity: `server/internal/interface/gateway/llm_client.go` — mirrors its error-wrapping convention (`fmt.Errorf("%w: ...", domain.ErrLLMGateway, err)`, from `server/internal/domain/errors.go`) and its DTO-mapping style (loop-based slice conversion) in the new gRPC client.
- Domain interface being implemented: `server/internal/domain/ai/gateway.go` (`ai.LLMGateway`) and its DTOs in `server/internal/domain/ai/entity.go` (`ChatMessage`, `CompletionRequest`, `CompletionResponse`, `ModelInfo`) — the new client must produce identical semantics to `LLMClient` (same field mapping) so the usecase layer (`server/internal/usecase/message/usecase.go`, `server/internal/interface/handler/model_handler.go`) is fully transport-agnostic; do not add any gRPC-specific type to the `domain/ai` package.
- `server/internal/app/container.go` and the DI wiring pattern (`Container`, `NewContainer(ctx, cfg)`) are established by Step 1 — read that PR's result before wiring the transport switch; this step only adds one branch inside the existing gateway-construction block, it must not restructure `NewContainer` or the router/registrar files.
- Config conventions: follow `server/internal/infrastructure/config/config.go`'s existing style exactly — plain `os.Getenv` + string/duration default fallback, `fmt.Errorf` reserved for the two required vars (`DATABASE_URL`, `JWT_SECRET`); do not introduce a config library. Use `time.ParseDuration` and `slog.Default().Warn(...)` for the backoff duration, matching the pattern Step 1 introduces for `DB_MAX_CONN_LIFETIME` et al.
- `go_package` / generated code: confirm `protoc` and `buf` are available (`which protoc buf`) in the dev environment before choosing a codegen invocation; either a `buf generate` flow (`server/buf.yaml` + `server/buf.gen.yaml` with `protoc-gen-go`/`protoc-gen-go-grpc` plugins) or a bare `protoc --go_out=... --go-grpc_out=...` command is acceptable — keep the generated files under `server/internal/interface/gateway/grpc/llmgatewaypb/` and commit them since there is no CI codegen step in this repo yet.
- No `schema.sql` or Atlas migration changes are needed for this step (no DB schema impact) — do not run `task migrate:generate`.
- All new exported symbols (`GRPCClient`, `NewGRPCClient`, `Close`, and any exported helper) need GoDoc comments per `CLAUDE.md`'s convention (describe what/why/constraints/error behavior), matching the doc-comment density already present on `LLMClient`.
- **Conflict notes**: this step adds exactly one new file (`server/internal/interface/gateway/grpc_client.go`, plus the generated `grpc/llmgatewaypb/` package) and one new branch inside `container.go`'s existing gateway-construction block; `llm_client.go` is not modified. `docker-compose.yml` and `.env.example` edits are additive `environment:`/variable-list lines only on the existing `api:` service block, consistent with the repo-wide convention (Step 1's conflict notes) that later server steps append rather than restructure that file.
