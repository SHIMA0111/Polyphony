# Step 23: Server: AI context control (soft delete, exclude flag, cutoff, context builder)

## Meta
- **Type**: feature
- **Components**: server
- **Wave**: 4 (parallel group — all steps of the same wave can run concurrently)
- **Depends on**: Step 13: Go 5-tier RBAC domain + authorization middleware + ModelUsecase
- **Unlocks**: Step 24: Server: per-room AI provider/model settings | Step 38: Web AI context UI: exclude toggle, delete, token meter | Step 41: Server: private AI mode | Step 50: Server: context summarization with cached summaries | Step 51: Go: consume gateway stream + WS chunk forwarding
- **Size**: 1 PR (a few hours for one AI agent)

## Context
`phases.md` Phase 5 ("AI Context Control") requires that AI context assembly consider three things it currently ignores: an explicit per-message AI-exclusion flag, soft-deleted messages, and a per-room cutoff datetime. Today `MessageUsecase.SendAIMessage`/`RegenerateAIMessage` (`server/internal/usecase/message/usecase.go`) build LLM context by calling an unexported `buildChatMessages` method that only skips `status=failed` placeholders; there is no message deletion path at all (`MessageRepository.Delete` exists but is called by nothing), no way to exclude a message from AI context, and `rooms` has no cutoff column. Step 13 lands the typed `room.Role`/`Action` RBAC primitives and the `Authorize`/`RequireRole` helpers this step needs to gate the new mutation endpoints. This step gives Phase 5 a real home: `domain/ai/context_builder.go`, matching the path phases.md's architecture tree already reserves for it, becomes the single place all AI-context filtering rules live, and later steps (context summarization in Step 50, streaming in Step 51) build on top of the interface it defines rather than re-deriving filtering logic.

## Goal
After this PR, `messages` has `is_deleted` and `exclude_from_ai` columns and `rooms` has `ai_context_cutoff_at`; a new `DELETE /rooms/:roomId/messages/:messageId` endpoint soft-deletes a message (sender or admin/master only), a new `PATCH /rooms/:roomId/messages/:messageId` endpoint toggles `exclude_from_ai` (any role that can invoke AI), and a new `PATCH /rooms/:roomId/ai-context-cutoff` endpoint sets or clears the room's cutoff (admin/master only). `MessageRepository.ListByRoom`/`ListByRoomUpTo` no longer return soft-deleted rows. A new `ai.ContextBuilder` interface in `server/internal/domain/ai/context_builder.go`, with a `DefaultContextBuilder` implementation, is the single place that filters soft-deleted messages, `exclude_from_ai` messages, `status=failed` placeholders, and pre-cutoff messages out of the chat history sent to the LLM Gateway; `MessageUsecase.SendAIMessage`/`RegenerateAIMessage` are wired to use it instead of the old ad hoc `buildChatMessages` method.

## Out of scope
- Anthropic/Gemini provider adapters, per-room provider/model selection, and any `ModelUsecase` filtering by room (Step 24 and Phase 6-7).
- The LLM Gateway token-estimation endpoint and any Go-side proxy for it (tracked separately as the gateway/Go pairing that follows Step 14's harness — this step does not touch `llm-gateway/` or add token counting anywhere).
- History summarization and any `message_context_summaries` caching (Step 50) — `ContextBuilder` is deliberately a plain filter/map function in this step; summarization is a later decorator/alternate implementation behind the same interface.
- Private AI mode and any per-message/per-room visibility scoping beyond `exclude_from_ai` (Step 41).
- Web frontend UI for the delete/exclude/cutoff controls or a token meter (Step 38) — this step ships server endpoints only.
- Wiring `RequireRole`/`RequireRole`-style Echo middleware into the new routes — consistent with how `SendAI`/`RegenerateAI` already perform authorization inside the usecase layer rather than via route middleware, the new `Delete`/`UpdateExclude`/`UpdateAIContextCutoff` handlers do the same; no `main.go` route-group restructuring.
- Hard/permanent deletion, message content editing, or any purge/retention job for soft-deleted rows.
- `GetNextInRoom`'s soft-delete filtering — `RegenerateAIMessage`'s existing "find the AI response following this human message" lookup is unchanged; if that AI response was itself soft-deleted, regenerate behavior for that edge case is left as-is (undefined by this step) rather than guessed at.
- Adding a new DB index for `is_deleted` — the existing `idx_messages_room_sequence` composite index is retained as-is; revisit indexing if it becomes a measured bottleneck.

## Implementation notes
- **Files this step reads first to confirm current (post-Step-13) state before editing**: `server/internal/domain/room/repository.go`, `server/internal/domain/room/entity.go` (or wherever Step 13 puts `Role`/`Action`), `server/internal/interface/middleware/rbac.go` (the `Authorize` helper signature), and the actual current bodies of `MessageUsecase.SendAIMessage`/`RegenerateAIMessage` and `RoomUsecase` in `server/internal/usecase/`. Step 13 is a dependency that changes these files; do not assume the pre-Step-13 shapes shown by the pre-existing code in this repo snapshot (e.g. `checkMembership`, `RoomMember.Role string`) are still current — verify against the merged state.
- **Reuse, don't duplicate**: `MessageRepository.UpdateAIResponse` (`server/internal/interface/repository/postgres/message_repository.go`) is the template for `UpdateExcludeFromAI`'s signature/SQL shape (`id`, mutated field(s), `updatedAt`, `RowsAffected() == 0` → `domain.ErrNotFound`). `RoomUsecase.UpdateRoom`'s existing get-check-mutate-persist shape is the template for `UpdateAIContextCutoff`.
- **Context builder placement matches phases.md**: the plan's architecture tree (see `phases.md`, Go API Server Architecture section) already lists `domain/ai/context_builder.go` — this step is what actually creates it. Keep `domain/ai/` free of any HTTP/pgx import (it currently has none; `entity.go`/`gateway.go` are pure Go + `context`).
- **`middleware.Authorize` usage**: Step 13 establishes the (architecturally unusual but explicitly decided) pattern of usecases importing `internal/interface/middleware` for the non-HTTP `Authorize(role, action) error` helper, specifically so usecases with an already-loaded `RoomMember` don't need a second repository round-trip or a duplicated capability matrix. This step follows that same pattern for `SetExcludeFromAI` (`domainroom.ActionInvokeAI`) and `UpdateAIContextCutoff` (`domainroom.ActionManageRoom`) — do not invent a new authorization primitive.
- **`DeleteMessage`'s owner-or-admin rule intentionally does not use `Action`/`Allows`**: Step 13's `Action` enum (`ActionSendMessage`, `ActionInvokeAI`, `ActionManageMembers`, `ActionManageRoom`, `ActionDeleteRoom`) has no message-level delete action, and adding one would touch `domain/room/role.go`, a file Step 13 owns exclusively per the plan's conflict notes. Use `member.Role.AtLeast(domainroom.RoleAdmin)` directly (already GoDoc'd/tested by Step 13) combined with the sender-equality check instead.
- **DTO/response shape**: `RoomResponse` gains `ai_context_cutoff_at` as an ISO-8601/RFC3339 nullable field, serialized the same way Go's `encoding/json` already serializes `*time.Time` elsewhere in this codebase (e.g. no custom marshaling needed). `MessageResponse` gains `is_deleted`/`exclude_from_ai` as plain booleans.
- **Schema/migration convention** (see `CLAUDE.md` and the plan's schema convention): edit `server/schema.sql` additively — only the `messages` and `rooms` table column lists in this step — then run `task migrate:generate -- add_ai_context_control_fields` from the repo root; this shells into `server/` and runs `atlas migrate diff <name> --env local` per `Taskfile.yml`, producing a new file under `server/migrations/` alongside `20260220060722_initial.sql` (and Step 13's own migration, already merged) and updating `server/migrations/atlas.sum`. Do not hand-edit `atlas.sum`.
- **Conflict notes**: this is the sole wave-4 step editing the `messages` table; Step 24 (per-room provider/model settings) is serialized after this step for its own `rooms` table edit (`ai_provider`/`ai_model` columns) — rebase onto this step's merged `rooms.ai_context_cutoff_at` addition before adding those columns, rather than racing the same `ALTER TABLE rooms` migration. This step also shares `SendAIMessage`/`RegenerateAIMessage` with Step 42 (token balance management): this step owns context assembly (the `contextBuilder.Build` call and everything feeding it); Step 42 is expected to add only a pre-call balance guard in its own separate file/call site, not touch the context-building logic added here. The `ai.ContextBuilder` interface frozen in this step is consumed — not modified — by Step 50 (summarization) and Step 51 (streaming); those steps may supply alternate implementations or wrap `DefaultContextBuilder`, but must not change `Build`'s method signature.
- English-only code/comments/docs; GoDoc on every new exported symbol per `CLAUDE.md`.
