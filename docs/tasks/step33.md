# Step 33: Server: Redis rate limiting + Kratos session cache

## Meta
- **Type**: feature
- **Components**: server
- **Wave**: 5 (parallel group — all steps of the same wave can run concurrently)
- **Depends on**: Step 20: Server: Kratos session auth swap + identity migration | Step 31: Redis in compose + RedisHub MessageHub swap
- **Unlocks**: Step 57: E2E regression: realtime AI core — send, model select, context controls, rate limiting
- **Size**: 1 PR (a few hours for one AI agent)

## Context
Phase 10 of `phases.md` calls for Redis-backed sessions, Pub/Sub, and rate limiting. Step 31 already brings a shared Redis connection into the server for `RedisHub` (`domain/event.MessageHub`'s Redis-backed implementation); this step reuses that same connection for two independent, previously-missing pieces of hardening: (1) `/auth/register`/`/auth/login` and the AI-invoke endpoints (`POST /rooms/:roomId/messages/ai`, `POST /rooms/:roomId/messages/:messageId/regenerate`) currently have no abuse protection at all — an attacker can brute-force credentials or hammer the (metered, provider-billed) AI path with unlimited requests; (2) Step 20's `KratosAuthService.ValidateToken` (`server/internal/interface/auth/kratos.go`) makes a real HTTP round trip to Kratos's `/sessions/whoami` on every single authenticated request, which is correct but wasteful once Kratos becomes the default auth backend. This step adds a Redis token-bucket rate limiter for the first problem and a short-TTL Redis cache in front of Kratos's `whoami` calls for the second, with an explicit logout path so the cache never outlives Kratos's own view of session validity by more than one TTL window.

## Goal
After this PR, `POST /auth/register` and `POST /auth/login` are protected by a per-client-IP Redis token-bucket limiter, and `POST /rooms/:roomId/messages/ai` / `POST /rooms/:roomId/messages/:messageId/regenerate` are protected by a per-authenticated-user Redis token-bucket limiter; both return HTTP 429 with a `Retry-After` header (in seconds) when exceeded, and the limiter fails open (logs and lets the request through) if Redis itself is unreachable, so a Redis outage degrades to "no rate limiting" rather than taking the API down. Both limits are configurable via environment variables, and the Docker Compose E2E test profile (Step 10's `api-e2e` service) sets much higher limits so Playwright specs never trip a 429 unintentionally. Independently, when `AUTH_MODE=kratos`, `ValidateToken` results are cached in Redis under a short TTL (SHA-256-hashed token as the key, so raw session tokens/cookies are never stored in Redis) so most authenticated requests no longer make a network call to Kratos; a new `POST /auth/logout` endpoint purges the cache entry for the caller's token and, for Kratos, also calls Kratos's real session-revocation endpoint so a logged-out session cannot be used again even within the cache TTL window. `AUTH_MODE=simple_jwt` is unaffected by the cache (SimpleJWT's `ValidateToken` is already a local, network-free HMAC check) and its `/auth/logout` is a no-op 200 (documented limitation: stateless JWTs cannot be server-side revoked without a denylist, which is out of scope here).

- [x] Add `server/internal/interface/auth/cached.go` (new file): `CachedAuthService` wraps any `domainauth.AuthService` and adds a Redis-backed cache in front of `ValidateToken`:
  - `func NewCachedAuthService(inner domainauth.AuthService, redisClient *redis.Client, ttl time.Duration) *CachedAuthService`.
  - `Register`/`Login` delegate to `inner` unchanged (no caching — these are not hot, repeated-per-request calls).
  - `ValidateToken(ctx, token)`: compute `key := "whoami:" + hex(sha256(token))`; `GET` the key from Redis — on a hit, unmarshal the cached `domainauth.Claims` (JSON) and return it without calling `inner`; on a miss (or any Redis error — fail open to `inner`, do not fail the request), call `inner.ValidateToken(ctx, token)`, and if it succeeds, `SET key <json> EX ttl` (best-effort — log and ignore a Redis write failure, never fail the request because the cache write failed). Never cache an error result (a transient Kratos hiccup must not pin a false rejection for the whole TTL window).
  - `Revoke(ctx, token) error`: always delete the Redis key for `token` first (best-effort, log on failure), then, if `inner` implements `auth.Revoker`, call `inner.Revoke(ctx, token)` and return its error; if `inner` does not implement `Revoker`, return `nil` (documents the SimpleJWT no-op case for whichever service happens to be wrapped, though in practice only `KratosAuthService` is ever wrapped by this type — see container wiring below).

## Out of scope
- Rate limiting any route other than `/auth/register`, `/auth/login`, and the two AI-invoke routes — no general-purpose per-route or global rate limiting is added here.
- A denylist/revocation mechanism for `SimpleJWTService` — its `/auth/logout` remains a no-op 200; true stateless-JWT revocation (e.g. a Redis-backed denylist checked on every `ValidateToken` call) is a larger design decision not required by this step's skeleton and is not implemented.
- Redis Pub/Sub, `RedisHub`, or any WebSocket/`MessageHub` change — entirely Step 31's territory; this step only reuses the Redis client Step 31 already established.
- Any RBAC (`middleware/rbac.go`) change — this step only adds a new sibling middleware file and per-route middleware arguments; it never touches `RequireRole`/`Authorize`.
- Per-plan/tier-based or billing-aware rate limits (e.g. higher limits for paying rooms) — Phase 16-17 territory, not this step.
- Distributed rate-limit dashboards/metrics or alerting on 429 rates — out of scope; this step only returns correct HTTP semantics.
- Any change to `KratosAuthService.ValidateToken`/`Register`/`Login`'s existing bodies beyond the new `Revoke` method — the cache wraps the service from outside; `kratos.go`'s existing three methods are untouched.
- Browser-side handling of 429s or the logout call (web frontend work) — server-only step; the web frontend's own logout/rate-limit UX (if any) is for a later web-focused step to add.

- **Redis client reuse**: this step assumes Step 31 already added a shared `*redis.Client` (package `github.com/redis/go-redis/v9`) to the DI wiring in `server/internal/app/container.go`, configured from `Config.RedisURL` (env `REDIS_URL`, already placeholder-scaffolded in `.env.example`/`docker-compose.yml` per Step 6 as `redis://redis:6379`). Reuse that exact client for both `redis_rate.NewLimiter(...)` and `CachedAuthService`'s cache reads/writes — do not construct a second connection pool. If Step 31 named the field, package, or client-construction helper differently than assumed here, adapt the reference accordingly; the only hard requirement is a single shared client instance.
- **Token-bucket library choice**: `github.com/go-redis/redis_rate/v10` implements the GCRA (generic cell-rate algorithm) token bucket entirely server-side via a Redis Lua script bundled in the library, avoiding a hand-rolled script or a naive `INCR`+`EXPIRE` fixed-window counter (which has boundary-burst problems a token bucket avoids). It is built directly on top of `go-redis/v9`, matching Step 31's client.
- **Key hashing for the whoami cache**: use `crypto/sha256` (stdlib) on the raw token/cookie string, hex-encode the digest, and prefix with `"whoami:"` — this avoids ever writing a raw, replayable bearer token or session cookie value into Redis as a key (which could otherwise leak via `redis-cli KEYS`/`MONITOR`/slow-log output). Store the cached value as JSON-marshaled `domainauth.Claims` (currently just `{"UserID": "..."}`), so the cache format survives future additions to `Claims` without a breaking migration (unmarshal ignores unknown/missing fields by default with `encoding/json`).
- **Fail-open is a deliberate, documented tradeoff** for both new pieces: a Redis outage must not take down login, AI invocation, or any authenticated request — it should only remove rate-limiting/caching benefits until Redis recovers. Log every fail-open occurrence at `Warn` (not `Error`, since it is an expected degraded-mode path, not a bug) via `middleware.GetLogger(c)` where an Echo context is available, or `slog.Default()` inside `CachedAuthService` (which has no Echo context).
- **`Retry-After` header convention**: mirror the exact convention already established on the LLM Gateway side (`llm-gateway/src/adapters/inbound/rest/handlers.rs`'s `DomainError::RateLimited` → HTTP 429 + `Retry-After` header, per Steps 3/8/14) so both halves of the stack return 429s the same shape for any client-side retry logic to handle uniformly.
- **DB shape**: none — `dbChanges` is empty for this step; no `schema.sql` edit, no `task migrate:generate` run.
- **Conflict notes** (per skeleton, "New middleware file + registrar lines"): the bulk of this step's blast radius is one new file (`middleware/rate_limit.go`) plus small, additive per-route middleware arguments in `routes_auth.go`/`routes_message.go` (not a restructuring of either file's existing route list). The `container.go` touch is a single new field plus a one-line conditional wrap inside the existing `AUTH_MODE` branch Step 20 already added — no other field or branch changes. The `kratos.go` touch is a single new additive method (`Revoke`), not a change to any existing method. The `docker-compose.yml`/`.env.example` touches are additive-only within existing blocks, consistent with the project's established convention (Steps 1/6/10/11/20).
