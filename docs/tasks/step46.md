# Step 46: Web: group management UI

## Meta
- **Type**: ui
- **Components**: web
- **Wave**: 6 (parallel group — all steps of the same wave can run concurrently)
- **Depends on**: Step 37: Web members, invitations, and roles UI | Step 40: Server: groups + batch invitations
- **Unlocks**: Step 56: E2E regression: auth, OAuth/Hydra, rooms, members, invitations, groups
- **Size**: 1 PR (a few hours for one AI agent)

## Context
`phases.md` Phase 13 ("Group Management + Batch Invitations") lets a user maintain personal address-book-style groups of other users and invite a whole group to a room in one action, instead of repeating Step 37's single-target invite-by-username flow once per person. Step 40 already shipped the full server surface for this (`GroupUsecase`/`GroupRepository`/`GroupHandler` behind `/groups*` and `POST /rooms/:roomId/invitations/batch-by-group`), and Step 37 shipped the `web/src/features/members/` module including `InviteDialog.tsx` (invite-by-username + generate-link) and the shared client-side RBAC-mirroring helpers in `web/src/features/members/lib/roles.ts` — but nothing in `web/` consumes any of Step 40's endpoints yet, and there is no group-scoped UI at all. This step builds a new `groups` feature module end to end, following the per-feature `types.ts` / `api/` / `hooks/` / `components/` pattern Step 9 established and Step 37 followed, and adds a group-picking batch-invite path into the `InviteDialog` Step 37 already owns.

## Goal
After this PR, a user can open a "Groups" screen from the top bar's avatar menu, see all groups they own, create a new group (name + description), open a group to rename/re-describe it or delete it, and manage its membership by adding/removing members by exact username (each row showing the resolved username Step 40's `GroupMemberWithUsername` join provides). Inside any room's invite dialog (`InviteDialog.tsx`, from Step 37), a new "Invite a group" section lets an admin/master pick one of their groups and a target role (reader/guest/member/admin, never master) and batch-invite the whole group in one call, showing how many members were invited and, for each skipped member, the reason (already a room member, already has a pending invitation, etc.) returned by the server — a single RBAC failure surfaces as one inline error instead of a partial list. New component tests (Vitest + RTL + MSW) cover group CRUD, membership management, and the batch-invite section; a new Playwright spec exercises the full group CRUD + membership + batch-invite lifecycle, including the skip-reason path on a repeated batch invite.

**Server response shapes this step's `api/` layer must match exactly** (from Step 40's server contracts):
```
GET    /groups                                       -> 200 { "groups": [{ "id","owner_id","name","description","created_at","updated_at" }] }
GET    /groups/:groupId                              -> 200 <Group>  | 403 (not owner) | 404
POST   /groups                                       -> 201 <Group>                        body: { "name", "description" }
PUT    /groups/:groupId                               -> 200 <Group>                        body: { "name", "description" }   | 403 (not owner)
DELETE /groups/:groupId                               -> 204                                | 403 (not owner)
GET    /groups/:groupId/members                       -> 200 { "members": [{ "id","group_id","user_id","username","added_at" }] }
POST   /groups/:groupId/members                        -> 201 { "id","group_id","user_id","username","added_at" }  body: { "username" }   | 404 (unknown username) | 409 (already a member)
DELETE /groups/:groupId/members/:userId                 -> 204                               | 403 (not owner)
POST   /rooms/:roomId/invitations/batch-by-group        -> 200 { "invited": [<Invitation>...], "skipped": [{ "user_id","username","reason" }...] }
                                                            body: { "group_id", "role", "expires_in_hours"? }
                                                            | 400 (invalid/master role) | 403 (caller doesn't own the group, or lacks Admin+ in the room)
```
Map HTTP error bodies (`{ "message": "..." }`) the same way the existing `httpClient`/proxy layer already normalizes them elsewhere — do not add a bespoke error-parsing path in this feature's `api/` modules.

**Why `httpClient.put` is a safe, minimal addition, not scope creep**: every existing Step 4/9 mutation in this codebase (`create-room.ts`, `create-invitation.ts`, `change-member-role.ts`, etc.) uses `post`/`patch`/`delete`; Step 40's `Update` group endpoint is the first REST contract in the plan to use `PUT` for a partial-object replace, and the Step 4 proxy route already forwards `PUT` end to end (`app/api/proxy/[...path]/route.ts` forwards "every method (GET/POST/PUT/PATCH/DELETE)" per Step 4's own contract) — only the thin client-side convenience wrapper is missing the method. Add it as a one-line mirror of the existing `patch` method's implementation; do not change `get`/`post`/`patch`/`delete`'s existing signatures or behavior.

**Chakra v3 conventions** (per `.claude/rules/chakra-ui.md`, applies to every new file under `web/src/features/groups/components/` and `web/src/app/(main)/groups/`): `@chakra-ui/react` compound components first (`Dialog.*`, `Menu.*`, `Avatar.*`, `Card.*`, `SimpleGrid`), style props only (no Tailwind/`cn()`), semantic color tokens (`bg.subtle`, `fg.muted`, `border`), `colorPalette="red"` for the destructive delete-group confirmation, `lucide-react` icons (`Users`, `UserPlus`, `Trash2`, or similar). Since `GroupList`/`GroupDetail`/`GroupMembersPanel`/`GroupPicker` are new UI surfaces (not small logic tweaks), use the `v0-design` skill per `CLAUDE.md`'s "UI Development Workflow" to generate their visual design, then adapt per the v0-conversion rules in `.claude/rules/chakra-ui.md` (replace shadcn/Radix primitives with the Chakra compound components named above, replace Tailwind classes with style props, keep `lucide-react` icons, replace `variant="destructive"` with `colorPalette="red"`). The `InviteDialog.tsx` and `(main)/layout.tsx` edits are small, additive insertions into existing structure and can be made directly without going through v0.

**Conflict notes**: This step owns the entire new `web/src/features/groups/` directory and `web/src/app/(main)/groups/**` outright — no other step touches them. It makes three narrowly scoped, additive edits to existing files: `web/src/lib/http-client.ts` (one new `put` method, non-breaking to existing methods), `web/src/features/members/components/InviteDialog.tsx` (one new section appended after the two Step 37 already owns — the "invite dialog owned here this wave" conflict note from this step's skeleton refers to this exact edit; Step 37 landed in a prior wave so there is no same-wave collision), and `web/src/app/(main)/layout.tsx` (one new `Menu.Item` inside the existing avatar menu, not touching Step 37's `InvitationsBellButton` insertion in the top bar).
