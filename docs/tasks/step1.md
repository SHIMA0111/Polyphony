# Step 1: Go server foundation: DI/router split, structured logging, lint, config

## Meta
- **Type**: refactor
- **Components**: server, infra
- **Wave**: 1 (parallel group — all steps of the same wave can run concurrently)
- **Depends on**: None
- **Unlocks**: Step 7: Go event-driven messaging core: MessageHub, atomic sequences, response linkage | Step 9: Web data layer migration: TanStack Query, RSC prefetch, per-feature API modules | Step 12: Server: MinIO object storage + attachments + presigned upload endpoints | Step 20: Server: Kratos session auth swap + identity migration | Step 27: Token estimation endpoint (gateway) + Go proxy | Step 28: Go: gRPC LLM client swap + retry + health
- **Size**: 1 PR (a few hours for one AI agent)

## Context
`server/cmd/api/main.go` currently does all DI wiring, route registration, and server lifecycle management inline (135 lines, one function). Every later server step (event-driven messaging, MinIO attachments, Kratos auth swap, token estimation proxy, gRPC LLM client) needs to add new dependencies and routes to this same file, which would force every later step onto a single serialized chain and guarantee merge conflicts. Error paths in the handler layer (`internal/interface/handler/*.go`) currently swallow the underlying error and return a generic `500`/`502` JSON body with no logging at all — there is no way to correlate a client-visible error with server-side context or a request ID. This step decomposes `main.go` into a small, append-friendly `internal/app` package, wires structured error logging with request-ID correlation into the existing centralized error-mapping functions, adds a `golangci-lint` configuration, and hardens the `pgxpool` connection pool configuration via environment variables — establishing the base that all later Go server steps build on without needing to touch each other's code. It also ships the one identity endpoint the whole plan otherwise lacks: an authenticated `GET /users/me` (whoami), which Step 9's web session hook consumes and which doubles as the first worked example of the new per-group route-registrar pattern.

## Goal
`server/cmd/api/main.go` is reduced to configuration loading, DI container construction, router construction, and start/shutdown lifecycle only. All dependency wiring lives in a new `server/internal/app` package split into a `Container` (DI holder) and one small route-registrar file per handler group, so later steps add a new registrar file or a new line in `container.go` instead of editing the same function body. Every request is tagged with a request ID that flows into structured `slog` log lines, and every centralized error-mapping function in the handler layer logs the underlying error (with request ID) before returning a `5xx`/`502` response. `golangci-lint` is configured and wired into `task lint:server`. The PostgreSQL pool's connection lifetime, idle timeout, and health-check period are configurable via environment variables instead of hardcoded pool size only.

## Implementation notes
- Reuse the exact wiring order already in `server/cmd/api/main.go` (repositories → `ifauth.NewSimpleJWTService` / `gateway.NewLLMClient` → usecases → handlers) inside `Container`'s `NewContainer`; do not change construction order or arguments, only relocate them.
- `middleware.JWTAuth` (`server/internal/interface/middleware/auth.go`) already takes an `auth.TokenValidator`; `Container.AuthUC` (the `*authusecase.AuthUsecase` returned by `authusecase.NewAuthUsecase`) already satisfies this — pass `c.AuthUC` the same way `main.go` currently does with `authUC`.
- The existing `handleRoomError` (`server/internal/interface/handler/room_handler.go`) and `handleMessageError` (`server/internal/interface/handler/message_handler.go`) already take `(c echo.Context, err error) error` — extend their bodies to call `middleware.GetLogger(c).Error(...)` before the final `c.JSON(http.StatusInternalServerError, ...)` (and, for `handleMessageError`, before the `ErrLLMGateway` → `502` branch too); no signature change is required since the logger is retrieved from the Echo context, which keeps existing handler test call sites (`room_handler_test.go`, `message_handler_test.go`) working without modification as long as those tests don't assert on log output.
- For `auth_handler.go`'s `Register`/`Login` and `model_handler.go`'s `List`, add the same `middleware.GetLogger(c).Error("...", "error", err)` call inline immediately before each `5xx`/`502` `c.JSON(...)` return — these are not routed through a shared error-mapping helper today.
- `echomw.RequestID()` (already registered in `main.go`) sets the `X-Request-Id` response header via `echo.HeaderXRequestID`; read it back with `c.Response().Header().Get(echo.HeaderXRequestID)` inside `RequestLogger`, since the ID is generated during the same middleware chain execution before your logger runs (register `RequestLogger` after `echomw.RequestID()` in `router.go`).
- Config: follow the existing pattern in `server/internal/infrastructure/config/config.go` (plain `os.Getenv` + default fallback, `fmt.Errorf` only for the two required vars) — do not introduce a config library (e.g. `envconfig`, `viper`); use `time.ParseDuration` and log via `slog.Default().Warn(...)` on parse failure, keeping `Load()`'s signature (`func Load() (*Config, error)`) unchanged.
- `NewPool` in `server/internal/infrastructure/database/postgres.go` sets `cfg.MaxConns`/`cfg.MinConns` on a `*pgxpool.Config` obtained from `pgxpool.ParseConfig`; add the three new fields (`cfg.MaxConnLifetime`, `cfg.MaxConnIdleTime`, `cfg.HealthCheckPeriod`) the same way, right after the existing `MaxConns`/`MinConns` assignment.
- No `schema.sql` or Atlas migration changes are needed for this step (no DB schema impact) — do not run `task migrate:generate`.
- `golangci-lint` is not currently installed/pinned anywhere in the repo (no `.golangci.yml`, no CI workflow, `go vet ./...` is the only lint today) — write `server/.golangci.yml` in the widely-supported schema (`run:`, `linters:` with `enable:` list, optional `linters-settings:` for `gosec`/`staticcheck`); if the `golangci-lint` binary available in your environment is a v2 release with an incompatible schema, adapt the config's shape to that binary's expected format while keeping the same linter set and `task lint:server` command — verification tolerates either schema as long as `golangci-lint run ./...` succeeds from `server/`.
- **Conflict notes**: this step claims `server/cmd/api/main.go` early specifically so that later server steps (7, 12, 20, 27, 28, and beyond) only ever add a new small file under `server/internal/app/` or a new field/line inside `container.go`/a registrar file, never touch the shrunk `main.go` again. The `Taskfile.yml` edit here is additive (only the `lint:server` task body changes) and must remain compatible with the separate additive edits later steps make to other tasks (e.g. `up`/`migrate:generate` deps in step 6) — do not reformat or reorder unrelated tasks in `Taskfile.yml`. The `docker-compose.yml` edit here only adds new `environment:` keys to the existing `api:` block and must not reorder or restructure the `api:` service block, since later steps (6, 10, 11, 12, 31, 44, 49, 55) add whole new alphabetized service blocks and additive env keys of their own.
