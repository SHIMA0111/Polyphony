# Step 50: Server: context summarization with cached summaries

## Meta
- **Type**: feature
- **Components**: server, web
- **Wave**: 6 (parallel group — all steps of the same wave can run concurrently)
- **Depends on**: Step 23: Server: AI context control (soft delete, exclude flag, cutoff, context builder) | Step 27: Token estimation endpoint (gateway) + Go proxy | Step 34: Model metadata (token limits + pricing) across gateway/server/web | Step 41: Server: private AI mode
- **Unlocks**: Step 58: E2E regression: summarization, streaming, private mode, images/Vision
- **Size**: 1 PR (a few hours for one AI agent)

## Context
`phases.md` Phase 18 ("Context Summarization") requires that when the filtered AI context would overflow a model's context window, older history is summarized by the AI and the summary is cached and reused, with only recent individual messages sent verbatim alongside it. By this wave, Step 23 has landed the frozen `ai.ContextBuilder.Build(msgs, cutoff) []ChatMessage` filter (soft-delete/exclude/cutoff-aware, chronological output, no I/O), Step 27 has added `ai.LLMGateway.EstimateTokens`, Step 34 has added `context_window`/pricing fields to `ai.ModelInfo`, and Step 41 has added per-message `Visibility` (`public`/`private`) with read-path filtering by `requestingUserID`. None of these steps decide what happens when the filtered context is simply too big, and none of them cache anything. This step is what actually makes `MessageUsecase.SendAIMessage`/`RegenerateAIMessage` (`server/internal/usecase/message/usecase.go`) detect overflow against a real (or fallback) token limit, summarize the older portion via the LLM Gateway, cache the result in a new `message_context_summaries` table, and surface whether a given AI response used a cached/fresh summary — both in the REST response and in the realtime event payload so Step 51's streaming path can carry the same flag without redesigning the contract.

## Goal
After this PR: `SendAIMessage`/`RegenerateAIMessage` estimate the token cost of the Step-23-filtered context via `ai.LLMGateway.EstimateTokens`, resolve the target model's context window via `ai.LLMGateway.ListModels` with a hard-coded fallback table when live metadata is unavailable or the model is unknown, and — when the estimate exceeds a token budget derived from that window — summarize the older portion of the fetched message window via `ai.LLMGateway.Complete`, cache the summary in a new `message_context_summaries` table, and prepend it (as a `system`-role `ChatMessage`) ahead of a verbatim recent tail. The cache is invalidated whenever a message delete or AI-exclude toggle happens in the room (Step 23's `DeleteMessage`/`SetExcludeFromAI`). Private messages (Step 41) are never written into the shared cache and are always kept verbatim regardless of age, so a cached summary can never leak one user's private exchange to another. `MessageResponse.used_context_summary` reports whether the just-produced AI message's context included a summary, and the same boolean is added to the realtime AI-message event payload. The web `MessageList` shows a small badge/tooltip on AI messages where `used_context_summary` is true.

## Out of scope
- Modifying `ai.ContextBuilder.Build`'s method signature — it stays exactly as Step 23 froze it (`Build(msgs []*message.Message, cutoff *time.Time) []ChatMessage`); this step only calls it multiple times over sub-slices and adds a new orchestration layer around it.
- Incremental/delta re-summarization that extends a previous summary with only newly-arrived older messages — this step's cache hit is an exact-match on `(room_id, model, covered_up_to_sequence)`; as new messages shift the boundary, the cache naturally misses and a fresh summary is computed. This is a deliberate simplification: the cache still helps repeated calls over an unchanged window (e.g. regenerate-without-new-messages, retried failed sends) even though a fast-growing conversation will re-summarize on most turns. A follow-up could make this incremental; not pursued here.
- Extending the fetch window beyond the existing `defaultContextMessages` (50) messages — summarization only ever operates within that already-fetched window; making the fetch window itself dynamic/unbounded is a separate concern.
- Real tokenizer-accurate limit enforcement or hard-rejecting oversized requests — this step degrades gracefully (best-effort summarization, falls back to sending the raw context if summarization itself fails) rather than erroring the AI call.
- Streaming AI responses and any `CompletionChunk`/SSE wiring (Step 51) — this step only adds the `UsedContextSummary` field to the event payload Step 51 will also emit over its streaming path; it does not touch streaming itself.
- Room-level AI cutoff settings UI or any per-message token meter UI (owned by the settings drawer and per-message-controls steps) — this step's only web surface is the summary-used badge in `MessageList`.
- Persisting `used_context_summary` on the `messages` table or making it visible after a page reload/refetch of historical messages — it is intentionally a one-time, request-scoped signal, not a message property; a future step could persist it if that becomes a requirement.
- Any new gRPC surface, provider adapter changes, or `llm-gateway` code changes — `EstimateTokens`/`ListModels`/`Complete` already exist and are reused as-is.
- Long-history seed tooling or an automated E2E spec proving summarization actually triggers end-to-end against realistic conversation volumes — that is Step 58's job; this step's own verification relies on unit tests with injected low-context-window fixtures plus a manual smoke check.

- **Vision/attachment interplay (Step 39, decided)**: image-bearing messages are treated like any other message for summarization purposes — they enter the older-public summarizable bucket by age/visibility exactly like text-only messages (do NOT exempt them). When refactoring `SendAIMessage`/`RegenerateAIMessage`'s call sites into `assembleAIContext`, preserve Step 39's post-`Build` attachment enrichment: apply the enrichment to each bucket's `Build` output, so (a) the verbatim buckets (`recentChat`, `olderPrivateChat`, and the under-budget older-public case) keep their full parts-shaped content for the actual completion call, and (b) the summarizer input (`BuildSummarizationPrompt(olderPublicChat, includeImages)`) receives the enriched list, with `includeImages` resolved upfront from the model's `SupportsImageInput` metadata (Step 34) via `ResolveSupportsImageInput` — metadata-driven, not trial-and-error. For a Vision-capable model the real image parts go through the same provider mappings as any Vision send, and this is deliberately the moment to spend Vision tokens: once summarized, the images age out of the live context and only the summary's textual description of them survives. For a non-Vision (or unknown) model, image parts are substituted with `[image attachment]` placeholders upfront, so no doomed call is issued. Presigned URLs in the summarizer *input* are fine (they are freshly issued by the enrichment and fetched by the provider at call time); the cached summary is the model's text *output*, so no URL or image data is ever persisted. The image-bearing call's cost is amortized by the cache.
- **Ordering caveat for `boundarySeq`**: `msgs` (as returned by `ListByRoom`/`ListByRoomUpTo`) is sequence-descending (newest first). After removing `recentRaw` (the first `summaryRecentTailCount` entries), the remainder is still sequence-descending; splitting that remainder into `olderPublicRaw`/`olderPrivateRaw` preserves relative order within each bucket but the two buckets are interleaved in real time — when reassembling the final chat message list, concatenate `olderPrivateChat` immediately before `recentChat` (both are "never summarized, always verbatim" regardless of exact interleaving with the summarized public bucket); this is an accepted, documented approximation of true chronological order, not a bug to "fix" by re-sorting — do not attempt to interleave individual private and public older messages by timestamp.
- **`system`-role summary message**: Rust's `llm-gateway` domain `Role` enum (`llm-gateway/src/domain/model.rs`) already has a `System` variant, and `CompletionRequestDto::into_domain`'s `parse_role` helper (introduced alongside `/completions`, extended by Step 27 for `/tokens/estimate`) is expected to accept `"system"` as a valid role string — confirm this before relying on it; if `parse_role` does not currently accept `"system"`, that is a pre-existing gap in an earlier step, not something to silently patch here — if you hit it, treat it as a blocking dependency issue and note it explicitly in the PR description rather than expanding this step's scope into `llm-gateway`.
- **`DeleteMessage`/`SetExcludeFromAI` invalidation is coarse by design**: wiping the entire room's cached summary on any delete/exclude-toggle (rather than checking whether the mutated message actually falls within the previously-summarized range) is intentionally conservative — it trades a possibly-unnecessary re-summarization for guaranteed correctness (never serving a summary that silently includes content that should now be excluded).
