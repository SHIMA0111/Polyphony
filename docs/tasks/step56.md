# Step 56: E2E regression: auth, OAuth/Hydra, rooms, members, invitations, groups

## Meta
- **Type**: testing
- **Components**: web, infra
- **Wave**: 7 (parallel group — all steps of the same wave can run concurrently)
- **Depends on**: Step 10: Playwright E2E harness + seeded compose test stack + LLM stub | Step 30: Web: Kratos-driven login/registration + auth data-plane flip | Step 37: Web members, invitations, and roles UI | Step 44: OAuth social login via Kratos OIDC (dex mock + Google/GitHub) | Step 46: Web: group management UI | Step 55: Ory Hydra OAuth2/OIDC provider + first-party client demo
- **Unlocks**: Step 60: Final E2E gate + docs/progress sync
- **Size**: 1 PR (a few hours for one AI agent)

## Context
By wave 6, five separate steps have each shipped their own Playwright spec in isolation against the Step 10 harness: `web/e2e/smoke.spec.ts` (Step 10, register/create-room/send-message), `web/e2e/auth.spec.ts` (Step 30, Kratos password login/registration/logout), `web/e2e/oauth-dex.spec.ts` (Step 44, dex social login), `web/e2e/members.spec.ts` (Step 37, invite/accept/role-change/leave/transfer-ownership/RBAC gating), and `web/e2e/groups.spec.ts` (Step 46, group CRUD + batch invite). Step 55 shipped no Playwright spec at all — its Hydra flow is verified by a standalone Bun script (`ory/hydra/test-oauth-flow.ts`, run via `task oauth:hydra:test`) against the dev stack, so browser-level Hydra coverage does not exist yet. None of these specs has ever been run together against the fully-merged wave 1-6 codebase, and two areas of the identity/collaboration surface still have no dedicated coverage at all: plain room CRUD (create/rename/delete via Step 36's settings drawer — `web/src/features/messages/components/ChatRoom.tsx`'s `MoreVertical` button only got wired up in Step 36, after Step 37's spec was written, and no later step added a spec for it) and the end-to-end Hydra authorization-code flow through Step 55's demo first-party client (Step 55's own scope is the Hydra config and consent/login routes, not necessarily a full round-trip regression spec). This step is the first of the plan's four area-specific regression suites (`phases.md` Phases 3, 4, 9, 11, 13, and 15 collectively): it closes those two coverage gaps with new specs, re-runs the five existing specs above against the merged wave 1-6 stack as a single suite, and fixes only whatever failures that combined run surfaces — it is explicitly not a rewrite of any feature step's already-passing spec or component.

## Goal
After this PR, `web/e2e/` has two new specs — `rooms.spec.ts` (room create → rename → delete lifecycle, plus a role-gated check that only the room's `master` sees the delete control) and `oauth-hydra.spec.ts` (a full Hydra authorization-code round trip through the demo first-party client Step 55 provisioned: unauthenticated visit to Hydra's authorize endpoint → Kratos-backed login/consent UI → redirect back to the demo client's callback with an authorization code → code exchange for an access/ID token) — and the seed harness gains a small set of additional pre-registered fixture identities so the new specs (and any future regression work in this wave) do not need to drive a full UI registration flow for every supporting actor. All seven specs (`smoke.spec.ts`, `auth.spec.ts`, `oauth-dex.spec.ts`, `oauth-hydra.spec.ts`, `rooms.spec.ts`, `members.spec.ts`, `groups.spec.ts`) pass together in one `bunx playwright test` run against the Step 10 harness rebuilt from the current `main` (i.e., with every wave 1-6 step's code present). Any failure the combined run surfaces is root-caused and fixed in the minimal file(s) responsible — no unrelated refactors, no rewriting of a passing spec's assertions to make a broken feature look green.

### Hydra's authorization-code contract (implementation-invariant, safe to assume regardless of Step 55's exact wiring)
Ory Hydra's OAuth2 provider role always follows this shape once a login/consent UI is configured: an unauthenticated `GET {HYDRA_PUBLIC_URL}/oauth2/auth?client_id=...&response_type=code&redirect_uri=...&scope=...&state=...` redirects the browser to whatever URL Hydra's `urls.login` config points at, appending a `login_challenge` query parameter; after that page authenticates the user (here, by delegating to Kratos) and calls Hydra's admin API to accept the login challenge, Hydra redirects back to `/oauth2/auth` which then redirects to `urls.consent` with a `consent_challenge` parameter; after that page's consent is accepted via the admin API, Hydra performs the final redirect to the original `redirect_uri` with `?code=...&state=...`. This request/redirect shape is fixed by Hydra itself — only the login/consent page *paths* and the demo client's `client_id`/`redirect_uri`/secret are Step 55-specific and must be read from its actual diff.

### Seed extension shape (illustrative; keep the existing `seed.ts` structure)
```ts
// web/e2e/seed/seed.ts — additive to the existing idempotent routine
await ensureUser(HYDRA_DEMO_FIXTURE_USER); // same register-then-login-on-conflict helper already used for the primary fixture user
```
Do not introduce a second seeding mechanism (e.g. a raw SQL insert, or a separate script) — reuse the exact `fetch`-based `/auth/register` → fallback-to-`/auth/login` idempotency pattern Step 10 already established, against the same `E2E_API_URL`.

### Chakra/UI conventions
No new UI components are added by this step (it only adds specs and a seed/fixture extension); if a surfaced failure requires a small fix inside an existing component, follow `.claude/rules/chakra-ui.md` and the conventions the owning step already established for that file (compound `@chakra-ui/react` components, semantic tokens, no new UI library).
