# Step 22: Server: member management, leave, role change, ownership transfer

## Meta
- **Type**: feature
- **Components**: server
- **Wave**: 4 (parallel group — all steps of the same wave can run concurrently)
- **Depends on**: Step 13: Go 5-tier RBAC domain + authorization middleware + ModelUsecase
- **Unlocks**: Step 37: Web members, invitations, and roles UI
- **Size**: 1 PR (a few hours for one AI agent)

## Context
Step 13 lands the typed `domainroom.Role` enum, the `Action` capability matrix, and the reusable `RequireRole` middleware / `Authorize` helper in `server/internal/interface/middleware/rbac.go`, but no route in `server/internal/app/routes_room.go` uses them yet, and `room.RoomRepository` still has no way to change a membership's role or transfer room ownership. `phases.md` Phase 3 calls for a member list endpoint and an explicit "leave" endpoint (`room_members` uses `ON DELETE RESTRICT`, so leaving must be handled in application code, not via cascade), plus an ownership-transfer endpoint; Phase 4 calls for a role-change endpoint gated by the RBAC rules Step 13 just defined. This step wires all four together against `rooms.owner_id`, the single source of truth for who currently owns a room, so that Step 37's Web UI has a complete, testable member-lifecycle API to build against.

## Goal
`RoomHandler` gains four new endpoints — list members, leave, change a member's role, and transfer ownership — all registered from the existing `server/internal/app/routes_room.go` registrar. `RoomUsecase` gains the corresponding business logic: any member (including `reader`) can list members; a member can leave a room unless they are its current owner (`rooms.owner_id`), in which case they must transfer ownership first; only members with the `ActionManageMembers` capability (`admin`, `master`) can change another member's role, and that endpoint can never grant `master` (only the ownership-transfer endpoint can) nor change the current owner's own role; and only the current owner can transfer ownership, which atomically updates `rooms.owner_id`, promotes the new owner to `master`, and demotes the previous owner to `admin` so a room always has exactly one `master`. `room.RoomRepository` gains `UpdateMemberRole` and `TransferOwnership` methods (the latter running in a single transaction) to back this.

## Scope
- [x] Add `domainroom.ErrOwnerRoleProtected` (new sentinel error, `server/internal/domain/room/entity.go` or a new `server/internal/domain/room/errors.go`) documenting that it is returned both when the current owner tries to leave without transferring first, and when someone tries to change the current owner's role directly instead of via ownership transfer.
- [x] Extend `domainroom.RoomRepository` (`server/internal/domain/room/repository.go`) with two new methods, fully GoDoc'd:
  - `UpdateMemberRole(ctx context.Context, roomID, userID string, role Role) error` — updates a single membership's role; returns `domain.ErrNotFound` if the membership does not exist.
  - `TransferOwnership(ctx context.Context, roomID, oldOwnerID, newOwnerID string) error` — atomically updates `rooms.owner_id` to `newOwnerID`, sets the new owner's `room_members.role` to `master`, and sets the previous owner's `room_members.role` to `admin`, all in one transaction; returns `domain.ErrNotFound` if either membership row does not exist.
- [x] Implement both methods on `postgres.RoomRepository` (`server/internal/interface/repository/postgres/room_repository.go`), following the existing `Create` method's transaction pattern (`r.pool.Begin` / `defer tx.Rollback` / `tx.Commit`) for `TransferOwnership`, and the existing `Update`/`RemoveMember` `RowsAffected() == 0 → domain.ErrNotFound` pattern for `UpdateMemberRole`.
- [x] Add four methods to `RoomUsecase` (`server/internal/usecase/room/usecase.go`), reusing the shared membership-lookup helper Step 13 introduced (instead of re-deriving membership checks):
  - `ListMembers(ctx, callerID, roomID) ([]*domainroom.RoomMember, error)` — requires the caller to be a member (any role, including `reader`); no `Action` capability required. The returned members carry a display `Username`: add a `Username string` field to `domainroom.RoomMember` (`server/internal/domain/room/entity.go`, GoDoc'd as "populated only by member-listing queries; empty elsewhere") and have the repository's member-listing query `JOIN users u ON u.id = rm.user_id` to fill it — this is what lets Step 37's member panel show human-readable names instead of raw UUIDs, without a separate user-directory endpoint.
  - `LeaveRoom(ctx, callerID, roomID, targetUserID string) error` — returns `domain.ErrForbidden` if `targetUserID != callerID` (this endpoint only supports self-leave; kicking other members is out of scope, see below); returns `domain.ErrForbidden` if the caller is not a member; loads the room and returns `domainroom.ErrOwnerRoleProtected` if `callerID == room.OwnerID`; otherwise calls `roomRepo.RemoveMember`.
  - `ChangeMemberRole(ctx, callerID, roomID, targetUserID string, newRole domainroom.Role) (*domainroom.RoomMember, error)` — loads the caller's membership and calls the `Authorize`/`RequireRole`-equivalent check for `domainroom.ActionManageMembers` (defense in depth alongside the route-level middleware below); loads the room and returns `domainroom.ErrOwnerRoleProtected` if `targetUserID == room.OwnerID`; loads the target membership (`domain.ErrNotFound` if absent); calls `roomRepo.UpdateMemberRole`; returns the updated member. (Rejecting `newRole == RoleMaster` is validated at the handler layer — see below — so the usecase never needs to special-case it.)
  - `TransferOwnership(ctx, callerID, roomID, newOwnerID string) (*domainroom.Room, error)` — loads the room; returns `domain.ErrForbidden` if `callerID != room.OwnerID`; if `newOwnerID == room.OwnerID`, returns the room unchanged as a no-op (idempotent, no error); otherwise loads the target membership via `roomRepo.GetMember` (`domain.ErrNotFound` if the target is not already a room member — ownership can only transfer to an existing member); calls `roomRepo.TransferOwnership(ctx, roomID, room.OwnerID, newOwnerID)`; updates and returns the room with the new `OwnerID`.

## Out of scope
- Kicking/removing another member from a room against their will — `phases.md` Phase 3 only specifies self-leave; there is no "admin removes another member" endpoint in this step. `DELETE /rooms/:roomId/members/:userId` requires `userId == middleware.GetUserID(c)` and returns 403 otherwise.
- Invitations (invite-by-link, invite-by-username-search, accept/reject) — a separate feature built on `room_invitations`, not part of this step.
- Wiring `RequireRole`/RBAC checks into the message-send or AI-invoke endpoints — already done in Step 13.
- Group batch invitations (later phase/step).
- Any Web Frontend member-management UI — that is Step 37, which consumes the endpoints this step ships.
- Per-room AI provider/model settings and the separate settings handler file Step 24 introduces — this step does not touch that file.
- Any `schema.sql`/Atlas migration — no DB schema changes are needed; `rooms.owner_id` and `room_members.role` already exist and Step 13 already added the `CHECK` constraint on `role`.

## Implementation notes
- Follow Clean Architecture layering per `CLAUDE.md`: `domainroom.ErrOwnerRoleProtected` lives in `internal/domain/room` with zero external imports; only the handler layer translates it to an HTTP status code.
- Reuse the exact route-registrar pattern Step 1 established: `server/internal/app/routes_room.go` exports `registerRoomRoutes(e *echo.Echo, c *app.Container)` and is called from `router.go`; add the four new route lines to this existing file rather than creating a new registrar file, matching this step's `conflictNotes` (Step 24 is the one that introduces a *separate* settings-handler file to avoid collision with this step — this step's job is to extend `room_handler.go`/`routes_room.go` directly).
- `handleRoomError` in `room_handler.go` currently maps `domain.ErrNotFound → 404`, `domain.ErrForbidden → 403`, else `500`. Add one more `errors.Is(err, domainroom.ErrOwnerRoleProtected) → 409` branch at the top of that function (or a small local wrapper used only by `Leave`/`ChangeRole`) so the existing mapping order and messages for the other two errors are undisturbed.
- Reuse Step 13's shared membership+role-lookup helper (introduced to de-duplicate `RoomUsecase`/`MessageUsecase`'s former `checkMembership` methods) for the "is the caller a member" and "does the caller have `ActionManageMembers`" checks in `ListMembers`/`ChangeMemberRole`, rather than calling `roomRepo.GetMember` ad hoc a second time — if that helper's exact name/signature differs from what's assumed here, adapt to whatever Step 13 actually landed.
- `RequireRole(c.RoomRepo, domainroom.ActionManageMembers)` (from `server/internal/interface/middleware/rbac.go`, added in Step 13) is the correct capability to gate the role-change route at the HTTP layer — it already encodes "admin and master may manage members, others may not" per Step 13's matrix. Do not gate `ListMembers`/`Leave`/`TransferOwnership` with `RequireRole`: their authorization rules ("any member", "self only", "must be `rooms.owner_id`") are not single-`Action` checks, so they are enforced entirely inside the usecase methods described above.
- `TransferOwnership`'s "exactly one master" invariant (new owner → `master`, old owner → `admin`) is a deliberate design decision for this step: `RoomUsecase.DeleteRoom` (from Step 13) authorizes purely on `member.Role == master`, not on `rooms.owner_id`, so leaving a stale second `master` after a transfer would let a former owner still delete the room. Demoting the old owner to `admin` closes that gap without changing `DeleteRoom`'s logic.
- Path parameter naming: use `:userId` for the leave/role-change routes to match the existing `:roomId`/`:messageId` convention already used elsewhere in `routes_room.go`/`routes_message.go`.
- No `schema.sql` or migration changes — do not run `task migrate:generate` for this step.
