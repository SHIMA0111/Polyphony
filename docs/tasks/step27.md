# Step 27: Token estimation endpoint (gateway) + Go proxy

## Meta
- **Type**: feature
- **Components**: llm-gateway, server
- **Wave**: 4 (parallel group — all steps of the same wave can run concurrently)
- **Depends on**: Step 1: Go server foundation: DI/router split, structured logging, lint, config | Step 14: Rust gateway test harness: router oneshot + wiremock provider tests
- **Unlocks**: Step 38: Web AI context UI: exclude toggle, delete, token meter | Step 50: Server: context summarization with cached summaries
- **Size**: 1 PR (a few hours for one AI agent)

## Context
Phase 5 of `phases.md` ("AI Context Control") calls for the LLM Gateway to expose a token estimation endpoint so the web UI can show an estimated token count while composing messages, and so later server-side context building (Step 50's summarization trigger) has a token count to check against a limit. Today `llm-gateway` only exposes `/health`, `/models`, and `/completions` (`llm-gateway/src/adapters/inbound/rest/router.rs`), and the Go API's `ai.LLMGateway` interface (`server/internal/domain/ai/gateway.go`) only has `Complete` and `ListModels`. Per the project's swap-point convention (`CLAUDE.md`'s `LLMGateway` interface abstraction) and the plan's auth/data-plane rule that the browser only ever talks to the Go API, the browser must never call the gateway directly — so this step adds the estimation capability to the gateway first, then extends the Go-side interface, REST client, and a small proxy route so the web app (Step 38) can call `POST /tokens/estimate` on the Go API.

## Goal
After this PR, `POST /tokens/estimate` exists on the `llm-gateway` REST API and returns an approximate token count for a list of chat messages, computed via a documented character-based heuristic estimator (no external tokenizer dependency is introduced). The Go API server exposes its own authenticated `POST /tokens/estimate` route that forwards the request to the gateway through a new `EstimateTokens` method on the `ai.LLMGateway` interface (implemented by `LLMClient`), so the browser calls only the Go API. Both sides ship unit/integration tests following the existing test harness patterns (`llm-gateway/tests/router_test.rs` from Step 14; hand-written mocks in `server/internal/interface/handler/*_test.go` and `server/internal/usecase/message/usecase_test.go`).

## Implementation notes
- **Rust file map**: `llm-gateway/src/domain/model.rs` (new structs), `llm-gateway/src/domain/token_estimator.rs` (new file, heuristic + unit tests), `llm-gateway/src/domain/mod.rs` (module registration), `llm-gateway/src/domain/service.rs` (trait impl + tests), `llm-gateway/src/ports/inbound/completion.rs` (trait method), `llm-gateway/src/adapters/inbound/rest/request.rs` (`TokenEstimateRequestDto`), `llm-gateway/src/adapters/inbound/rest/response.rs` (`TokenEstimateResponseDto`), `llm-gateway/src/adapters/inbound/rest/handlers.rs` (handler fn), `llm-gateway/src/adapters/inbound/rest/router.rs` (route registration), `llm-gateway/tests/router_test.rs` (extend Step 14's harness).
- **Go file map**: `server/internal/domain/ai/entity.go`, `server/internal/domain/ai/gateway.go`, `server/internal/interface/gateway/llm_client.go` (+ new `llm_client_test.go`), `server/internal/interface/handler/dto.go`, `server/internal/interface/handler/token_handler.go` (+ new `token_handler_test.go`), `server/internal/app/container.go`, `server/internal/app/routes_token.go` (new), `server/internal/app/router.go` (one added call), plus mock updates in `server/internal/interface/handler/message_handler_test.go` and `server/internal/usecase/message/usecase_test.go`.
- **API shape** — gateway: `POST /tokens/estimate` request `{"model": "gpt-5.2", "messages": [{"role": "user", "content": "hello"}]}` → response `{"model": "gpt-5.2", "estimated_tokens": 6}`. Go proxy: same shape, same path, but requires a valid JWT (`Authorization: Bearer <token>`) like the other authenticated routes; the Go handler forwards the parsed request to the gateway unchanged (no transformation beyond DTO conversion).
- Follow the **exact** DTO/marshal/error-wrapping style already established by `Complete`/`ListModels` in `server/internal/interface/gateway/llm_client.go` — same `domain.ErrLLMGateway`-wrapped `fmt.Errorf` calls at each failure point (marshal, request construction, `httpClient.Do`, non-200 status, decode).
- Because `Container` and the `internal/app` route-registrar split are introduced by Step 1 (a dependency of this step), confirm the actual field name Step 1 gave the `ai.LLMGateway` instance inside `Container` (referred to here as `c.LLMGateway`, per Step 1's own scope description "LLMGateway client") and the actual authenticated-group mechanism `routes_room.go`/`routes_message.go` use before wiring `routes_token.go` — mirror whichever pattern is actually present rather than assuming.
- Do not add the new route to the small set of currently-public routes (`/health`, `GET /models`, `/auth/*`); register it through the same authenticated-group path as `/rooms/:roomId/messages*`.
- All new Rust code needs rustdoc (`///`) on public items; all new Go code needs GoDoc comments on exported symbols, per `CLAUDE.md`.
- All code, comments, and test names in English, per `CLAUDE.md`.
- **Conflict notes**: this is a small, additive step on both sides. On the Go side it adds one new handler file, one new registrar file, and one new field/line in `container.go`/`router.go` — the same append-only pattern Step 1 establishes for later steps, so it does not conflict with other wave-4 server feature files (which touch different handler/usecase files). On the Rust side it extends the shared `CompletionUseCase` trait and `AppState`, which is a narrow, single-purpose addition (one new method, one new route) unlikely to collide with the provider-adapter work of Steps 25/26 (different files: `adapters/outbound/*.rs`) or the streaming work of Step 43 (different files: `stream.rs` per the hexagonal module split), since none of those steps touch `ports/inbound/completion.rs`, `domain/service.rs`'s non-provider-dispatch code paths, or `router.rs`'s `/tokens/estimate` route.
