# Step 45: Web: image upload + attachment UI + Vision send

## Meta
- **Type**: ui
- **Components**: web
- **Wave**: 6 (parallel group — all steps of the same wave can run concurrently)
- **Depends on**: Step 10: Playwright E2E harness + seeded compose test stack + LLM stub | Step 29: Web send pipeline UX: optimistic send, AI thinking, retry, infinite scroll | Step 39: Vision multimodal plumbing: gateway content-parts mapping + Go DTOs
- **Unlocks**: Step 47: Web private AI mode UI | Step 58: E2E regression: summarization, streaming, private mode, images/Vision
- **Size**: 1 PR (a few hours for one AI agent)

## Context
Phase 12 of `phases.md` ("Image Upload + Vision") requires end users to attach images to a chat message and have the AI see them. Step 12 already landed MinIO storage plus three REST endpoints (presigned upload, attach-to-message, list-with-view-urls) and Step 39 already taught the LLM Gateway and the Go context-assembly path (the post-Step-23 `ai.ContextBuilder` plus Step 39's attachment-part enrichment) to turn a message's linked `message_attachments` rows into Vision content parts — but nothing in `web/` calls any of it yet: `web/src/features/messages/components/MessageInput.tsx` is a text-only textarea, `web/src/features/messages/components/MessageBubble.tsx` (landed by Step 18's `ChatRoom`/`MessageList` decomposition) has no notion of attachments, and `web/src/lib/api.ts` has no attachment methods at all. This step closes that last gap: the actual upload/preview/thumbnail UI, wired to Step 12's endpoints, and a documented send sequence that gets attachment data in front of the AI within Step 39's already-frozen server contract.

## Goal
After this PR, a user in a chat room can attach one or more images to a message via a file-picker button, drag-and-drop onto the input, or pasting from the clipboard; sees a preview chip with an upload progress bar for each attached image before sending; and, after sending, sees the message render with its image thumbnail(s) in the transcript, clickable to a full-size lightbox. When the message is sent through the "Send with AI" path, the AI's reply is generated with the image(s) visible as Vision content parts (via a documented two-call send-then-regenerate sequence that respects the exact preconditions of the existing `SendAIMessage`/`RegenerateAIMessage` usecases), so the user sees the AI's answer update once it has actually seen the attached image(s). A Playwright spec (reusing Step 10's harness) attaches a fixture image, sends it, and asserts both the thumbnail renders in the transcript and an AI reply appears (from the Step 10 LLM stub).

  - Plain send with attachments: call `sendMessage(roomId, content)` → for each resolved `attachmentId`, call `attachToMessage(roomId, humanMessage.id, attachmentId)` (sequentially or `Promise.all`, order does not matter) → update the local/query-cache message with attachment info so it renders immediately without waiting on a fresh `listAttachments` fetch (see `useMessageAttachments` note below).
  - AI send with attachments: call `sendAIMessage(roomId, content, model)` first (creating the human+AI pair as usual — the AI's first-pass reply does **not** see the image yet, since attachments cannot be linked to a message that does not exist yet) → attach each `attachmentId` to the returned `user_message.id` → call `regenerateAIMessage(roomId, user_message.id, model)`, which now succeeds because an AI message already exists immediately after the human message (satisfying `RegenerateAIMessage`'s precondition in `server/internal/usecase/message/usecase.go`) and re-runs the context assembly (Step 23's builder plus Step 39's attachment enrichment), which now finds the just-linked attachment and builds Vision content parts for it. Reuse the existing AI "thinking"/regenerating indicator from Step 29 for this second call so the UI reads as "AI is looking at your image" rather than a silent flicker.
  - Document this two-call sequence with a code comment at the call site explaining *why* (the regenerate-precondition reasoning above) so a future refactor doesn't collapse it into a single call without re-checking the server contract.

## Implementation notes
- **Current pre-step state observed in this checkout** (Phase 1 only, before Steps 4/5/9/10/12/18/29/39 land): `web/src/lib/api.ts` has no attachment methods and is a `localStorage`-JWT singleton client; `web/src/features/messages/components/MessageInput.tsx` is a plain textarea with `onSend(content)`/`onSendWithAI(content, model)` props and no file handling; `web/src/features/messages/components/MessageList.tsx` renders messages inline with no `MessageBubble` split. By the time this step is implemented, Step 4 will have moved auth to httpOnly cookies behind an `app/api/proxy/[...path]` BFF route, Step 9 will have introduced per-feature TanStack Query modules under `web/src/features/messages/api/`, Step 18 will have split `MessageList` into `MessageBubble`/`MessageGroup`/`DaySeparator` components plus a `useChatRoom` orchestration hook, and Step 29 will have added optimistic send/AI-thinking/retry state to that same hook. Locate the actual post-Step-29 file names/exports before wiring this step's changes — do not reintroduce a manual `fetchData`/`useState` pattern if it has already been replaced.
- **Server contract this step consumes, verbatim from Step 12** (`server/internal/interface/handler/attachment_handler.go`, routes registered via Step 12's `server/internal/app/routes_attachment.go` registrar):
  - `POST /rooms/:roomId/attachments/upload-url` — body `{"mime_type": "...", "size_bytes": ...}` → `201 {"attachment_id": "...", "s3_key": "...", "upload_url": "https://...", "expires_at": "..."}`.
  - `POST /rooms/:roomId/messages/:messageId/attachments` — body `{"attachment_id": "..."}` → `200 {"id": "...", "message_id": "...", "s3_key": "...", "mime_type": "...", "size_bytes": ..., "created_at": "..."}`.
  - `GET /rooms/:roomId/messages/:messageId/attachments` → `200 {"attachments": [{"id": "...", "message_id": "...", "s3_key": "...", "mime_type": "...", "size_bytes": ..., "view_url": "https://...", "created_at": "..."}]}`.
  - All three routes sit behind the same authenticated/room-membership middleware as the existing message routes — call them the same way `web/src/lib/api.ts` (or its post-Step-9 per-feature replacement) already calls `sendMessage`/`listMessages`, through the BFF proxy path (`/api/proxy/rooms/...`), not a direct `NEXT_PUBLIC_API_URL` call.
- **Why the two-call AI-send sequence is required, not optional**: `server/internal/usecase/message/usecase.go`'s `RegenerateAIMessage` explicitly requires `msgRepo.GetNextInRoom(ctx, roomID, targetMsg.Sequence)` to already return an AI-typed message (`if nextMsg.Type != domainmessage.MessageTypeAI { return nil, domain.ErrNotFound }`), and `SendAIMessage` builds its `CompletionRequest` from context fetched immediately after creating the human message row in the same call — so there is no single existing endpoint that both creates a message and includes attachments linked to that same message in the same outbound completion request. The documented flow (`sendAIMessage` → `attachToMessage` → `regenerateAIMessage`) is the only sequence that satisfies both preconditions using only the frozen Step 12/39 server contract. Read `server/internal/usecase/message/usecase.go` (`SendAIMessage`, `RegenerateAIMessage`, and the post-Step-23/39 context-assembly path) before implementing to confirm this reasoning still holds against whatever the checkout's actual state is by the time this step runs; if a later step has since added `attachment_ids` support directly to `SendAIMessage`'s request DTO, prefer that simpler single-call path instead and drop the regenerate step (this would only shorten the implementation, not require additional API surface).
- **MinIO / E2E reachability**: Step 12 adds `minio`/`minio-init` to `docker-compose.yml` with no `profiles` key (i.e., the default/untagged group), and Docker Compose always starts untagged services regardless of which `--profile` flag is passed — so `task test:e2e:up` (Step 10's `docker compose --profile test up -d --build`) already brings up the same `minio` instance the dev stack uses. Confirm `api-e2e` (added by Step 10) has `S3_ENDPOINT`/`S3_BUCKET`/`S3_ACCESS_KEY`/`S3_SECRET_KEY` env vars set (reusing the same values as the dev `api` service, since they share the one `minio` instance) before writing `attachments.spec.ts` — if they are missing, add them as a small additive env-var block to the existing `api-e2e` service definition in `docker-compose.yml` (do not add a new service; do not touch any other service block).
- **Chakra v3 conventions** (`.claude/rules/chakra-ui.md`): use `@chakra-ui/react`'s `Dialog.*` compound API for the lightbox (no custom modal), `IconButton` for the attach trigger, `Progress.Root`/`Progress.Track`/`Progress.Range` (or `Progress.Circle` if a ring is preferred) for per-chip upload progress, and the existing `@/components/ui/tooltip` snippet for any icon-only button labels. Do not add shadcn/Radix primitives. Style with Chakra style props (`bg`, `rounded`, `shadow`), consistent with the existing floating-card input styling in `MessageInput.tsx`.
- **File/type conventions**: name the new types `AttachmentResponse`, `AttachmentWithUrl` (matching Step 12's JSON field names in camelCase-free/snake_case-preserved form, i.e. keep `message_id`/`mime_type`/`size_bytes`/`view_url`/`created_at` as-is to match every other type in `web/src/features/messages/types.ts`, which mirrors the Go JSON tags verbatim). English-only identifiers/comments per `CLAUDE.md`.
- **Conflict note**: this step owns `MessageInput.tsx` and the `MessageList`/`MessageBubble` transcript-rendering files for wave 6 (per the plan's rotating ownership: 18 → 29 → 38 → 45 → 47/54); Step 47 (private AI mode UI) is serialized after this step specifically because it also touches these files — do not attempt to coordinate with Step 47, just land this step's changes cleanly and let Step 47 rebase on top.
