# Step 7: Go event-driven messaging core: MessageHub, atomic sequences, response linkage

## Meta
- **Type**: refactor
- **Components**: server
- **Wave**: 2 (parallel group — all steps of the same wave can run concurrently)
- **Depends on**: Step 1: Go server foundation: DI/router split, structured logging, lint, config; Step 2: Go test infrastructure: testcontainers helper + shared mocks
- **Unlocks**: Step 12: Server: MinIO object storage + attachments + presigned upload endpoints; Step 13: Go 5-tier RBAC domain + authorization middleware + ModelUsecase; Step 15: Server WebSocket endpoint + realtime delivery; Step 32: Server: room fork (async batch copy); Step 42: Server: token balance management
- **Size**: 1 PR (a few hours for one AI agent)

## Context
The current message pipeline (`server/internal/usecase/message/usecase.go`) is a synchronous request/response flow with no way to notify anyone other than the HTTP caller that a message was created or updated — there is no seam for WebSocket delivery (Phase 2), and none of the later realtime/Redis/room-fork work can be bolted on without one. Sequence allocation is also unsafe for the exact case the code already tries to guard against: `SendAIMessage` calls `MessageRepository.GetNextSequence` twice (once via the internal `SendMessage` call for the human message, once for the AI message), and a concurrent request can call `GetNextSequence` for an unrelated message in the gap between those two calls, breaking the human+AI adjacency that `RegenerateAIMessage`'s `GetNextInRoom` lookup depends on. Finally, an AI message has no durable link back to the human message that triggered it beyond "the next message by sequence," which is fragile and blocks future context-building/summarization work (Phase 5, 18) that needs to reason about prompt/response pairs explicitly. This step fixes all three problems in the domain/usecase/repository layers before any other wave-2+ server step touches messaging.

## Goal
After this PR, message creation and update flows in the Go API are event-driven and race-free: a new `domain/event` package defines a `MessageHub` port (with per-user-targeted publish/subscribe) and an `InProcessHub` implementation that later steps can swap for a Redis-backed hub without changing usecase code; `MessageUsecase` publishes `message_created`/`message_updated` events after each successful persist, and a publish failure never causes a write to be rolled back or the HTTP request to fail; sequence numbers for a human message and its AI response are reserved atomically as a single contiguous range so no other message can land between them; every AI message stores `in_response_to_message_id` pointing at the human message it answers; and `messages` enforces `UNIQUE(room_id, sequence)` in the schema as a hard invariant, verified under real concurrency with a testcontainers-backed PostgreSQL test.

## Implementation notes
- **conflictNotes**: this is the only wave-2 step editing the `messages` table in `schema.sql`. Step 12 (MinIO attachments) is serialized after this step specifically to avoid a same-wave collision on that table — do not coordinate with it, just land this step's schema edit cleanly.
- Reuse existing conventions rather than inventing new ones:
  - `domain/errors.go` (`server/internal/domain/errors.go`) already defines `ErrNotFound`; `ReserveSequenceRange` should return it the same way `GetNextSequence` does today (`errors.Is(err, pgx.ErrNoRows)` → `domain.ErrNotFound`).
  - Follow the existing `scanMessage`/`messageColumns` pattern in `server/internal/interface/repository/postgres/message_repository.go` — add the new column to the shared constant and scan function rather than duplicating SQL.
  - Follow the existing DTO nullable-pointer convention already used for `SenderID *string` in `dto.go` for `InResponseToMessageID *string`.
  - `MessageUsecase`'s existing `checkMembership` helper, `buildChatMessages`, and the failed-placeholder-on-LLM-error behavior in `SendAIMessage` must be preserved exactly — only the sequence-reservation and publish calls change.
- Package placement: put both `MessageHub` (port) and `InProcessHub` (the initial adapter) in `domain/event` together, per the swap-point table's own phrasing ("`MessageHub` | InProcessHub | Phase 10 (Redis)"). This is a deliberate, minimal exception to strict Clean Architecture layering — `InProcessHub` has zero external dependencies (stdlib `sync`/channels only), so keeping it beside the interface it implements keeps the domain package self-sufficient and gives every usecase test a real, dependency-free hub to construct instead of needing a mock.
- `RoomEvent.Message` should hold the full `*message.Message` (not a re-serialized DTO) — `domain/event` importing `domain/message` is a domain→domain dependency and does not violate the dependency rule (only usecase/interface/infrastructure importing into domain would).
- Non-blocking `Publish` is the mechanism that guarantees "broadcast never rolls back writes": because `Publish` has no error return and never blocks on a full subscriber channel, there is no way for event delivery to affect the transaction/response that already completed. Do not add error handling in `MessageUsecase` around `hub.Publish` calls beyond calling it after the corresponding `Create`/`UpdateAIResponse` succeeds.
- Sequence-range fix: today `SendAIMessage` calls `u.SendMessage(...)` (which itself calls `GetNextSequence`) and then calls `GetNextSequence` again for the AI message — this is the race the docstring above `SendAIMessage` already warns about, but the current code does not actually close the gap. Reserving both sequence numbers as one range via `ReserveSequenceRange(ctx, roomID, 2)` *before* creating either row removes the window entirely. Factor a small private helper (e.g. `newHumanMessage(userID, roomID, content string, seq int64) *message.Message` plus the `Create`+`Publish` sequence) so `SendMessage` (reserving 1) and `SendAIMessage` (reserving 2, using the first slot) share the exact same persist/publish logic instead of diverging.
- DB migration: `schema.sql` is Atlas-declarative (see `server/atlas.hcl`); do not hand-write a migration file — edit `schema.sql` and run `task migrate:generate` from the repo root (see `Taskfile.yml`'s `migrate:generate` task, which runs `atlas migrate diff <name> --env local` inside `server/`), then commit the generated file(s) under `server/migrations/` plus the updated `atlas.sum`.
- DI wiring: `server/cmd/api/main.go` currently constructs `msgUC := msgusecase.NewMessageUsecase(msgRepo, roomRepo, llmClient)` directly; Step 1 is expected to have relocated this construction into a DI container, but wherever it lives, add `hub := event.NewInProcessHub()` (or equivalent constructor name you choose) and pass it as the fourth argument.
- All new/changed exported Go symbols need GoDoc comments describing what/why/constraints/error behavior, per `CLAUDE.md`.
