# Step 38: Web AI context UI: exclude toggle, delete, token meter

## Meta
- **Type**: ui
- **Components**: web
- **Wave**: 5 (parallel group — all steps of the same wave can run concurrently)
- **Depends on**: Step 10: Playwright E2E harness + seeded compose test stack + LLM stub | Step 23: Server: AI context control (soft delete, exclude flag, cutoff, context builder) | Step 27: Token estimation endpoint (gateway) + Go proxy | Step 29: Web send pipeline UX: optimistic send, AI thinking, retry, infinite scroll
- **Unlocks**: Step 57: E2E regression: realtime AI core — send, model select, context controls, rate limiting
- **Size**: 1 PR (a few hours for one AI agent)

## Context
Phase 5 of `phases.md` ("AI Context Control") requires that users be able to shape what the AI sees and gauge how large that context is before sending. Step 23 already gave the server everything needed for this — `messages.is_deleted`, `messages.exclude_from_ai`, `DELETE /rooms/:roomId/messages/:messageId`, and `PATCH /rooms/:roomId/messages/:messageId` — and Step 27 added `POST /tokens/estimate` (proxied through the Go API). None of it has a web surface yet: today `web/src/features/messages/components/MessageList.tsx` renders each message with only a "Regenerate" button (no menu, no exclude/delete affordance) and `web/src/features/messages/components/MessageInput.tsx` has no token feedback at all. This step is the first place a user can actually exclude a message from AI context, delete a message, or see an estimated token count while composing — closing the last web-facing gap in Phase 5 before Step 36 (same overall feature area, later wave) adds the room-level cutoff control to the settings drawer.

## Goal
After this PR, every message rendered by `MessageList.tsx` has a per-message action menu offering "Exclude from AI" / "Include in AI" (toggling `exclude_from_ai` via Step 23's `PATCH` endpoint) and "Delete message" (soft-deleting via Step 23's `DELETE` endpoint, behind a confirmation dialog); excluded messages carry a clear, persistent visual indicator so a user can tell at a glance which messages the AI will never see. `MessageInput.tsx` shows a live, debounced estimated token count — computed by sending the currently-visible, non-excluded, non-deleted messages plus the in-progress draft to Step 27's `POST /tokens/estimate` proxy — so a user can gauge context size before sending. A Playwright spec exercises the full loop (send messages, exclude one, delete another, observe the meter and message list reflect both actions) against Step 10's harness.

## Out of scope
- The room-level AI context cutoff control — that is Step 36's territory (its settings drawer), deliberately not duplicated here; this step ships only per-message controls plus the token meter.
- Members list, invitations, and per-member role management UI (Step 37).
- Editing message content, hard/permanent deletion, or any purge job for soft-deleted rows (server-side out of scope already per Step 23; nothing to surface here either).
- Displaying the estimated token count as a percentage of the selected model's context window or any pricing display — that needs Step 34's model metadata (token limits/pricing on `ModelInfo`), which this step does not depend on; the meter here is a plain absolute count.
- WebSocket-driven propagation of another user's exclude/delete action into this client's view — that is Step 35's cache-merge territory (same wave, different files); this step's own optimistic update only covers the acting user's own request/response round trip.
- Streaming token-by-token AI response rendering (Step 54).
- Any server or gateway code changes — Steps 23 and 27 already shipped the endpoints this step consumes; if either is missing or shaped differently than expected at implementation time, adapt the client call to match the actual merged server code, but do not add new server routes, DB columns, or gateway logic from this step.
- `docker-compose.yml`, `Taskfile.yml`, or `llm-stub/` changes — this step reuses Step 10's harness and services unmodified.

  - `POST /tokens/estimate` body `{"model": "...", "messages": [{"role": "user"|"assistant", "content": "..."}]}` → `200` with `{"model": "...", "estimated_tokens": <number>}`; this route requires `Authorization: Bearer <token>` (it is not one of the public routes like `GET /models`).

- **Debounce**: a plain `useEffect` + `setTimeout`/`clearTimeout` is sufficient (matches the codebase's existing plain-hooks style, e.g. the auto-resize effect already in `MessageInput.tsx`); do not add `lodash`/`use-debounce` or any new dependency for this.
- **Meter payload filtering**: filter the in-view `Message[]` to `!m.is_deleted && !m.exclude_from_ai` before mapping to the estimate request, even though the server already omits `is_deleted` rows from `GET /rooms/:roomId/messages` — this defends against any not-yet-reconciled optimistic/WS entry that might transiently carry `is_deleted: true` in the local cache.
