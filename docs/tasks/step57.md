# Step 57: E2E regression: realtime AI core — send, model select, context controls, rate limiting

## Meta
- **Type**: testing
- **Components**: web, infra
- **Wave**: 7 (parallel group — all steps of the same wave can run concurrently)
- **Depends on**: Step 10: Playwright E2E harness + seeded compose test stack + LLM stub | Step 31: Redis in compose + RedisHub MessageHub swap | Step 33: Server: Redis rate limiting + Kratos session cache | Step 34: Model metadata (token limits + pricing) across gateway/server/web | Step 35: Web WebSocket client + live cache merge | Step 36: Web room settings drawer | Step 38: Web AI context UI: exclude toggle, delete, token meter
- **Unlocks**: Step 60: Final E2E gate + docs/progress sync
- **Size**: 1 PR (a few hours for one AI agent)

## Context
By wave 6, six independent features have each shipped behind their own narrow feature-level spec (or none, in the case of steps 31/33 which are server-only and only smoke-tested manually per their own verification sections): the Redis-backed `MessageHub` (step 31), Redis rate limiting (step 33), enriched model metadata (step 34), the live WebSocket cache merge (step 35), the room settings drawer's cutoff control (step 36), and the per-message exclude/delete/token-meter UI (step 38). None of these has been exercised together, end to end, against the real Redis-backed stack the way a production deployment actually runs. `phases.md`'s Phase 10 (Redis) and Phase 5 (AI context control) are only "done" in the sense that their unit/component tests pass in isolation — this step is the first place the realtime + AI-core surface is regression-tested as a whole, against the actual compose stack (not mocks), using the step-10 LLM stub for deterministic AI responses. It is one of four disjoint regression suites (56/57/58/59) that split the full-stack E2E surface so each stays reviewable in one PR; this one owns realtime delivery, AI send + model selection, context controls' effect on AI, and rate limiting.

## Goal
After this PR, `web/e2e/regression/` gains four new, disjoint Playwright spec files exercising: (1) AI send with an explicit model selection over the Redis-backed stack, hitting the step-10 LLM stub and asserting the returned content and the model actually used; (2) two-client realtime delivery — a message sent from one WebSocket-holding browser context appears in a second, independent browser context without a page reload; (3) that the context controls shipped in steps 36/38 (per-message exclude/delete, room-level AI cutoff) measurably change what the AI receives, verified by asserting the AI's canned stub response reflects only the messages that should still be in context; (4) that the E2E compose profile's relaxed rate limits (step 33) do not spuriously trip any of these suites, plus one explicit spec that deliberately tightens the AI-invoke rate limit for a single, isolated run and asserts an HTTP 429 with a `Retry-After` header is returned and surfaced sanely by the UI. Any bug these four specs surface in steps 31/33/34/35/36/38's shipped code is fixed in this same PR, scoped strictly to what a failing assertion here actually caught — no unrelated refactors.

## Scope
- [ ] Add `web/e2e/regression/ai-send-model-select.spec.ts`: using Step 10's fixture user/room (`web/e2e/support/fixtures.ts`), open the room, open the model selector (`web/src/features/messages/components/ModelSelector.tsx`), assert models are grouped by provider (Step 34) and an OpenAI-provider model is present, explicitly select a specific OpenAI model (the only provider wired to the step-10 stub via `llm-gateway-e2e`'s `OPENAI_BASE_URL`), send a message via "Send with AI" containing the `[[fixture:model-select]]` marker, and assert the rendered AI response matches the new fixture's canned text and that no other provider's model was silently substituted.
- [ ] Add `llm-stub/fixtures/model-select.json`: a new canned non-streaming completion fixture (distinct text from `default.json`) for the spec above to assert against — a new fixture file only, per Step 10's convention that later steps extend the stub via fixtures, never by touching `llm-stub/server.ts` or adding a second provider stub.
- [ ] Add `web/e2e/regression/two-client-realtime.spec.ts`: using two independent Playwright `BrowserContext`s both authenticated as the fixture user (mirroring Step 35's own manual verification of "two different users (or two browser profiles) in the same room"), open the same fixture room in both, assert both `ConnectionStatus.tsx` indicators reach `"connected"`, send a plain (non-AI) message from context A, and assert it renders in context B within a short timeout with no reload/refetch — proving the Redis Pub/Sub `RedisHub` (step 31) plus the web `useRoomSocket`/cache-merge (step 35) actually deliver across two independent WebSocket connections against the real compose stack, not just step 35's own narrower unit tests.
- [ ] Extend the same spec (or a clearly separated `test.describe` block in the same file) with a dedup assertion: the message sent from context A must render exactly once in context A's own view (no duplicate from the optimistic entry plus the WS echo), matching step 35's dedupe contract.
- [ ] Add `web/e2e/regression/context-controls-ai-effect.spec.ts`: send two or three plain messages in a fresh room, then (a) exclude one message from AI via its per-message menu (Step 38's `MessageList.tsx`/`MessageItem` exclude toggle) and assert its persistent visual indicator (muted styling + tooltip) appears; (b) delete another message via its menu + confirmation dialog (Step 38) and assert it disappears from the rendered list; (c) open the room settings drawer (Step 36's `RoomSettingsDrawer.tsx`) as the fixture user (who must be admin/master of a room they created) and set the AI context cutoff to "now"; (d) send a further plain message after the cutoff, then send an AI message with a distinct `[[fixture:context-check]]` marker and assert the AI response is the fixture's canned text (proving the request reached the gateway successfully with the excluded/deleted/pre-cutoff messages filtered out server-side) — this spec does not need to inspect the exact prompt sent to the gateway (the stub is content-blind besides the marker), so the assertion is: exclude/delete/cutoff actions all succeed, are reflected in the UI, and a subsequent AI send still completes correctly against the same stub, which is the externally observable proof that the context-control code paths did not break the AI-send pipeline they sit in front of.
- [ ] Add `llm-stub/fixtures/context-check.json`: a second new canned fixture (new file only) for the assertion above.
- [ ] Add `web/e2e/regression/rate-limiting.spec.ts` with two cases:
  - [ ] Case 1 ("relaxed limits don't trip the suite"): run a short burst of ordinary actions this step's own specs already perform at normal volume (e.g. login + a handful of plain/AI sends in a loop, well under the E2E profile's default `RATE_LIMIT_AI_INVOKE_PER_MINUTE_E2E`/`RATE_LIMIT_LOGIN_PER_MINUTE_E2E` defaults of `1000`/min per Step 33) and assert none of them receives an HTTP 429 — a regression guard proving the E2E profile's relaxed defaults are actually in effect for this suite's own traffic pattern.
  - [ ] Case 2 (explicit 429): temporarily point the AI-invoke rate limit at a tight value for an isolated run by recreating just the `api-e2e` container with `RATE_LIMIT_AI_INVOKE_PER_MINUTE_E2E` overridden to a small number (e.g. `3`) via `docker compose --profile test up -d --no-deps api-e2e` with that env var set low, then drive `POST /rooms/:roomId/messages/ai` past the limit (either through repeated "Send with AI" UI actions or Playwright's `request` fixture calling the BFF proxy route directly) and assert the response beyond the limit is HTTP 429 with a numeric `Retry-After` header; restore the default (`RATE_LIMIT_AI_INVOKE_PER_MINUTE_E2E` unset / recreate `api-e2e` again) at the end of the test (in an `afterAll`) so the rest of the E2E suite is unaffected by the tightened limit.
- [ ] Add a Taskfile task `test:e2e:regression:realtime-ai` (or extend an existing `test:e2e:regression*` grouping task if steps 56/58/59 have already landed one by the time this step is implemented — check `Taskfile.yml` first) that runs exactly these four new spec files: `bunx playwright test e2e/regression/ai-send-model-select.spec.ts e2e/regression/two-client-realtime.spec.ts e2e/regression/context-controls-ai-effect.spec.ts e2e/regression/rate-limiting.spec.ts`.
- [ ] Run the full existing E2E suite (`task test:e2e`) alongside these four new specs and fix any failure they surface in the steps 31/33/34/35/36/38 code they exercise — scope every fix narrowly to the specific assertion that failed (e.g. a wrong query key in the cache-merge dedupe logic, a missing `Retry-After` header, an off-by-one in the rate limiter's fail-open path); do not use this step to refactor or "improve" code that the new specs did not actually catch failing.
- [ ] Document any fix applied in the PR description, one line per fix, naming the exact defect and which spec caught it.

## Out of scope
- Any spec covering identity/collaboration (registration, login, invitations, member roles, ownership transfer) — that is Step 56's regression suite, disjoint spec files.
- Any spec covering context summarization triggers, long-history seeding, streaming AI responses, private AI mode, or image/Vision upload — that is Step 58's regression suite.
- Any spec covering token balances, billing/Stripe, or room fork — that is Step 59's regression suite.
- Adding new product features or UI to steps 31/33/34/35/36/38 beyond what those steps already shipped — this step only tests and, where a test fails, fixes the already-shipped behavior.
- Any change to `llm-stub/server.ts`, the compose test-profile service definitions, or `Taskfile.yml`'s existing `test:e2e*` tasks beyond the one new additive regression-runner task — this step is a consumer of Step 10's harness, not a second owner of it.
- Real provider API keys or live OpenAI/Anthropic/Gemini calls — every AI-send assertion in this step goes through the step-10 stub via `llm-gateway-e2e`'s `OPENAI_BASE_URL`; Anthropic/Gemini models are only exercised as selectable list entries (Step 34's grouping), never actually invoked, since the E2E profile has no real keys for them.
- Multi-instance (`--scale api=2`) verification — that is Step 31's own `verify:redis-hub` script territory; this step exercises the single-instance E2E compose profile (`api-e2e`), which already runs against the same `RedisHub` code path, just not scaled to multiple replicas.
- A dedicated Kratos/session-cache regression spec — Step 33's whoami-cache/logout behavior is exercised functionally through this step's ordinary authenticated actions (every spec logs in and makes authenticated calls), but a targeted cache-hit/expiry/logout-revocation spec is Step 56's identity-focused territory, not this step's.

## Implementation notes
- **Directory layout**: create `web/e2e/regression/` if it does not already exist (steps 56/58/59 may create it in parallel — if it already exists when this step lands, add files into it, do not restructure it). Keep this step's four spec files and its two new stub fixture files as the only new files this step owns; do not touch spec files with names implying another regression suite's territory (identity/collaboration, summarization/streaming/private/vision, billing/fork).
- **Reuse, do not reinvent, Step 10's harness**: import the fixture user/room constants from `web/e2e/support/fixtures.ts`, rely on `web/e2e/seed/seed.ts`'s `globalSetup` (already wired into `web/playwright.config.ts`) for a logged-in-capable fixture user and room, and run everything against the existing `task test:e2e:up`/`task test:e2e:down` compose test profile (`db-e2e`, `migrate-e2e`, `api-e2e`, `llm-stub`, `llm-gateway-e2e`, `web-e2e`) plus whatever Redis/rate-limit test-profile additions Steps 31/33 made to that same profile (a `redis-e2e`-style service and the `RATE_LIMIT_*_E2E`/`WHOAMI_CACHE_TTL_E2E` env vars on `api-e2e`, per Step 33's scope). Do not add a new compose profile or a new LLM stub.
- **Model selection spec — provider constraint**: only OpenAI models actually resolve to a real completion in the E2E profile, since `api-e2e`/`llm-gateway-e2e` only sets a dummy `OPENAI_API_KEY` pointed at the stub (per Step 10); Anthropic/Gemini entries added to the model list by Step 34 have no configured key in the E2E profile and would fail if actually invoked. The spec must select an OpenAI-provider model from the grouped selector before sending — do not attempt to exercise Anthropic/Gemini completions here (that would require real or additionally-stubbed provider keys, out of scope).
- **Fixture files**: follow the exact shape `default.json` already uses (`llm-stub/fixtures/default.json`) — the stub fills in `id`/`model` per Step 10's contract, so `model-select.json`/`context-check.json` only need `choices[0].message.content` (distinct canned text per fixture) and a plausible `usage` block. Trigger them by prefixing the outgoing user message content with `[[fixture:model-select]]` / `[[fixture:context-check]]` respectively, per the stub's documented marker convention (`llm-stub/server.ts`, Step 10).
- **Two-client spec — session mechanics**: use `browser.newContext()` twice (or `test.describe.configure({ mode: "parallel" })` with two `page` fixtures) within one spec file, each performing its own login against the fixture user's credentials (`web/e2e/support/fixtures.ts`), then both navigating to the same fixture room URL. Assert the `ConnectionStatus` indicator (`web/src/features/messages/components/ConnectionStatus.tsx`, Step 35) is visible and shows a connected state in both contexts before sending — a WS message sent before the socket is open cannot be delivered live, so this ordering matters for spec reliability, not just readability.
- **Context-controls spec — role requirement**: the fixture user must be the creator (hence `master`) of whatever room this spec operates in for the settings-drawer cutoff control (Step 36 gates the cutoff control to `admin`/`master`) — reuse the fixture room from `web/e2e/support/fixtures.ts` if the fixture user is guaranteed to be its master (per Step 10's seed logic, the seed creates the room as the fixture user, so this should already hold), or create a fresh room within the spec if isolation from other specs' side effects on the shared fixture room is preferable — prefer a fresh room per spec to avoid inter-spec ordering dependencies on the shared fixture room's message history.
- **Rate-limit spec — container recreate mechanics**: use Playwright's `test.beforeAll`/`test.afterAll` (not per-`test`) to bracket the container recreate around Case 2 only, e.g. via `execa`/Node's `child_process.execSync` (whatever process-invocation utility, if any, Step 10's `seed.ts` already uses — mirror it rather than adding a new dependency) running `docker compose --profile test up -d --no-deps api-e2e` with `RATE_LIMIT_AI_INVOKE_PER_MINUTE_E2E=3` in the child process's env, then in `afterAll` re-running the same command with that env var unset (falling back to the compose file's own `:-1000` default) so subsequent spec files (this suite's own Case 1, and any other regression suite sharing the same running stack) are not left rate-limited. Because Playwright can run spec files in parallel workers by default, mark this one spec file with `test.describe.configure({ mode: "serial" })` and, if the project's `playwright.config.ts` runs multiple workers, consider tagging this file to run in its own worker/last (e.g. via a project-level `dependencies`/`testMatch` ordering, or simply accept and document that this spec's container recreate is a brief, self-contained blip that only affects AI-invoke calls made during its own `beforeAll`/`afterAll` window) — the goal is that no other concurrently-running spec's AI-invoke calls land during the tightened window and get an unexpected 429.
- **`Retry-After` assertion**: match Step 33's documented contract exactly — HTTP 429, a `Retry-After` response header containing a positive integer (seconds), and (if the web app surfaces rate-limit errors distinctly rather than a generic failure — check `MessageInput.tsx`'s/`ChatRoom.tsx`'s current error handling for AI-send failures, extended by whichever step wired 429-specific UI feedback, if any) assert whatever UI feedback actually exists rather than assuming a specific toast/message was added; if no distinct 429 UI feedback exists at implementation time, assert only on the underlying HTTP response (via Playwright's `page.waitForResponse`/`request` fixture) — do not add new UI for 429 handling from this step (that would be a feature addition, out of scope for a testing step).
- **Fix-scoping discipline**: per the plan-wide regression-suite mandate, only fix what these four specs themselves catch failing — if `task test:e2e` (the full existing suite) surfaces a pre-existing, unrelated failure in a spec owned by a different step/suite, do not fix it here; note it in the PR description as an out-of-scope observation instead.
- **Conventions**: all new spec/fixture files and PR descriptions in English per `CLAUDE.md`. No `schema.sql`/Atlas migration in this step (`dbChanges` is empty). No Chakra UI component changes are expected from this step (testing-only), but any bug fix in `web/src/features/messages/components/*`/`web/src/features/rooms/components/RoomSettingsDrawer.tsx` that this step's specs surface must still follow `.claude/rules/chakra-ui.md` (Style Props, compound components, no Tailwind/shadcn).
- **Conflict notes**: this step's spec files (`web/e2e/regression/ai-send-model-select.spec.ts`, `two-client-realtime.spec.ts`, `context-controls-ai-effect.spec.ts`, `rate-limiting.spec.ts`) and its two new stub fixtures (`llm-stub/fixtures/model-select.json`, `llm-stub/fixtures/context-check.json`) are disjoint from whatever files steps 56/58/59 add under the same `web/e2e/regression/` directory and `llm-stub/fixtures/` — do not edit or rename another regression suite's spec/fixture files even if they appear related. Any source fix this step applies is bounded to the specific file/function a failing assertion pointed at (e.g. `server/internal/infrastructure/event/redis_hub.go`, `web/src/features/messages/lib/merge-message-event.ts`, `web/src/features/rooms/components/RoomSettingsDrawer.tsx`, `server/internal/interface/middleware/rate_limit.go`) — never a speculative, broader refactor of those files.
