# Step 47: Web: private AI mode UI

## Meta
- **Type**: ui
- **Components**: web
- **Wave**: 7 (parallel group — all steps of the same wave can run concurrently)
- **Depends on**: Step 10: Playwright E2E harness + seeded compose test stack + LLM stub | Step 35: Web WebSocket client + live cache merge | Step 41: Server: private AI mode | Step 45: Web: image upload + attachment UI + Vision send
- **Unlocks**: Step 58: E2E regression: summarization, streaming, private mode, images/Vision
- **Size**: 1 PR (a few hours for one AI agent)

## Context
Phase 14 of `phases.md` (`Private AI Mode`) lets a user ask the AI something inside a shared room without other room members ever seeing the question or the answer: the Go API tags the exchange with a `visibility` flag and the `MessageHub`'s per-user targeted delivery (already part of the architecture since the wave-3 WebSocket work) routes those events only to the sender's own connection instead of broadcasting to the room. Step 41 lands that server-side plumbing (the `visibility` column, the request flag, and REST/WS filtering so non-senders never receive the rows or events at all). This step is the web counterpart: a way to opt into private mode when sending to the AI, and a visual treatment that reminds the sender which exchanges in their own view are private — reusing the WebSocket hook and cache-merge utility Step 35 built and coordinating file ownership with Step 45, which is landing image/attachment controls in the same input and list components in the same wave.

## Goal
After this PR, the AI controls in the message composer expose a private-mode toggle. When enabled, the triggering human message and the resulting AI reply are both sent with the private flag set, both render with a distinct sender-only badge/styling in the message list, and both arrive to the sender exclusively through the existing WebSocket connection (never via a room-wide broadcast) — because the server only targets the sender's connection, a second user in the same room never receives the event or sees the row on refresh. A Playwright spec drives two independent users in the same room and asserts the second user never observes the private exchange while ordinary messages still flow normally between them.

  - [ ] Reset the toggle to off after each send with AI (mirroring the existing `setInput("")` reset in `handleSendWithAI`), so private mode is opt-in per message, not sticky.

- [ ] If the send path uses an optimistic local insert (Step 29's optimistic-update mutation), tag the optimistically-inserted human message with the same `visibility` the user selected so the badge/styling appears immediately, before the WS/REST-confirmed message reconciles over it via Step 35's id-based merge.
- [ ] Add sender-only visual treatment in the message list (`web/src/features/messages/components/MessageList.tsx` or its evolved equivalent): for any message with `visibility === "private"`, render a small `Badge` (e.g. `colorPalette="purple"` or `"orange"`, `variant="subtle"`, a `lucide-react` `Lock` icon + "Private" label) next to the existing sender label, and a distinguishing bubble treatment (e.g. a dashed or tinted border) on both the human prompt and the AI reply of that exchange. No sender-identity comparison is required to decide whether to show the badge — because Step 41 guarantees private rows/events are only ever delivered to the sender's own client, any `visibility === "private"` message present in a given client's cache already belongs to that client's own private exchange.
- [ ] Handle targeted WS events in the socket hook merge introduced by Step 35: update the discriminated event type (`web/src/features/messages/types/ws-events.ts` or wherever Step 35 defined `RoomSocketEvent`) and `merge-message-event.ts` so the `visibility` field on incoming `message-created`/`message-updated` payloads is parsed and passed through unchanged into the cached `Message` object (no silent stripping of the field, no special-cased branch needed beyond typing it correctly) — the "targeted" part of delivery is entirely a server-side scoping concern (per-user `MessageHub` delivery), the client only needs to merge whatever event it actually receives, correctly typed.
- [ ] Add a defensive no-op guard in the merge utility: if an inbound event's message somehow includes a `sender_id` that does not match the currently authenticated user's id while `visibility === "private"` (i.e. a private message the client should never have received), drop it instead of merging it into the cache and log a single `console.error` — a cheap belt-and-suspenders check that costs nothing when the server behaves correctly, exercised by the Playwright spec below. Reuse whatever current-user identity accessor exists by this wave (Step 9/30's `useSession()` in `web/src/features/auth/hooks/use-session.ts` is the expected one); if no such accessor exists yet, compare against `sender_id` only when a current-user id is available and skip the check otherwise — do not invent a new auth/session endpoint to make this check possible, that is out of scope here.
- [ ] Unit tests: extend `MessageInput`'s existing test coverage (or add `web/src/features/messages/components/MessageInput.test.tsx` if none exists yet) to cover the toggle's state/reset behavior and that `onSendWithAI` receives the correct boolean; extend `MessageList`'s tests (or add one) to assert the private badge/styling renders only for `visibility === "private"` messages; extend `merge-message-event.test.ts` from Step 35 with a case asserting `visibility` passes through untouched and a case asserting the defensive sender-mismatch guard drops the event.
- [ ] Playwright spec `web/e2e/private-mode.spec.ts` (per the harness Step 10 established): register two independent users (unique emails/usernames per run, following the pattern in `web/e2e/smoke.spec.ts`), have one invite/add the other to the same room (or otherwise get both into the same room per whatever member-management UI Step 37 landed by this wave), open the room in two separate browser contexts, have user A toggle private mode and send an AI message, assert user A's view shows the private badge and the AI reply; assert user B's view — polled for a few seconds to allow for any WS delivery — never shows that message (neither the human prompt nor the AI reply), while a subsequent ordinary (non-private) message from user A still appears promptly in user B's view, proving the WS connection and normal delivery are otherwise unaffected.

## Out of scope
- The `visibility` column, migration, request DTO field, and REST/WS filtering/targeted-delivery logic that makes private messages invisible to non-senders in the first place (Step 41, server-side).
- The WebSocket client, reconnect/backoff, ticket auth, and the base cache-merge utility and connection-status indicator (Step 35) — this step only extends the event type and merge function Step 35 created, it does not rebuild the hook.
- Image/attachment upload UI and Vision send wiring in the composer (Step 45, same wave) — coordinate on `MessageInput.tsx`/`MessageList.tsx` ownership per the conflict notes below; do not touch attachment-related code.
- Streaming token rendering of the AI reply bubble (Step 54, same wave) — this step's private badge/styling must not assume or require a non-streaming bubble; if Step 54 lands first, style the streaming bubble container, not a separate non-streaming one.
- Room-level default privacy settings, group-wide private mode policy, or any RBAC gating of who may use private mode (not part of Phase 14's scope; no such control exists in `phases.md`).
- A dedicated "private messages" filter/inbox view — this step only affects the existing single room timeline.
- Any new auth/session/current-user endpoint — the defensive sender-mismatch guard degrades gracefully to a no-op check if no current-user id is available client-side yet.
