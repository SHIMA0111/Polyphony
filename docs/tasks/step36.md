# Step 36: Web room settings drawer

## Meta
- **Type**: ui
- **Components**: web
- **Wave**: 6 (parallel group — all steps of the same wave can run concurrently)
- **Depends on**: Step 16: Web persistent sidebar chat layout | Step 24: Server: per-room AI provider/model settings | Step 34: Model metadata (token limits + pricing) across gateway/server/web
- **Unlocks**: Step 52: Web room fork UI | Step 57: E2E regression: realtime AI core — send, model select, context controls, rate limiting
- **Size**: 1 PR (a few hours for one AI agent)

## Context
`web/src/features/messages/components/ChatRoom.tsx` already renders a `MoreVertical` icon button in its header, but it has no `onClick` — it is dead UI left over from the original design. At the same time, three server-side capabilities have landed with no web surface at all: Step 13's per-room `role` on `RoomResponse` (reader/guest/member/admin/master), Step 23's `ai_context_cutoff_at` cutoff on `rooms` (Phase 5, "AI Context Control"), and Step 24's `ai_provider`/`ai_model` room defaults plus `PATCH /rooms/:roomId/settings` (Phase 6, "Provider/model selection in room settings"). Step 34 layered token-limit/pricing metadata onto `GET /models` so a model picker can show more than a bare name. This step is the first place any of that becomes usable from the web app: it turns the dead button into a real, role-gated settings surface for the room a user is currently in.

## Goal
Clicking the header's overflow (`MoreVertical`) button in `ChatRoom.tsx` opens a `Drawer.Root`-based room settings drawer. Any member can open it and see the room's current name, description, AI provider/model default, and AI context cutoff as read-only information. Members whose role is `admin` or `master` (per `RoomResponse.role`) additionally see editable controls: rename + description (saved via the existing room update endpoint), an AI provider/model selector preselected from the room's current settings and backed by live `/models` metadata (saved via `PATCH /rooms/:roomId/settings`), and an AI context-cutoff control (saved via whatever endpoint Step 23 exposes for `ai_context_cutoff_at`). Only `master` sees a "Delete room" action, gated behind a confirmation dialog, after which the caller is navigated back to `/rooms`. No other room chrome changes.

## Out of scope
- Members list, invitations, and per-member role changes inside the drawer — that is Step 37's dedicated UI; this drawer only reads the current user's own `role` for gating and does not list or manage other members.
- Per-message AI-exclude toggle and the token-usage meter — that is Step 38's territory; this step owns only the room-level cutoff control, deliberately placed here instead of Step 38 so there is no interim/duplicate placement.
- Room fork trigger/UI (Step 52 builds on this drawer later; no fork entry point is added here).
- Token balance / usage history UI (Step 48).
- Any RBAC, endpoint, or schema changes on the server — this step only consumes endpoints Steps 13/23/24 already ship; if any of those endpoints are missing or shaped differently than expected when this step is implemented, adapt the client call to match the actual merged server code, but do not add new server routes or DB columns from this step.
- Redesigning `ChatRoom.tsx`'s header layout beyond wiring the existing button's `onClick` and any local `isSettingsOpen` state.
- Anthropic/Gemini-specific provider UX beyond what a flat model list already provides (no per-provider grouping/branding beyond what `ModelSelector`-style badges already do).
- WebSocket-driven live updates to room settings from other users editing concurrently — out of scope; the drawer reflects the data it fetched on open/last save.
