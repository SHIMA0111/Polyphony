# Step 42: Server: token balance management

## Meta
- **Type**: feature
- **Components**: server
- **Wave**: 4 (parallel group — all steps of the same wave can run concurrently)
- **Depends on**: Step 7: Go event-driven messaging core: MessageHub, atomic sequences, response linkage | Step 13: Go 5-tier RBAC domain + authorization middleware + ModelUsecase
- **Unlocks**: Step 48: Web: token balance + usage history UI | Step 49: Server: Stripe billing (test mode) + subscription lifecycle | Step 51: Go: consume gateway stream + WS chunk forwarding (streaming sends reuse this step's `BillingGuard`)
- **Size**: 1 PR (a few hours for one AI agent)

## Context
`phases.md` Phase 16 ("Token Balance Management") requires that AI usage be metered and that an AI invocation be rejected with a clear error once the paying user's balance is exhausted, per the "room master pays" billing model described in `CLAUDE.md`'s Token billing section. Today `server/internal/domain/ai/entity.go`'s `CompletionResponse` already carries `PromptTokens`/`OutputTokens` back from the LLM Gateway, but nothing in `server/internal/usecase/message/usecase.go` ever reads them — `SendAIMessage`/`RegenerateAIMessage` call `llmGateway.Complete` unconditionally and no notion of cost or balance exists anywhere in the Go server. Step 13 lands the typed `room.Role`/`Action` RBAC primitives this step's routes don't need directly (billing endpoints are scoped to "the authenticated user's own balance", not room-role-gated), but its `ModelUsecase`/handler-layering pattern and its serialization of the message-usecase file are both prerequisites this step builds on. Step 7 lands the sequence/event-publish shape of `SendAIMessage`/`RegenerateAIMessage` that this step's pre-call guard is inserted into. Room ownership (`rooms.owner_id`) — not the `master` RBAC role label — is the billed identity: `phases.md` Phase 3 explicitly calls out that ownership transfer is "required for billing entity (`token_balances`) migration", meaning balances are keyed by user so that transferring a room's ownership naturally moves who pays for its AI usage, without any data migration. This step gives Phase 16 a real home before Step 48 (web balance/usage UI) and Step 49 (Stripe top-ups) build on it.

## Goal
After this PR, every user has a lazily-created token balance (`token_balances`, keyed by `user_id`, starting at zero — no automated initial provisioning, per `phases.md`'s explicit exclusion for this phase). Before each AI invocation, `MessageUsecase.SendAIMessage`/`RegenerateAIMessage` calls a small `BillingGuard` (new file, not touching Step 23's context-assembly code) that checks the room owner's balance and returns HTTP 402 (`domain.ErrInsufficientBalance`) if it is at or below zero. After a successful completion, the same guard debits the room owner's balance by `PromptTokens + OutputTokens` and records an immutable `token_transactions` row — this is fire-and-forget (logged, never rolls back the already-persisted message) exactly like the existing event-publish pattern. `GET /billing/balance` and `GET /billing/transactions` expose the authenticated user's own balance and a cursor-paginated usage/transaction history. A `task billing:topup` dev task (backed by a small `server/cmd/seed-tokens` CLI reusing the same repository code, not a hand-written SQL script) lets a developer credit a user's balance locally since automated provisioning is out of scope.

## Out of scope
- Stripe integration, subscription plans, and any payment-rail webhook that credits `token_balances` from a real purchase (Step 49 / Phase 17) — `CreditAndRecord` is built here but only exercised by the dev seed CLI in this step.
- Automated initial balance provisioning for new users (explicitly excluded by `phases.md` Phase 16) — new users start at zero and must be topped up manually (`task billing:topup`) for local testing.
- Any change to AI context assembly, `ai.ContextBuilder`, or the `rm, err := u.roomRepo.GetByID(...)` cutoff-lookup line Step 23 adds to `SendAIMessage`/`RegenerateAIMessage` — this step's guard/record calls are added as separate, non-overlapping lines in the same two methods, per the plan's conflict notes.
- Per-token-type or per-provider pricing/cost multipliers — `RecordUsage` debits the raw `PromptTokens + OutputTokens` count as-is; converting tokens to a currency cost is Phase 17's concern.
- Estimating the cost of an in-flight request before it completes (e.g. rejecting a request whose *estimated* cost exceeds the remaining balance) — the guard is a simple `balance > 0` check; exact-cost pre-estimation is not attempted here.
- Any Web Frontend changes to display balance or usage history (Step 48 ships the UI against the endpoints this step creates).
- Room-role-based authorization on the billing endpoints — `GET /billing/balance`/`GET /billing/transactions` only require the standard `JWTAuth` (any authenticated user reading their own balance/history), not any room-scoped RBAC check from Step 13.
- Refunds, chargebacks, or any transaction-reversal flow beyond the generic `adjustment` transaction type existing as a placeholder for later manual corrections.

- **Conflict notes**: this step shares `SendAIMessage`/`RegenerateAIMessage` with Step 23 (AI context control), which lands in the same wave. Step 23 owns context assembly (the `contextBuilder.Build` call, the cutoff lookup, `DeleteMessage`/`SetExcludeFromAI`); this step owns only the balance guard (first line of `SendAIMessage`, one line after the auth check in `RegenerateAIMessage`) and the post-completion `RecordUsage` call. Put the guard/record logic in the new `billing_guard.go` file specifically so the diff surface in `usecase.go` itself is minimal (a few single-line insertions), reducing the chance of a textual merge conflict with Step 23's larger edits to the same file. `token_balances`/`token_transactions` are brand-new tables — no coordination is needed with Step 23 (touches `messages`/`rooms` columns) or Step 24 (touches `rooms` columns) on the schema side.
- **Reuse, don't duplicate**: `postgres.MessageRepository`'s `messageColumns`/`scanMessage`/cursor-pagination pattern (`server/internal/interface/repository/postgres/message_repository.go`) is the direct template for `BillingRepository.ListTransactions`; `MessageHandler.List`'s `cursor`/`limit` query-param parsing and clamping (`server/internal/interface/handler/message_handler.go`) is the direct template for `BillingHandler.ListTransactions`; `MessageRepository.GetNextSequence`'s single-statement atomic `UPDATE ... RETURNING` pattern is the direct template for the balance mutation inside `DebitAndRecord`/`CreditAndRecord` (wrapped in an explicit transaction here only because a second `INSERT` must commit atomically alongside it).
- **Why `BillingGuard` is a locally-defined interface in `usecase/message` rather than importing `usecase/billing` directly**: this keeps `usecase/message` decoupled from `usecase/billing`'s internals and mirrors the existing `ai.LLMGateway` dependency shape (`MessageUsecase` depends on a narrow domain-level interface, not a concrete adapter). Since Go interface satisfaction is structural, `*billingusecase.BillingUsecase` implements `message.BillingGuard` automatically — no explicit adapter type is needed, and the DI container passes `billingUC` straight into `NewMessageUsecase`.
- **Billing entity is the room owner, not the RBAC `master` role**: `room.RoomMember.Role == RoleMaster` is a per-room authorization label (Step 13) that can, in principle, be held by more than one path through role changes in later steps; `rooms.owner_id` (already on `domain/room.Room`, unchanged since Phase 1) is the single stable "who pays" identity `phases.md` Phase 3's ownership-transfer note refers to. `CheckBalance`/`RecordUsage` must always resolve the payer via `roomRepo.GetByID(ctx, roomID).OwnerID`, never via a membership role lookup.
- **DTO/response shape must match Step 48's already-written contract exactly**: `web/src/features/billing/types.ts` (introduced by Step 48) defines `TokenBalance { user_id, balance, updated_at }`, `TokenTransaction { id, user_id, room_id, type, amount, balance_after, description, created_at }` with `type` as `"consumption" | "charge" | "adjustment"`, and `TokenTransactionPage { transactions, next_cursor }`. This step's Go DTOs and DB `CHECK` constraint values must produce exactly this JSON shape — do not rename fields, change casing, or use different transaction-type strings.
- **Schema/migration convention** (see `CLAUDE.md` and the plan's schema convention): edit `server/schema.sql` additively — only two brand-new tables in this step — then run `task migrate:generate -- add_token_balances` from the repo root; this shells into `server/` and runs `atlas migrate diff <name> --env local` per `Taskfile.yml`, producing a new file under `server/migrations/` and updating `server/migrations/atlas.sum`.
