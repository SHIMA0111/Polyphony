# Step 16: Web persistent sidebar chat layout

## Meta
- **Type**: ui
- **Components**: web
- **Wave**: 3 (parallel group — all steps of the same wave can run concurrently)
- **Depends on**: Step 9: Web data layer migration: TanStack Query, RSC prefetch, per-feature API modules
- **Unlocks**: Step 36: Web room settings drawer | Step 37: Web members, invitations, and roles UI | Step 48: Web: token balance + usage history UI
- **Size**: 1 PR (a few hours for one AI agent)

## Context
`phases.md`'s target frontend directory tree already names `web/src/app/(main)/layout.tsx` as part of the Bulletproof React layout, but the file does not exist yet: today `web/src/app/(main)/rooms/page.tsx` renders a full-page `RoomList` (its own header, logo, and avatar menu) and `web/src/app/(main)/rooms/[roomId]/page.tsx` renders a full-page `ChatRoom` with its own back-chevron header — there is no shared chrome and no persistent room list, so switching rooms means leaving the room list entirely. This step introduces the Slack/LINE-like persistent layout described in the project vision: a room-list rail that stays mounted across navigations plus a chat pane, with the two collapsing responsively into a single list-then-thread flow on mobile. It is the foundation every later room-context UI (settings drawer, members/invitations, token usage) will dock into, per the "Unlocks" steps above.

## Goal
After this PR, `web/src/app/(main)/layout.tsx` renders a persistent two-region shell: a top bar (logo + user menu, moved out of `RoomList`) and, below it, a room-list rail (`RoomRail`) alongside the routed page content. At `>= md` viewports both the rail and the content pane are always visible side by side, and navigating between rooms only swaps the pane (the rail, its data, and the top bar never remount, and no full page reload occurs). Below `md`, the same tree collapses to a single visible region at a time — the rail (acting as the room list screen) when no room is selected, the content pane (the chat) when a room is selected — driven purely by the current route, not by separate mobile-only markup. Deep links to `/rooms/[roomId]` render correctly in both breakpoints on first load.

If, unexpectedly, no such hook exists yet when this step is implemented, add the minimal query hook in `web/src/features/rooms/` first (small, in-scope addition) and have both `RoomList` and `RoomRail` consume it — do not leave two independent fetch paths for the same data.
- Auth/user-menu logic (post-Step-9: the `useLogout()` mutation hook from `web/src/features/auth/hooks/`) moves with the header markup into `(main)/layout.tsx`. Keep using the existing `Menu.Root`/`Menu.Trigger`/`Menu.Positioner`/`Menu.Content`/`Menu.Item` compound pattern already in `RoomList.tsx` — it is correct Chakra v3 usage per `.claude/rules/chakra-ui.md`.
- Rail/pane structure: use Chakra `Flex`/`Grid` with style props only — no Tailwind classes, no `cn()`. A reasonable shape: an outer `Flex direction="column" h="100vh"` containing the top bar `Flex` (fixed height, spans full width) and a second `Flex flex={1} minH={0}` row containing `RoomRail` (fixed width e.g. `w="280px"`, `flexShrink={0}`, own `overflowY="auto"`) and a `Box flex={1} minW={0} overflowY="auto"` wrapping `{children}`. Apply the responsive `display` props described in Scope to the rail and to the `{children}` wrapper (not to the top bar, which is always visible).
- Active-room detection: `const params = useParams<{ roomId?: string }>(); const activeRoomId = typeof params.roomId === "string" ? params.roomId : undefined;` — this works because `useParams()` in a Client Component reads the params of whichever page is currently rendered beneath the layout, including from a layout file itself.
