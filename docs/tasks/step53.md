# Step 53: Web: plans, Stripe Checkout, subscription management, billing history UI

## Meta
- **Type**: ui
- **Components**: web
- **Wave**: 6 (parallel group — all steps of the same wave can run concurrently)
- **Depends on**: Step 10: Playwright E2E harness + seeded compose test stack + LLM stub | Step 17: Web forms, toaster, and App Router error surfaces | Step 49: Server: Stripe billing (test mode) + subscription lifecycle
- **Unlocks**: Step 59: E2E regression: billing and room fork
- **Size**: 1 PR (a few hours for one AI agent)

## Context
`phases.md` Phase 17 ("Stripe Billing") requires that users be able to purchase subscriptions and on-demand token packs via Stripe, and lists "Web Frontend: Plan selection, Stripe Checkout integration, billing history" as its web scope. Step 49 lands the server side (plan catalog, Checkout Session creation, webhook-driven subscription lifecycle, billing-portal session creation, `subscriptions`/`payment_history` tables), but today `web/` has no billing surfaces beyond the read-only token balance/usage-history views Step 48 ships (`web/src/features/billing/`, `web/src/app/(main)/billing/usage/page.tsx`) — there is nowhere for a user to actually spend money, see what plan they are on, cancel, or review past payments. This step closes that gap by adding the purchase and subscription-management surfaces on top of the `billing` feature module Step 48 established, without touching Step 48's existing balance/usage files or any shared chrome (top bar, avatar menu, message components).

## Goal
After this PR, a signed-in user can open `/billing/plans` to see subscription plans and one-time token packs, click through to a real Stripe test-mode Checkout Session and land back on a success or cancel route in `web/`, view their current plan and renewal/cancellation state at `/billing/subscription` with a "Manage subscription" action that opens the Stripe billing portal, and browse a paginated `/billing/history` of past payments. All four routes share a small new billing sub-navigation layout. A Playwright spec exercises the plan-selection → Stripe test Checkout → webhook-driven success flow using `stripe-cli`, and MSW-backed component tests cover the plan list, subscription summary, and payment history list in isolation.

## Implementation notes

**Contracts from Step 49** (Step 49's doc pins these down — this step's Scope items above are written against them; confirm the merged code matches before implementing):
```
GET  /billing/plans                       -> 200 { "plans": [{ "code", "name", "description", "price_cents", "currency", "interval": "month"|"one_time", "token_allowance" }] }
POST /billing/checkout-session            body { "type": "subscription"|"token_purchase", "plan_code"?, "package_code"? } -> 201 { "checkout_url" }
GET  /billing/subscription                -> 200 <subscription> | 204 No Content (no subscription — map to this step's status: "none" client-side)
POST /billing/subscription/cancel         -> 200 <subscription with cancel_at_period_end: true> | 404
POST /billing/portal-session              body { "return_url" } -> 200 { "portal_url" }
GET  /billing/payments?cursor=&limit=     -> 200 { "payments": [...], "next_cursor": string|null }
POST /webhooks/stripe                     -> Stripe webhook receiver (server-to-server only; not called from web/)
```
Step 49's checkout success/cancel URLs default to this step's routes (`/billing/checkout/success?session_id={CHECKOUT_SESSION_ID}` and `/billing/checkout/cancel`), so no server-side config change is needed here.
`price_cents`/`amount_cents` are integer minor-currency units (Stripe convention) — format with `Intl.NumberFormat` at display time, never send/display raw floats.

**Assumed contracts from earlier waves** (per this codebase's established per-feature pattern, same as cited in `docs/tasks/step48.md`):
- `web/src/lib/http-client.ts` (or equivalent named by Step 4/9) exports a client with `get/post<T>(path, body?)` methods calling `/api/proxy${path}` — the successor to `RealApiClient.request()` in `web/src/lib/api.ts`. Confirm the actual file/method names at implementation time; do not reintroduce a second parallel fetch wrapper.
- Query keys already in use: `["rooms"]`, `["rooms", roomId]`, `["billing", "balance"]`, `["billing", "transactions", ...]` (Step 48). This step adds four new, non-colliding keys: `["billing", "plans"]`, `["billing", "subscription"]`, `["billing", "payment-history", ...]`, plus two mutations with no persisted key.
- `toaster` from `@/components/ui/toaster` (Step 17) for all mutation-error surfacing, per the pattern in `web/src/features/auth/components/LoginForm.tsx`.

**Chakra v3 conventions** (per `.claude/rules/chakra-ui.md`): `@chakra-ui/react` compound components first (`Card.*`, `Table.*`, `Badge`, `SimpleGrid`, `Skeleton`), style props only (no Tailwind/`cn()`), semantic color tokens (`bg.subtle`, `fg.muted`, `border`), `colorPalette` for the status-color badges, `lucide-react` icons where useful (e.g. `CreditCard`, `Receipt`, `CheckCircle2` on the success page). `PlanCard`/`PlanList`/`SubscriptionSummary`/`PaymentHistoryList` and the new billing pages are new UI surfaces, not small logic tweaks, so per `CLAUDE.md`'s "UI Development Workflow" use the `v0-design` skill to generate their visual design, then adapt per the v0-conversion rules in `.claude/rules/chakra-ui.md` (replace shadcn/Radix primitives with the named Chakra compound components, replace Tailwind classes with style props, keep `lucide-react` icons, replace `variant="destructive"` with `colorPalette="red"`).

**No `schema.sql` changes** — this step is purely a client-side feature module; `subscriptions`/`payment_history` are Step 49's territory.

**Conflict notes**: this step owns the entirely new `web/src/app/(main)/billing/layout.tsx`, `web/src/app/(main)/billing/plans/`, `web/src/app/(main)/billing/subscription/`, `web/src/app/(main)/billing/history/`, and `web/src/app/(main)/billing/checkout/` directories outright, plus additive-only exports in the shared `web/src/features/billing/types.ts` and `web/src/features/billing/api/handlers.ts` files Step 48 created.
