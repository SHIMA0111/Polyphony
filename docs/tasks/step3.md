# Step 3: Rust gateway domain/ports reshape (streaming+multimodal-ready)

## Meta
- **Type**: refactor
- **Components**: llm-gateway
- **Wave**: 1 (parallel group — all steps of the same wave can run concurrently)
- **Depends on**: None
- **Unlocks**: Step 8: Rust gateway operational hardening | Step 14: Rust gateway test harness: router oneshot + wiremock provider tests | Step 19: gRPC contract: proto definitions + Rust tonic inbound adapter
- **Size**: 1 PR (a few hours for one AI agent)

## Context

The LLM Gateway (`llm-gateway/`) currently has a minimal hexagonal skeleton (`llm-gateway/src/domain/`, `llm-gateway/src/ports/`, `llm-gateway/src/adapters/`) built for a single synchronous OpenAI-only completion flow: `domain/error.rs` is a hand-written `enum` with manual `Display`/`Error` impls and no source chains, `domain/model.rs`'s `ChatMessage` holds plain-`String` content with no way to represent image parts, `LLMProvider::models()` is synchronous, and there is no streaming port at all. `phases.md` schedules Anthropic/Gemini providers, Vision/multimodal input, and streaming responses as later phases, and `adapters/outbound/openai.rs` already has two independent, subtly inconsistent role-string conversion functions (`role_to_string`/`string_to_role`) duplicated again in `adapters/inbound/rest/request.rs` (`parse_role`) and `adapters/inbound/rest/response.rs` (`role_to_api_string`). Reshaping the domain/ports layer once, now, before more providers and endpoints land — richer errors, multimodal-ready content, async model listing, a streaming port, and a per-provider module layout — means every subsequent gateway step (hardening, testing, gRPC, new providers, Vision, SSE streaming) builds on a stable foundation instead of each re-deriving it independently.

## Goal

After this PR, `llm-gateway`'s domain and ports layers are shaped for everything phases 6–19 will need, without implementing any of those features yet: `DomainError` is a `thiserror`-derived enum with proper `#[source]` chains and a new `RateLimited` variant (mapped to HTTP 429); `ChatMessage.content` is a `MessageContent` enum (`Text` or `Parts` of text/image-url/image-base64 parts) so Vision input can be added later without another domain rewrite; `LLMProvider::models()` and `CompletionUseCase::list_models()` are async (`futures::future::BoxFuture`), with `OpenAIProvider` caching its static model list in a `std::sync::OnceLock`; a new `CompletionChunk` domain type and `stream()` method exist on both the outbound (`LLMProvider`) and inbound (`CompletionUseCase`) ports (returning `futures::stream::BoxStream`), with `OpenAIProvider` providing a documented not-yet-implemented stub; `adapters/outbound/openai.rs` is split into `adapters/outbound/openai/mod.rs` + `request.rs` + `stream.rs` so the Vision-mapping step and the SSE-streaming step can each own one submodule without touching the same file; and the three duplicated role-parsing functions are unified into a single `domain::model::Role::parse` (fixing the inconsistency where `"developer"` was accepted by the OpenAI response parser but rejected by the REST inbound parser).

- Files to delete and replace with a directory module: `llm-gateway/src/adapters/outbound/openai.rs` → `llm-gateway/src/adapters/outbound/openai/mod.rs`, `llm-gateway/src/adapters/outbound/openai/request.rs`, `llm-gateway/src/adapters/outbound/openai/stream.rs`. No edit needed to `llm-gateway/src/adapters/outbound/mod.rs` (currently `pub mod env_key; pub mod openai;` — Rust resolves `openai` to `openai/mod.rs` automatically) or `llm-gateway/src/main.rs` (DI assembly at `llm-gateway/src/main.rs:31-39` calls `OpenAIProvider::new(key_store)` and `CompletionService::new(vec![...])`, whose public signatures are unchanged by this step).
- **Role unification rationale**: today there are three separate role-string functions — `adapters/outbound/openai.rs`'s `string_to_role` (lenient, defaults to `User` on unknown, *does* accept `"developer"`) and `role_to_string` (System → `"developer"`), and `adapters/inbound/rest/request.rs`'s `parse_role` (strict `Result`, *rejects* `"developer"` — this is the bug). The two *parsing* (wire → domain) functions get unified into one `Role::parse` in `domain/model.rs` so both REST clients and OpenAI responses now treat `"developer"` as a `System` alias consistently. The two *serialization* (domain → wire) functions stay conceptually separate because they target genuinely different protocols: `Role::as_str` is the canonical REST-wire form (`"system"`, used by `rest/response.rs`), while OpenAI's outbound convention (`"developer"`) is provider-specific and stays as a small private helper in `openai/request.rs` — do not try to merge these two, only the parsing side.
- **Clean Architecture guard**: `domain/error.rs`'s new `#[source]` field must stay `Box<dyn std::error::Error + Send + Sync>`, never a concrete crate type like `reqwest::Error` or `serde_json::Error` — the domain layer must not gain a dependency on `reqwest`/`serde_json`, per `CLAUDE.md`'s "Domain layer must NOT import infrastructure packages" rule. Adapters (in `openai/request.rs`) box their own concrete errors when calling `DomainError::provider_error_with_source`.
- `OpenAIProvider::new` (currently `llm-gateway/src/adapters/outbound/openai.rs:37-54`) reads `OPENAI_BASE_URL` from `std::env` directly and only sets a `connect_timeout` on its `reqwest::Client` — leave that as-is in this step; Step 8 ("Rust gateway operational hardening") is the one that moves env reads into `Config` and adds a request timeout + retry policy. Do not pre-build that here.
- `CompletionService::new(providers: Vec<Box<dyn LLMProvider>>)` (`llm-gateway/src/domain/service.rs:22`) keeps its current constructor signature in this step — Step 8 is the one that adds a `key_store` parameter for readiness checks. Do not add it here.
- `Cargo.toml` currently pins `axum = "0.8"`, `reqwest = { version = "0.13", features = ["json"] }`, `tokio = { version = "1", features = ["full"] }` — add `thiserror = "2"` and `futures = "0.3"` alongside these without touching existing entries.
- Rustdoc: every new/changed public item (`MessageContent`, `ContentPart`, `CompletionChunk`, `Role::parse`, `Role::as_str`, `DomainError::provider_error`/`provider_error_with_source`, the new `LLMProvider`/`CompletionUseCase` trait methods) gets a `///` doc comment with `# Arguments`/`# Returns`/`# Errors` sections as applicable, following the existing style in `llm-gateway/src/ports/outbound/key_store.rs` and `llm-gateway/src/adapters/outbound/env_key.rs`.
- All code, comments, and test names in English, per `CLAUDE.md`.
- **conflictNotes**: this step rewrites `domain/`, `ports/`, and the OpenAI adapter ahead of every other gateway step — land it first in the merge queue among wave-1 gateway PRs. The `openai/request.rs` + `openai/stream.rs` split is deliberate: a later Vision-mapping step edits only `openai/request.rs` (plus new shared content-part DTOs it introduces itself) and a later SSE-streaming step edits only `openai/stream.rs` (plus new endpoint files), so the two stay disjoint in the same wave. `llm-gateway/src/adapters/inbound/rest/request.rs` is a *different file* from `llm-gateway/src/adapters/outbound/openai/request.rs` despite the shared filename — the REST inbound DTO layer is not part of that same-wave ownership split.
