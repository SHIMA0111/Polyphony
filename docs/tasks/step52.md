# Step 52: Web room fork UI

## Meta
- **Type**: ui
- **Components**: web
- **Wave**: 7 (parallel group — all steps of the same wave can run concurrently)
- **Depends on**: Step 10: Playwright E2E harness + seeded compose test stack + LLM stub | Step 32: Server: room fork (async batch copy) | Step 36: Web room settings drawer
- **Unlocks**: Step 59: E2E regression: billing and room fork
- **Size**: 1 PR (a few hours for one AI agent)

## Context
Phase 20 of `phases.md` ("Room Fork") requires a "Fork button, progress display" on the web frontend, on top of Step 32's server-side async batch-copy job (`POST /rooms/:roomId/fork` returns HTTP 202 with a `job` + `new_room`, `GET /rooms/:roomId/fork-jobs/:jobId` is pollable, and the destination room stays `is_archived=true` — rejecting new posts with HTTP 409 — until the job reaches `completed`). Step 36 already turned `ChatRoom.tsx`'s dead `MoreVertical` header button into a role-gated `RoomSettingsDrawer` (admin/master-only editable sections, a `master`-only "Danger zone") but explicitly left the fork entry point out of scope for that step ("Room fork trigger/UI (Step 52 builds on this drawer later; no fork entry point is added here)"). This step is the first (and only) place a user can actually trigger and observe a fork from the web app, and the first place the app has to render a room that exists but cannot yet accept messages.

## Goal
After this PR, `RoomSettingsDrawer` (from Step 36) gains a "Fork this room" action, visible to the same admin/master audience as its other management controls, in its own section (not the `master`-only "Danger zone", since forking is scoped to `ActionManageRoom` — admin and master — per Step 32's authorization rule, distinct from delete's master-only rule). Triggering it calls `POST /rooms/:roomId/fork`, then shows an inline progress view (copied/total message counts, a percentage or indeterminate state) that polls `GET /rooms/:roomId/fork-jobs/:jobId` until the job reaches `completed` or `failed`, at which point the drawer offers a link to open the new room. Navigating directly to a room whose `is_archived` is `true` (via that link, a bookmark, or the room rail) renders `ChatRoom` in a read-only "Archived — fork in progress" state: the message list and history remain visible, but `MessageInput` is replaced with a banner and no send action is available; once the underlying job completes and the room's `is_archived` flips to `false`, the same room view becomes writable again without a manual reload. A new Playwright spec drives the full fork → progress → new-room-usable path against the Step 10 harness.

## Scope
- [ ] Extend the `Room` interface in `web/src/features/rooms/types.ts` (Step 9's per-feature types module) with `is_archived: boolean` and `forked_from_room_id: string | null`, matching the exact JSON field names Step 32 added to `RoomResponse` (verify against the merged `server/internal/interface/handler/dto.go` before naming these — if Step 36 or another prior step already added `is_archived`/`forked_from_room_id` to the client `Room` type, reuse it, do not add a duplicate field).
- [ ] Add `ForkJob` and `RoomForkResponse` types to `web/src/features/rooms/types.ts`, mirroring Step 32's `ForkJobResponse`/`RoomForkResponse` DTOs exactly (field names/casing as actually shipped by the merged server code): `ForkJob { id: string; source_room_id: string; new_room_id: string; status: "pending" | "running" | "completed" | "failed"; total_messages: number; copied_messages: number; error_message: string | null; created_at: string; updated_at: string }`; `RoomForkResponse { job: ForkJob; new_room: Room }`.
- [ ] Add a fork-trigger API call and a fork-job-status API call to wherever the rest of the room API surface already lives in the merged codebase at implementation time (the rooms feature's typed API client module, e.g. alongside the room-update/settings/cutoff calls Step 36 added — do not reintroduce a second parallel client): `forkRoom(roomId: string): Promise<RoomForkResponse>` (`POST /rooms/:roomId/fork` via `/api/proxy`) and `getForkJobStatus(roomId: string, jobId: string): Promise<ForkJob>` (`GET /rooms/:roomId/fork-jobs/:jobId`).
- [ ] Add a `useForkJobPolling` hook (or equivalent, colocated with the rooms feature's other hooks) that, given a `roomId`/`jobId` pair, polls `getForkJobStatus` on a short fixed interval (e.g. 1.5–2s) and stops polling once `status` is `"completed"` or `"failed"`; if the codebase's TanStack Query migration has landed by the time this step is implemented, implement this as a `useQuery` with `refetchInterval: (query) => (terminal status ? false : 1500)` on query key `["rooms", roomId, "fork-jobs", jobId]`; if it has not yet landed for the rooms feature, use a plain `useEffect` + `setInterval`/cleanup, consistent with whatever pattern `ChatRoom.tsx` itself still uses for data fetching at that point.
- [ ] In `web/src/features/rooms/components/RoomSettingsDrawer.tsx`, add a new "Fork room" section (admin/master only, i.e. gated by the same `canManage` boolean Step 36 already computes from `role`, not the master-only `canDelete` boolean): a short explanatory line ("Copy every message in this room into a new, independent room.") and a "Fork this room" `Button`. Clicking it calls `forkRoom(roomId)`, then swaps the section's content to an inline progress view driven by `useForkJobPolling` for the returned `job.id`:
  - While `status` is `"pending"`/`"running"`: a `Progress.Root`/`Progress.Track`/`Progress.Range` (Chakra v3 compound API) showing `copied_messages / total_messages` (or an indeterminate/`value={null}` bar while `total_messages` is still `0`, since Step 32's worker only sets it once the job transitions to `running`), plus a text line like "Copying messages… 320 / 1000".
  - On `status === "completed"`: replace the progress bar with a success message and a `Link`/`Button` ("Open forked room") navigating to `/rooms/{job.new_room_id}`.
  - On `status === "failed"`: replace the progress bar with an inline error state showing `error_message` and a "Try again" button that re-triggers `forkRoom` (starting a new job; Step 32 does not support resuming/retrying a failed job in place).
  - Do not block the rest of the drawer while a fork is in progress — the user can close the drawer and keep using the current (source) room normally; if the drawer is reopened while a job from this session is still running, it is acceptable to just show the "Fork this room" button again in its initial state (no requirement to persist in-flight fork-job tracking across a drawer close/reopen or a page reload — Step 32's job is durable server-side and remains pollable via its own room's settings drawer once opened, but rediscovering an already-in-flight job id after a client-side reset is out of scope for this step).
- [ ] In `web/src/features/messages/components/ChatRoom.tsx` (or wherever the room's `is_archived` flag is read once Step 36's `Room` extension lands), add an archived-room read-only state: when `room.is_archived` is `true`, render an `Alert`/`Banner`-style strip above or in place of `MessageInput` (e.g. "This room is archived — a fork copy is still in progress and cannot accept new messages yet.") and do not render `MessageInput` at all (no send box, no AI-send controls) while archived; `MessageList`/message history remain visible and scrollable exactly as for a normal room. This is an additive conditional around the existing `MessageInput` render, not a rewrite of `ChatRoom.tsx`'s layout.
- [ ] Ensure the archived-room banner clears automatically once the room becomes writable again without requiring a manual page reload: either (a) the same polling this step already added for the settings-drawer progress view also invalidates/refetches the room object once a job tied to `new_room_id === roomId` completes (only relevant if the user is viewing the destination room from the same browser tab that triggered the fork), or (b), simpler and sufficient for the common case (a user navigating to the new room only after seeing "completed" in the drawer, or opening it in a fresh tab), just re-fetch the room's own data (including `is_archived`) each time `ChatRoom` mounts/the room id changes, which already reflects the server's current state at that moment. Do not add a background poll to every open `ChatRoom` for its own `is_archived` status — only the drawer's own in-flight fork-job polling (per the item above) needs a live progress subscription.
- [ ] Add component tests (matching whatever test runner/pattern is established for `RoomSettingsDrawer`/sibling components by the time this step lands, e.g. Vitest + RTL + MSW mirroring `CreateRoomForm.test.tsx`): fork section is hidden for reader/guest/member; visible for admin/master; clicking "Fork this room" calls the fork endpoint and renders the progress view; a mocked terminal `"completed"` status renders the "Open forked room" link pointing at `new_room.id`; a mocked terminal `"failed"` status renders `error_message` and a working "Try again" button. If no component-test runner exists yet at implementation time, perform and document the equivalent manual verification instead (do not introduce new test tooling here).
- [ ] Add `web/e2e/room-fork.spec.ts` (Playwright, against the Step 10 harness): see Verification for the exact scenario and assertions.

## Out of scope
- Any server-side change to the fork job model, batch-copy algorithm, RBAC action, or the archived-room 409 guard — all Step 32's territory; this step only consumes `POST /rooms/:roomId/fork` and `GET /rooms/:roomId/fork-jobs/:jobId` as Step 32 shipped them.
- Members list, invitations, per-member role changes, rename/description/AI-settings/cutoff editing, and the "Delete room" danger zone inside `RoomSettingsDrawer` — all owned by Step 36 (already landed) or Step 37; this step only adds a new, disjoint "Fork room" section to the drawer Step 36 built.
- WebSocket-pushed fork-progress events — this step polls `GET /rooms/:roomId/fork-jobs/:jobId` via a fixed-interval client-side timer/refetch; if a `room_fork_job.progress` WebSocket event type exists by the time this step is implemented, wiring to it instead of polling is a nice-to-have, not required, and must not be assumed to exist.
- Retrying/resuming a `failed` job in place (server-side) — "Try again" starts a brand-new fork (new job, new destination room); Step 32 does not support resuming a partially-copied job.
- Copying room membership, inviting the source room's other members into the fork, or any UI for that — Step 32's `ForkRoom` makes the triggering user the fork's sole member/master; no membership UI is added here.
- Deleting/cleaning up an abandoned or `failed` fork's destination room from the UI — the existing room-delete flow (Step 36) already covers deleting any room the user is `master` of, including an abandoned fork target; no dedicated cleanup affordance is added here.
- Restructuring `ChatRoom.tsx`'s header, `MessageList.tsx`, or the room rail beyond the additive archived-room banner/`MessageInput` conditional described above.
- A dedicated "forked from" indicator/breadcrumb linking a fork back to its `forked_from_room_id` source room — not required by this step's keyScope; only the fork trigger, its progress view, and the destination room's archived treatment are in scope.

  - New (only if the test runner exists): `web/src/features/rooms/components/RoomSettingsDrawer.test.tsx` additions, or a new co-located test file for the fork section if the drawer's existing test file is being kept narrowly scoped.
- Server contract this step consumes (from Step 32, as actually shipped — verify exact field names against the merged `server/internal/interface/handler/dto.go`/`room_fork_handler.go` before wiring):
  ```
  POST /rooms/:roomId/fork                         -> 202 { "job": ForkJobResponse, "new_room": RoomResponse }
  GET  /rooms/:roomId/fork-jobs/:jobId              -> 200 ForkJobResponse
  ForkJobResponse: { id, source_room_id, new_room_id, status: "pending"|"running"|"completed"|"failed",
                     total_messages, copied_messages, error_message, created_at, updated_at }
  ```
  A `403` from `POST /rooms/:roomId/fork` means the caller is not admin/master in the source room (should not be reachable from the UI since the section is already gated by `canManage`, but surface the thrown error via the same inline-error pattern used elsewhere in the drawer if it ever occurs, e.g. a stale role after a concurrent demotion).
  Posting a message into an archived room returns `409`; per Step 32's scope, `MessageInput` is not rendered at all while `room.is_archived` is `true`, so this step's UI should never actually trigger that 409 — it is a defensive backstop, not a path this step needs to specifically handle in the send-error UI.
- Chakra v3 conventions (per `.claude/rules/chakra-ui.md`): use `Progress.Root`/`Progress.Track`/`Progress.Range`/`Progress.ValueText` (compound API) for the copy-progress bar, `Alert.Root`/`Alert.Indicator`/`Alert.Title`/`Alert.Description` for both the archived-room banner in `ChatRoom.tsx` and the failed-job error state in the drawer, and `Link`/`Button` from `@chakra-ui/react` for "Open forked room" (use Next.js `Link` from `next/navigation`/`next/link` for the actual route change, matching the existing `router.push`/`Link` conventions in `RoomSettingsDrawer.tsx` and Step 9's auth hooks). Use the `chakra-ui` MCP server's `get_component_props`/`get_component_example` for `Progress`/`Alert` if their v3 API shape is unclear rather than guessing. This is a small, additive section inside an existing drawer plus one conditional banner — not a new full-page surface — so it does not need to go through the `v0-design` skill; direct implementation is appropriate, consistent with how Step 36 treated its own small, logic-oriented edits.
- Progress percentage math: guard the division (`total_messages > 0 ? copied_messages / total_messages : 0`) since `total_messages` starts at `0` until Step 32's worker calls `forkJobRepo.MarkRunning` with the real count; render an indeterminate/label-only state ("Preparing…") for that brief `pending` window before falling back to the numeric bar.
- Polling cadence and cleanup: whatever interval mechanism is used (TanStack Query `refetchInterval` or a manual `setInterval`), it must stop once `status` is `"completed"` or `"failed"` and must be cleaned up on unmount (drawer closed, or user navigates away mid-fork) to avoid leaking timers/requests after the component is gone.
- Conflict notes: this step's only touch to `RoomSettingsDrawer.tsx` is a new, disjoint "Fork room" section — do not modify the rename/description, AI-settings, cutoff, or danger-zone sections Step 36 already built. Its only touch to `ChatRoom.tsx` is the additive archived-room conditional around `MessageInput`'s render — do not restructure the header (Step 36's territory) or touch `MessageList.tsx`/`MessageInput.tsx`'s own internals (their ownership rotates across other waves per the plan's rotation schedule: 18 → 29 → 38 → 45 → 47/54 — this step is not on that rotation and must not edit those two files' internals, only whether `MessageInput` is rendered at all in `ChatRoom.tsx`).
- English-only code/comments per `CLAUDE.md`; keep every new/edited file `"use client"` consistent with the rest of `web/src/app`/`web/src/features`.
- No `schema.sql`/Atlas changes — this step is purely client-side, consuming endpoints Step 32 already ships.
