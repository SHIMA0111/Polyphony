# Step 55: Ory Hydra OAuth2/OIDC provider + first-party client demo

## Meta
- **Type**: feature
- **Components**: infra, web
- **Wave**: 5 (parallel group — all steps of the same wave can run concurrently)
- **Depends on**: Step 11: Infra: Ory Kratos services in docker-compose | Step 30: Web: Kratos-driven login/registration + auth data-plane flip
- **Unlocks**: Step 56: E2E regression: auth, OAuth/Hydra, rooms, members, invitations, groups
- **Size**: 1 PR (a few hours for one AI agent)

## Context
Phase 15 of `phases.md` requires the app to act as a full OAuth2/OIDC *provider* (not just a consumer of social login, which Step 44 delivers on the same wave), so that third-party or first-party clients can obtain tokens scoped to a Polyphony identity. Step 11 stood up Ory Kratos purely as the identity/session backend, and Step 30 flipped the web app onto Kratos browser flows with a same-origin `ory_kratos_session` cookie. This step adds Ory Hydra as the OAuth2/OIDC authorization server sitting in front of that Kratos session: Hydra owns the `/oauth2/auth`, `/oauth2/token`, and `/userinfo` endpoints and the login/consent "challenge" handshake, while this app's own tiny login/consent route handlers act as Hydra's login/consent provider by checking the existing Kratos session cookie — no new authentication mechanism is introduced, Hydra is purely a protocol layer on top of Kratos. A registered first-party demo client and a scripted authorization-code flow prove the whole chain end to end without requiring any external OAuth app registration.

## Goal
After this PR, `docker compose up` brings up `hydra` (public API `:4444`, admin API `:4445`) backed by its own dedicated Postgres database (`hydra-db`) with migrations applied by a one-shot `hydra-migrate` job — following the exact same three-service pattern Step 11 established for Kratos. Hydra's `urls.login`/`urls.consent` point at two new Route Handlers, `web/src/app/(auth)/oauth/login/route.ts` and `web/src/app/(auth)/oauth/consent/route.ts`, which resolve a Hydra login/consent challenge by checking the caller's Kratos session (via the same `sessions/whoami` contract Step 30's proxy already relies on) and calling Hydra's admin API to accept it — the Kratos identity's UUID becomes the OAuth2 `subject`, and `traits.email`/`traits.username` are attached to the issued ID token. A demo first-party OAuth2 client is registered via a new `task oauth:hydra:register-demo-client` Taskfile task wrapping the Hydra CLI, and a scripted end-to-end test (`ory/hydra/test-oauth-flow.ts`, run via `task oauth:hydra:test`) drives the full authorization-code flow — register a throwaway Kratos user, establish a session, hit Hydra's `/oauth2/auth`, follow the login/consent hops through this app's new routes, capture the issued code at the client's redirect URI, exchange it for tokens at `/oauth2/token`, and call `/userinfo` — asserting the returned claims match the throwaway user. `ory/README.md` documents how to register additional first-party clients with different scopes/redirect URIs.

## Out of scope
- Social login / Kratos-as-OIDC-*consumer* work (`selfservice.methods.oidc`, dex mock, `SocialLoginButtons.tsx`) — that is Step 44 (same wave, disjoint files: Step 44 owns `ory/kratos/kratos.yml`'s OIDC section and the login/register *pages*; this step owns `ory/hydra/` and the new `app/(auth)/oauth/login|consent/*` routes, which Step 44 never touches).
- A `return_to`-chained redirect back into `/oauth/login` after an unauthenticated user completes the existing Kratos login form — if a browser hits `/oauth/login` with no active Kratos session, it is redirected to the plain `/login` page and the user must re-initiate the OAuth authorization request afterward. This step's automated verification always establishes the Kratos session *before* starting the authorization request, so this fast-path limitation does not block verification; threading `return_to` through `LoginForm.tsx` is left to a future step to avoid touching Step 30/44-owned login page files here.
- An actual `/oauth/logout` Route Handler or any Hydra `urls.logout` implementation beyond a placeholder URL in `hydra.yml` — Hydra's own admin API (`revoke oauth2-client-session` / consent revocation) is out of scope; no automated flow in this step exercises logout.
- An interactive consent-screen UI showing requested scopes to the end user — the demo client is first-party and trusted by construction, so `web/src/app/(auth)/oauth/consent/route.ts` auto-grants every requested scope with no rendered page; a real per-scope consent UI is a future concern if/when third-party clients are supported.
- Registering more than one demo client, or any real third-party OAuth application — only one demo client is created by this step's Taskfile task; the README documents (but this step does not execute) registering additional clients.
- Wiring `HYDRA_ADMIN_URL`/`HYDRA_PUBLIC_URL` onto the `web-e2e`/`api-e2e` Docker Compose test-profile services, and any Playwright-based Hydra spec — this step has no dependency edge on Step 10's E2E harness and verifies purely via the scripted `ory/hydra/test-oauth-flow.ts` against the plain dev-profile stack (ports 3000/4444/4445); Step 56 (E2E regression, which does depend on Step 10) is the first step permitted to add a browser-automation Hydra spec and to extend the e2e-profile compose services accordingly.
- Any change to `server/` (Go) or `llm-gateway/` (Rust) code — Hydra-issued tokens are not yet consumed by the Go API in this step; validating a Hydra access token as an alternative auth mechanism on `server/internal/interface/middleware/auth.go` is not part of this step's scope (the Go API continues to authenticate exclusively via the Kratos session cookie / `AuthService`, unaffected by Hydra's existence).
- Any `schema.sql`/Atlas migration — Hydra owns its schema entirely inside `hydra-db` via its own `hydra migrate sql` tool, independent of Atlas, matching `dbChanges: ""`.
- Refresh-token rotation policies, JWT (vs. opaque) access tokens, dynamic client registration, or client-credentials/device-code grants — none of `phases.md` Phase 15 requires them; the demo client uses the standard authorization-code + refresh-token grant only.
- Redis-backed Hydra login/consent session caching — Phase 10/later-wave territory, not touched here.
- Any change to `ory/kratos/kratos.yml`, `ory/kratos/identity.schema.json`, or Kratos's own service definition — this step only *reads* the existing Kratos session via `sessions/whoami`; it does not modify Kratos configuration.

## Implementation notes
- **Reference files to read before editing**: `docker-compose.yml` (the `kratos`/`kratos-db`/`kratos-migrate` triplet from Step 11 is the exact template — same `depends_on`/healthcheck/volume-mount pattern to replicate for `hydra`/`hydra-db`/`hydra-migrate`; the `web` service block, to find where `KRATOS_PUBLIC_URL` was added by Step 30 so the new `HYDRA_ADMIN_URL` line sits alongside it), `ory/kratos/kratos.yml` and `ory/README.md` (Step 11's config-templating and docs conventions to mirror for Hydra), `.env.example` (existing `# === Ory Kratos ===` section header style), `web/src/app/api/kratos/[...path]/route.ts` and `web/src/features/auth/api/get-session.ts` (Step 30 — the exact `sessions/whoami` request shape and cookie-forwarding pattern that `web/src/lib/kratos-session.ts` reuses in a new, standalone module), `web/src/middleware.ts` (Step 30 — confirm `/oauth/*` paths are not accidentally caught by the `(main)`/`(auth)` route-group auth guard; the new routes live under `app/(auth)/oauth/*` but are unauthenticated-by-design API-shaped routes, not pages, so they must not be redirected by the middleware — verify the middleware's matcher/path logic and, if it would intercept `/oauth/login` or `/oauth/consent`, add them to its existing public-path allowlist rather than restructuring the middleware).
- **Hydra config-via-env convention**: identical to Kratos's — `hydra.yml` contains only non-secret static settings (`serve`, `oauth2`, `urls.self.issuer`/`urls.login`/`urls.consent`/`urls.logout` as documented defaults, `strategies`, `ttl`); `DSN`, `SECRETS_SYSTEM`, and any override of `URLS_SELF_ISSUER`/`URLS_LOGIN`/`URLS_CONSENT` are supplied as container `environment:` entries in `docker-compose.yml`, using Ory's uppercase-dot-to-underscore env-var-to-config-key mapping (the same mechanism Step 11's implementation notes documented for `kratos.yml`).
- **Hydra Admin API v2 shapes** (verify exact paths/fields against the pinned image's own OpenAPI/`--help` output if they've drifted): `GET /admin/oauth2/auth/requests/login?login_challenge=` → `{ skip, subject, client, requested_scope, ... }`; `PUT /admin/oauth2/auth/requests/login/accept?login_challenge=` body `{ subject, remember?, remember_for?, context? }` → `{ redirect_to }`; `GET /admin/oauth2/auth/requests/consent?consent_challenge=` → `{ skip, subject, client, requested_scope, requested_access_token_audience, ... }`; `PUT /admin/oauth2/auth/requests/consent/accept?consent_challenge=` body `{ grant_scope, grant_access_token_audience, session?: { access_token?, id_token? }, remember?, remember_for? }` → `{ redirect_to }`. Public API: `GET /oauth2/auth` (authorize), `POST /oauth2/token` (token exchange, `client_secret_basic` via HTTP Basic auth), `GET /userinfo`, `GET /.well-known/openid-configuration`.
- **Why consent is fully automatic here**: the only registered client is this app's own first-party demo client (created by `task oauth:hydra:register-demo-client`), so there is no untrusted third party whose scope grants a human must review — `web/src/app/(auth)/oauth/consent/route.ts` therefore always grants exactly the scopes Hydra reports as `requested_scope` and never renders a page. If a real third-party client is registered later, a proper consent screen becomes necessary before Hydra should be considered safe for non-first-party clients — flagged in Out of scope, not solved here.
- **Cookie handling in `test-oauth-flow.ts`**: Bun/Node's `fetch` does not maintain a cookie jar automatically across requests the way a browser does; the script must read every `Set-Cookie` response header (there may be several per hop — both the app's Kratos session cookie and Hydra's own internal login/consent-challenge session cookie) and re-attach them as a single `Cookie:` request header on the next hop, exactly the same "no browser, manual redirect + cookie bookkeeping" technique `curl -c/-b cookiejar` would use, chosen here as a Bun script instead of a shell script per this project's bun-first tooling preference.
- **Chakra UI v3 conventions do not apply to this step** — no JSX/UI is added; both new files under `app/(auth)/oauth/*` are plain Route Handlers (`route.ts`), not pages.
- **Conflict notes**: `docker-compose.yml`/`Taskfile.yml` edits are additive-only new blocks/tasks (per the `chakra-ui.md`-independent project convention already exercised by steps 6/10/11/12/31/44/49) — this step's three new service blocks and two new Taskfile tasks touch no line of any existing block/task. `ory/README.md` gains a new, disjoint "OAuth2/OIDC provider (Hydra)" section; Step 44 (same wave) independently adds its own disjoint "Social login (OIDC)" section to the same file — both are additive Markdown sections with no expected line overlap, but if both PRs are rebased close together a trivial non-conflicting merge of two appended sections may be needed. This step's only web-side files are new (`web/src/lib/kratos-session.ts`, `web/src/lib/hydra-admin.ts`, `web/src/app/(auth)/oauth/login/route.ts`, `web/src/app/(auth)/oauth/consent/route.ts`) — it does not edit `LoginForm.tsx`, `RegisterForm.tsx`, `kratos.yml`, or any file Step 44 owns, matching the plan's same-wave boundary.
