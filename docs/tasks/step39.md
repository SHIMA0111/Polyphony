# Step 39: Vision multimodal plumbing: gateway content-parts mapping + Go DTOs

## Meta
- **Type**: feature
- **Components**: llm-gateway, server
- **Wave**: 5 (parallel group — all steps of the same wave can run concurrently)
- **Depends on**: Step 12: Server: MinIO object storage + attachments + presigned upload endpoints | Step 25: Rust: Anthropic provider adapter | Step 26: Rust: Gemini provider adapter
- **Unlocks**: Step 45: Web: image upload + attachment UI + Vision send
- **Size**: 1 PR (a few hours for one AI agent)

## Context
Phase 12 of `phases.md` requires the AI to perform image recognition (Vision) on uploaded attachments. Step 12 already lands MinIO storage, the `message_attachments` table, and presigned upload endpoints; Steps 25/26 already give the gateway Anthropic and Gemini adapters alongside the existing OpenAI adapter. None of the three providers can yet accept image content — `CompletionRequest.messages` is `Vec<ChatMessage>` with a plain `String` content field, and the Go side has no notion of attachments flowing into an AI request at all. This step lands the shared multimodal data model end-to-end (Go message-attachment lookup → REST/gRPC DTOs → gateway domain model → per-provider request mapping) so Step 45 only has to build the upload/preview UI on top of an already-working pipeline.

## Goal
After this PR, a chat message that has one or more image attachments can be sent through `POST /rooms/:roomId/messages/ai` (and its gRPC equivalent, if already wired) and the resulting `ai.CompletionRequest` carries typed content parts (text + image) instead of a flat string. The LLM Gateway's `CompletionRequest`/`ChatMessage` domain model represents content as `MessageContent::Text(String) | MessageContent::Parts(Vec<ContentPart>)`, and each of the three providers (OpenAI, Anthropic, Gemini) maps `ContentPart::Image` into its own Vision request shape (OpenAI `image_url`, Anthropic `image` source block with base64, Gemini `inline_data`/`file_data` part) inside that provider's own `request.rs` submodule. Text-only requests are unaffected (existing behavior and existing tests keep passing unmodified). Every provider's mapping is covered by a wiremock-backed test that asserts the exact JSON body sent for an image-bearing request.

## Scope
- [x] **Gateway domain model** (`llm-gateway/src/domain/model.rs`): reuse the `MessageContent` enum Step 3 already landed — `MessageContent::Text(String) | MessageContent::Parts(Vec<ContentPart>)` with `ContentPart::Text(String) | ContentPart::ImageUrl(String) | ContentPart::ImageBase64 { media_type, data }` and the existing `as_text()` helper. `ChatMessage.content` is already `MessageContent` after Step 3 — do not redefine or reshape it (in particular, do not introduce a divergent `ContentPart::Image(ImageSource)` wrapper); only extend it (with rustdoc) if a genuinely missing variant is needed for a provider mapping.
- [x] **REST DTOs** (`llm-gateway/src/adapters/inbound/rest/request.rs` and `response.rs`): extend `MessageDto`/response `MessageDto` so `content` accepts either a plain JSON string (backward compatible, maps to `MessageContent::Text`) or an array of part objects `{"type":"text","text":"..."}` / `{"type":"image_url","image_url":{"url":"..."}}` / `{"type":"image_base64","media_type":"...","data":"..."}` (mirrors OpenAI's `content` union shape, since that's the closest existing convention already visible in `to_openai_request`/`from_openai_response`). Use `#[serde(untagged)]` on an internal `ContentDto` enum to accept both shapes; convert to/from `MessageContent` in `into_domain()` / `From<CompletionResponse>`.
- [x] **gRPC DTOs**: if the gRPC inbound adapter/proto exists in the repo by this point (landed by an earlier wave-3/4 step per the plan's gRPC swap point), extend the `.proto` message type for chat messages with an equivalent `oneof content { string text = N; ContentParts parts = N+1; }` shape and regenerate/hand-update the generated bindings plus the DTO⇄domain mapping. If no gRPC adapter file exists yet in this checkout, skip this bullet and note it as not-yet-applicable in the PR description — do not scaffold gRPC from scratch here (out of scope, belongs to the gRPC step).
- [x] **Per-provider request mapping** — each provider's own `request.rs` submodule (this step owns request.rs across all three providers; do not touch `stream.rs`):
  - `llm-gateway/src/adapters/outbound/openai/request.rs`: map `ContentPart::Text`/`ImageUrl`/`ImageBase64` to OpenAI's array-of-parts message content (`{"type":"text","text":...}` / `{"type":"image_url","image_url":{"url":...}}`, using a `data:{media_type};base64,{data}` URL for `ContentPart::ImageBase64`). Text-only messages keep serializing as a plain string (OpenAI accepts both).
  - `llm-gateway/src/adapters/outbound/anthropic/request.rs`: map to Anthropic's content-block array (`{"type":"text","text":...}` / `{"type":"image","source":{"type":"base64","media_type":...,"data":...}}` for `ContentPart::ImageBase64`; for `ContentPart::ImageUrl`, fetch-and-inline is out of scope for this step — pass through as an Anthropic `{"type":"image","source":{"type":"url","url":...}}` block if the Anthropic API version already in use by Step 25 supports URL sources, otherwise return `DomainError::InvalidRequest` documented in rustdoc; pick whichever matches what Step 25 actually implemented and document the choice).
  - `llm-gateway/src/adapters/outbound/gemini/request.rs`: map to Gemini's `parts` array (`{"text":...}` / `{"inline_data":{"mime_type":...,"data":...}}` for `ContentPart::ImageBase64`; `{"file_data":{"file_uri":...}}` for `ContentPart::ImageUrl`).
  - Each mapping function has rustdoc documenting the shape and the `# Errors` it can return.
- [x] **Domain error**: if any provider cannot represent a given `ContentPart` variant, return the existing `DomainError::InvalidRequest(String)` (`llm-gateway/src/domain/error.rs`) — no new error variant needed unless a provider genuinely needs one, in which case document why in rustdoc.
- [x] **Go: attachment lookup + part building**:
  - Add an `ai.MessageContent`/`ai.ContentPart` shape to `server/internal/domain/ai/dto.go` (or the file currently holding `ChatMessage`/`CompletionRequest`) mirroring the gateway's enum via a tagged struct (`Type string; Text string; ImageURL string; ImageBase64 *ImageBase64Data`), replacing `ChatMessage.Content string` with a field that can hold either — keep a `Content string` convenience field only if it can stay backward compatible, otherwise introduce `Parts []ContentPart` alongside `Content` and require exactly one to be set (document the invariant in the GoDoc comment).
  - In `server/internal/usecase/message/usecase.go`, extend the context-assembly path used by both `SendAIMessage` and `RegenerateAIMessage` — note that Step 23 replaced the old `buildChatMessages` helper with the frozen `ai.ContextBuilder.Build` interface, whose signature must NOT change; add the attachment enrichment as a post-`Build` step in the usecase (or a small wrapper around the builder output) that looks up attachments per message via the attachment repository introduced in Step 12 and, when a message has one or more image attachments, upgrades that message's entry to a `Parts` payload: the message's text (if any) as a text part, followed by one image part per attachment using the attachment's presigned/public URL (reuse Step 12's presigned-URL issuance helper rather than re-deriving S3 URLs here). Messages with no attachments keep going through the plain-`Content` path unchanged.
  - Update `server/internal/interface/gateway/llm_client.go`'s `completionReqDTO`/`chatMsgDTO` to serialize the new content shape to the gateway's REST contract (matching the `#[serde(untagged)]` shape landed above) so `Complete` continues to round-trip correctly.
  - GoDoc on every new/changed exported symbol per `CLAUDE.md` conventions.
- [x] **Tests**:
  - Rust: unit tests in each provider's `request.rs` for `MessageContent::Text` (unchanged behavior) and `MessageContent::Parts` with a mix of text + image parts (both `Url` and `Base64` sources where supported), asserting the exact serialized JSON body — extend the existing `#[cfg(test)] mod tests` pattern already used in `openai.rs`.
  - Rust: add wiremock-backed integration tests (add `wiremock` to `[dev-dependencies]` in `llm-gateway/Cargo.toml` if not already present from Steps 25/26) per provider that stub the provider's completion endpoint, send a `CompletionRequest` with an image part, and assert the mock received the expected multimodal JSON body.
  - Go: unit tests for the attachment-enrichment/context-assembly path in `server/internal/usecase/message/usecase_test.go` covering a message with zero attachments (plain content, unchanged) and a message with one/multiple image attachments (parts built correctly), using the existing hand-written mock pattern already used in that test file.
  - Go: unit test for the updated `completionReqDTO` marshaling in `server/internal/interface/gateway/llm_client_test.go` (create if it doesn't exist) asserting the JSON shape sent to the gateway for a parts-bearing request.

- Conflict boundary (per plan-wide notes): this step owns each provider's `request.rs` submodule plus the shared content-part DTO/enum files (`domain/model.rs`, `adapters/inbound/rest/request.rs`, `adapters/inbound/rest/response.rs`) for this wave. - Reference the OpenAI adapter's conversion pattern (`to_openai_request`/`from_openai_response` in `llm-gateway/src/adapters/outbound/openai/request.rs` post-Step-3) as the template for how request/response mapping and its unit tests are structured; replicate that shape in the new `request.rs` files.
