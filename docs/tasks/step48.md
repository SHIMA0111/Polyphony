# Step 48: Web: token balance + usage history UI

## Meta
- **Type**: ui
- **Components**: web
- **Wave**: 5 (parallel group — all steps of the same wave can run concurrently)
- **Depends on**: Step 10: Playwright E2E harness + seeded compose test stack + LLM stub | Step 16: Web persistent sidebar chat layout | Step 42: Server: token balance management
- **Unlocks**: Step 59: E2E regression: billing and room fork
- **Size**: 1 PR (a few hours for one AI agent)

## Context
`phases.md` Phase 16 ("Token Balance Management") requires that AI usage debit a per-user balance, that the balance be checked before every AI request, and that an insufficient-balance condition is surfaced as a clear error rather than a silent failure or a generic 500. Step 42 lands the server side of this (balance read endpoint, a paginated usage/transaction history endpoint, and a pre-call balance guard in the `SendAIMessage` usecase that returns HTTP 402 when the room master's balance cannot cover the request), but today nothing in `web/` shows a balance anywhere, there is no usage history view, and `web/src/features/messages/components/MessageInput.tsx`'s `onSendWithAI` handler has no error path at all beyond a bare `try`/`finally` in `ChatRoom.tsx` (a rejected promise currently vanishes with a `// TODO: handle error` comment). This step closes that gap: a balance widget always visible in the room chrome, a browsable usage history page, and a specific, user-legible error state when an AI send is rejected for insufficient balance — without touching subscription purchase flows, which belong to Step 53 (Stripe billing UI) once Phase 17 lands.

## Goal
After this PR, every room view shows the current token balance in the persistent top bar introduced by Step 16 (`web/src/app/(main)/layout.tsx`), a new `/billing/usage` page lists the user's token transaction/usage history with cursor pagination, and attempting to send an AI message when the room master's balance is insufficient surfaces a distinct, actionable inline error in `MessageInput.tsx` (not a generic failure) instead of silently discarding the rejected request. A new Playwright spec proves both the balance display and the 402 error path against the Step 10 harness's seeded/zero-balance fixture user.

## Implementation notes

**Assumed contracts from Step 42** (adapt field/path names if the actual implementation differs slightly, but keep the shapes below as the working assumption since no earlier step doc pins them down further):
```
GET /billing/balance                         -> 200 { "user_id", "balance", "updated_at" }
GET /billing/transactions?cursor=&limit=     -> 200 { "transactions": [{ "id","user_id","room_id","type","amount","balance_after","description","created_at" }], "next_cursor" }
POST /rooms/:roomId/messages/ai              -> 402 { "message": "insufficient token balance" }   (existing endpoint, Step 42 adds the pre-call guard; no path change)
```
`balance`/`amount`/`balance_after` are plain numbers (token counts, not currency) per Phase 16's "Token consumption recording, balance check" scope — do not format them as currency.
