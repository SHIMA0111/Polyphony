# Step 5: Web vitest + RTL unit-test harness + MSW mock layer

## Meta
- **Type**: testing
- **Components**: web
- **Wave**: 1 (parallel group — all steps of the same wave can run concurrently)
- **Depends on**: None
- **Unlocks**: Step 9: Web data layer migration: TanStack Query, RSC prefetch, per-feature API modules
- **Size**: 1 PR (a few hours for one AI agent)

## Context
`web/package.json` currently has zero test tooling — no `test` script, no Vitest/Jest, no React Testing Library, no MSW — so every component and hook in `web/src/features/**` and `web/src/hooks/**` (e.g. `web/src/features/rooms/components/RoomList.tsx`, `web/src/hooks/use-auth.ts`) has shipped untested since Phase 1. `CLAUDE.md`'s testing conventions call for unit tests across every component, and the plan's wave-1/2/3 harness principle requires this harness to exist before feature work resumes so later steps "ship tests cheaply" instead of each inventing its own test setup. This step is deliberately auth-agnostic: `web/src/hooks/use-auth.ts` is rewritten by Step 4 in this same wave (httpOnly-cookie BFF auth), so any harness code that tested today's `localStorage`-based `useAuth` would be thrown away immediately — auth/session tests are explicitly deferred to Step 9, which lands after the cookie rewrite has settled. Instead, this step pins its MSW handlers to the `/api/proxy/*` BFF proxy path contract that Step 4 introduces (`app/api/proxy/[...path]/route.ts`, a catch-all that forwards the same path suffixes `web/src/lib/api.ts`'s `RealApiClient` already uses today — e.g. `/rooms`, `/rooms/:roomId/messages`, `/models` — to the Go API with a Bearer header), so the harness and its handlers are correct on day one regardless of merge order within the wave, and Step 9 only has to migrate call sites onto these already-correct handlers rather than rewrite them.

## Goal
`web/` has a working Vitest + React Testing Library unit-test setup runnable via `bun run test` (and `task test:web` from the repo root): a `vitest.config.ts` with a `jsdom` environment and the `@/*` path alias resolved the same way `tsconfig.json` resolves it; a shared test-setup file wiring `@testing-library/jest-dom` matchers, RTL `cleanup`, jsdom polyfills real components in this repo need (`scrollIntoView`, `matchMedia`), and MSW server lifecycle hooks; an MSW mock layer with both a Node `setupServer` (used by Vitest) and a browser `setupWorker` (for future interactive/dev-mode mocking), sharing one `handlers.ts` whose routes are pinned to the `/api/proxy/*` contract Step 4 will introduce — not to `web/src/lib/api.ts`'s current absolute `http://localhost:8080` paths. Two auth-agnostic example tests prove the harness end-to-end: one pure-component RTL test (props in, DOM/callback out, no network) and one MSW-backed data-fetching-hook test (a small new example hook that fetches from `/api/proxy/rooms`, showing the loading → success and loading → error paths against the MSW handlers). No `use-auth`/session test is added here; Step 9 adds that after Step 4's cookie rewrite lands.

## Implementation notes
- Path alias: mirror `web/tsconfig.json`'s `compilerOptions.paths` (`"@/*": ["./src/*"]`) in `vitest.config.ts`'s `resolve.alias` using `node:path` (`path.resolve(__dirname, "./src")`) — Vitest does not read `tsconfig.json` paths automatically without a plugin, and this step intentionally avoids adding `vite-tsconfig-paths` as an extra dependency when a two-line manual alias suffices.
- `web/src/components/ui/provider.tsx` already exists and is the correct wrapper to reuse in `web/src/test/render.tsx` — do not hand-roll a second `ChakraProvider value={defaultSystem}` wrapper.
- `web/src/features/messages/components/MessageList.tsx` is the chosen pure-component target because its props (`messages: Message[]`, `onRegenerate`, `isRegenerating`) are fully self-contained (see `web/src/types/api.ts` for the `Message` shape) — it has no `useState`/network/auth dependency, only a `useEffect` calling `scrollIntoView` (hence the polyfill in `setup.ts`). Avoid `ModelSelector.tsx` or `CreateRoomForm.tsx` as the "pure" example: the former's Chakra `Popover`/`Portal` combination and the latter's direct `apiClient.createRoom` network call add jsdom/portal or network complexity this example test is meant to avoid.
- MSW route contract: base every handler path on the exact suffix `web/src/lib/api.ts`'s `RealApiClient.request` calls already use today (e.g. `/rooms/${roomId}/messages/${messageId}/regenerate`), just prefixed with `/api/proxy` — do **not** reuse `RealApiClient`'s current `API_BASE_URL` (`http://localhost:8080`) anywhere in the test handlers; that absolute-URL, direct-to-Go-API path is what Step 9 removes when it migrates call sites onto the BFF proxy.
- Fixture shapes must satisfy the interfaces in `web/src/types/api.ts` exactly (`AuthResponse`, `Room`, `Message`, `MessagePage`, `AIMessageResponse`, `ModelInfo`/`ModelListResponse`) — reuse those types when typing handler response bodies (`HttpResponse.json<Room[]>(...)`) so a future type change surfaces as a handler compile error.
- Chakra UI usage in any new/modified `.tsx` file under `web/src/features/**/components/**` or `web/src/test/render.tsx` must follow `.claude/rules/chakra-ui.md`'s import-priority rules (prefer `@chakra-ui/react` compound components; only use existing `@/components/ui/*` snippets, never add new ones in this step).
- English-only comments/TSDoc per `CLAUDE.md`; the new `useRooms()` hook should carry a TSDoc block explaining its narrow, temporary purpose (see Scope) so a future reader does not mistake it for the intended long-term data-fetching pattern.
- `Taskfile.yml` conflict note: this step's only edit is the additive `test:web` task plus appending `test:web` to the root `test:` task's `deps` list — later waves' steps that touch `docker-compose.yml`/`Taskfile.yml` (per the plan's shared "additive, alphabetized service blocks" convention) add their own new blocks and should not need to touch this step's `test:web` block; do not reorder or reformat unrelated existing tasks while editing.
- `package.json` dependency additions are purely additive (`devDependencies` only) and do not touch any `dependencies` entries Step 4 might also touch in the same wave, so the two PRs' `package.json` diffs should merge cleanly; if `bun.lock` conflicts on merge, resolve by re-running `bun install` rather than hand-editing the lockfile.
