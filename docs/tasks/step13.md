# Step 13: Go 5-tier RBAC domain + authorization middleware + ModelUsecase

## Meta
- **Type**: refactor
- **Components**: server
- **Wave**: 3 (parallel group — all steps of the same wave can run concurrently)
- **Depends on**: Step 2: Go test infrastructure: testcontainers helper + shared mocks; Step 7: Go event-driven messaging core: MessageHub, atomic sequences, response linkage
- **Unlocks**: Step 21: Server: room invitations; Step 22: Server: member management, leave, role change, ownership transfer; Step 23: Server: AI context control (soft delete, exclude flag, cutoff, context builder); Step 24: Server: per-room AI provider/model settings; Step 32: Server: room fork (async batch copy); Step 42: Server: token balance management
- **Size**: 1 PR (a few hours for one AI agent)

## Context
`room_members.role` is currently a free-form `VARCHAR(50)` with no validation anywhere in the stack — `RoomRepository.Create` hardcodes the owner's role to `'master'` (`internal/interface/repository/postgres/room_repository.go`), test fixtures use ad-hoc strings like `"owner"` and `"member"` (`internal/usecase/room/usecase_test.go`, `internal/interface/handler/mock_test.go`), and there is no code path that ever checks a non-owner member's role at all. `RoomUsecase` (`internal/usecase/room/usecase.go`) and `MessageUsecase` (`internal/usecase/message/usecase.go`) each hand-roll an identical `checkMembership` helper that only proves membership, never authorization level, and `ModelHandler` (`internal/interface/handler/model_handler.go`) calls `ai.LLMGateway` directly from the handler layer, skipping the usecase layer that Clean Architecture (per `CLAUDE.md`) requires. Phases 4 and 11 of `phases.md` call for a full reader → guest → member → admin → master hierarchy (reader: view only; guest: send messages but cannot invoke AI; member: send + invoke AI; admin: manage members but cannot delete the room; master: full control including delete/ownership). This step lands that hierarchy as a typed domain enum plus a single reusable authorization primitive so that every later RBAC-consuming step (invitations, member management, AI context control, provider settings, room fork, token balances) can depend on one settled contract instead of re-deriving permission rules.

## Goal
`room.Role` is a typed 5-value enum (`reader`, `guest`, `member`, `admin`, `master`) with ordering/capability helper methods, backed by a DB `CHECK` constraint restricting `room_members.role` to those five values. A single reusable authorization helper (used as Echo middleware and/or as a usecase-layer guard) enforces the four documented rules — reader is read-only, guest cannot invoke AI, admin can manage members but not delete the room, master has full control — replacing the duplicated `checkMembership` methods in `RoomUsecase` and `MessageUsecase` with role-aware checks built on the same helper. `ModelHandler` no longer holds `ai.LLMGateway` directly; a thin `ModelUsecase` wraps `ai.LLMGateway.ListModels` and the handler calls the usecase instead. `RoomResponse` gains a `role` field carrying the requesting user's role in that room, giving Web Frontend and later steps a stable place to read permission level from.

  - `func (r Role) IsValid() bool`
  - `func (r Role) AtLeast(min Role) bool` — true if `r`'s rank is >= `min`'s rank
  - `func (r Role) Allows(action Action) bool` — capability check (see below)

## Implementation notes
- Follow Clean Architecture layering per `CLAUDE.md`: `internal/domain/room/role.go` must have zero imports beyond the standard library (no `echo`, no `pgx`). The middleware in `internal/interface/middleware/rbac.go` and the shared `Authorize` helper are the only places that translate `Role`/`Action` into HTTP-facing or usecase-facing decisions.
- Existing error-mapping conventions to preserve: `handleRoomError` and `handleMessageError` in `internal/interface/handler/room_handler.go` / `message_handler.go` already map `domain.ErrForbidden` → 403 and `domain.ErrNotFound` → 404; the new authorization checks should keep returning `domain.ErrForbidden` (never a new error type) so these existing handler-level mappers keep working unchanged.
- `internal/interface/middleware/auth.go` already establishes the pattern this step should mirror for `rbac.go`: a constructor returning `echo.MiddlewareFunc`, an unexported context key, and a `Get*` accessor if state needs to flow to downstream handlers (in this case none is needed — `RequireRole` only gates, it does not need to publish the loaded `RoomMember` into context, since usecases reload it themselves via the shared helper).
- Current duplicated mock room repositories in `internal/usecase/room/usecase_test.go` (`mockRoomRepo`) and `internal/interface/handler/mock_test.go` (`mockRoomRepoForHandler`) are near-identical hand-written mocks; Step 2 introduces shared test mocks — use that shared mock location (extending it with `Role`-typed fixtures) instead of re-duplicating the maps-of-maps pattern a third time in `rbac_test.go` and `usecase/message/usecase_test.go`. If Step 2's shared mock package name differs from what's assumed here, adapt to whatever it actually exports, but do not reintroduce a third hand-copied mock.
- Schema/migration convention (see `CLAUDE.md` and the plan's schema convention): edit `server/schema.sql` additively (only the `room_members` table's `CHECK` constraint in this step), then run `task migrate:generate -- add_room_members_role_check` from the repo root — this shells into `server/` and runs `atlas migrate diff <name> --env local` per `Taskfile.yml`, producing a new file in `server/migrations/` alongside the existing `20260220060722_initial.sql` and updating `server/migrations/atlas.sum`. Do not hand-edit `atlas.sum`.
- `ModelUsecase` is intentionally thin in this step (delegate-only) — do not add caching, filtering, or per-room model lists here; that's Step 24's job. Keep `internal/domain/ai/gateway.go` and `internal/domain/ai/entity.go` untouched.
- `RoomResponse.Role` should serialize as the plan's `Role` type's underlying string value (e.g. `"master"`), not a numeric rank, so the web frontend can do plain string comparisons/permission checks later.
- Conflict note: this step is serialized after Step 7 because both rework the message/room usecase files (`internal/usecase/message/usecase.go`, `internal/usecase/room/usecase.go`); rebase onto Step 7's merged state before editing `checkMembership` call sites. Other Wave 3 steps in flight touch different tables/files and should not conflict with `room_members`' schema or the usecase files this step edits.
