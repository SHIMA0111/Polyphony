# Step 15: Server WebSocket endpoint + realtime delivery

## Meta
- **Type**: feature
- **Components**: server
- **Wave**: 3 (parallel group — all steps of the same wave can run concurrently)
- **Depends on**: Step 7: Go event-driven messaging core: MessageHub, atomic sequences, response linkage
- **Unlocks**: Step 31: Redis in compose + RedisHub MessageHub swap; Step 35: Web WebSocket client + live cache merge; Step 41: Server: private AI mode; Step 51: Go: consume gateway stream + WS chunk forwarding
- **Size**: 1 PR (a few hours for one AI agent)

## Context
Step 7 gives `MessageUsecase` an event-driven core (`domain/event.MessageHub`, `RoomEvent`, `InProcessHub`) that publishes `message_created`/`message_updated` events after every successful write, but nothing in the Go API ever subscribes to it — clients today only see new messages by polling `GET /rooms/:roomId/messages`. This step adds the missing transport: an authenticated, membership-gated WebSocket endpoint that streams `RoomEvent`s to connected clients as JSON frames in real time. Because browsers cannot attach custom headers (like `Authorization: Bearer ...`) to a WebSocket handshake request, authentication for the upgrade itself cannot reuse the existing `JWTAuth` middleware directly; instead, an already-authenticated REST endpoint mints a short-lived, server-signed "ticket" that the client passes as a query parameter on the WebSocket URL. This ticket mechanism is deliberately built directly on top of the already-authenticated request's user ID (via the existing `middleware.GetUserID` helper) rather than on `auth.AuthService`, so it keeps working unchanged whether the underlying session token was issued by `SimpleJWTService` today or by Ory Kratos after the Phase 9 swap (Step 20/30) — nothing in this step imports `domain/auth`. This matches Phase 2 of `phases.md` and is the foundation the Web WebSocket client (Step 35), Redis-backed hub swap (Step 31), private AI mode (Step 41), and streaming chunk forwarding (Step 51) all build on.

## Goal
After this PR, an authenticated user can call `POST /ws/ticket` to obtain a short-lived ticket, then open `GET /rooms/:roomId/ws?ticket=<ticket>` to establish a WebSocket connection scoped to that room. The handshake validates the ticket, confirms the user is a member of the room (reusing the existing membership check, not the new RBAC middleware being built in parallel by Step 13), and on success upgrades the connection and subscribes it to `MessageHub.Subscribe(ctx, roomID, userID)`. Every `RoomEvent` published for that room — filtered by the hub itself according to `TargetUserIDs` for per-user-targeted delivery — is forwarded to the client as a JSON frame `{"type": "...", "room_id": "...", "message": {...}}` using the existing `MessageResponse` DTO shape. Disconnection (client close, network drop, or context cancellation) cleanly unsubscribes from the hub. Two clients connected to the same room both receive a broadcast event; a targeted event (`TargetUserIDs` set) is delivered only to the matching client. Unit tests cover the ticket issuer and handshake failure paths; an integration-style test (real HTTP server, two real WebSocket clients, one room) proves both broadcast and per-user-targeted delivery.

## Implementation notes
- **Reuse, don't duplicate membership checks.** `RoomUsecase.GetRoom(ctx, userID, roomID)` (`server/internal/usecase/room/usecase.go`) already enforces "only members can access it" and already maps a non-member (or non-existent room) to `domain.ErrForbidden` via its `checkMembership` helper (see `errors.Is(err, domain.ErrNotFound) → domain.ErrForbidden` at the bottom of that file). **Call it only for its error return and ignore the returned room value** (`_, err := h.roomUsecase.GetRoom(ctx, userID, roomID)`). This is deliberate: Step 13 runs in the same wave and may change `GetRoom`'s return type to a role-aware wrapper (`RoomWithRole`) as part of landing the RBAC model; by never touching the returned value, this handler keeps compiling regardless of which of the two same-wave steps merges first, with zero coordination needed.
- **Ticket independence from `AuthService` is the whole point.** `wsticket.Issuer` must not import `domain/auth` or `auth.AuthService`. It only needs a `userID string`, which `IssueTicket` obtains from the already-validated request context via the existing `middleware.GetUserID(c)` (`server/internal/interface/middleware/auth.go`) — that middleware itself already works uniformly across `SimpleJWTService` today and `KratosAuthService` after the future swap, because `JWTAuth` depends on the `auth.TokenValidator` interface, not a concrete implementation. This step's ticket layer sits one level below that abstraction and never needs to change when the swap happens.
- **`coder/websocket` API shape** (verify against the version `go get` resolves, but the stable public API has been consistent): `websocket.Accept(w http.ResponseWriter, r *http.Request, opts *websocket.AcceptOptions) (*websocket.Conn, error)`; Echo's `c.Response()` implements `http.ResponseWriter` (and the underlying `http.Hijacker` needed for the upgrade) and `c.Request()` gives the `*http.Request` — both work directly with `Accept`. Use `github.com/coder/websocket/wsjson` for `wsjson.Write(ctx, conn, v any) error` / `wsjson.Read(ctx, conn, v any) error` to avoid hand-rolling JSON framing. `conn.CloseRead(ctx) context.Context` is the documented idiom for connections that only ever push data to the client (never expect client-sent application messages) — it starts a background reader that answers pings/handles close frames and returns a derived context that's canceled when the peer disconnects; drive your event-forwarding loop off that derived context rather than writing your own read loop.
- **Origin check.** `websocket.Accept` rejects cross-origin upgrades by default unless `AcceptOptions.OriginPatterns` is set. Derive patterns from `cfg.CORSOrigins` (already loaded, comma-separated full origin URLs, e.g. `http://localhost:3000`) by stripping the scheme to get `host[:port]` patterns (`net/url.Parse` each entry, use `.Host`) — do not set `InsecureSkipVerify: true`.
- **Frame envelope naming.** Use the field name `message` for the `MessageResponse` payload in this step's frames (`{"type": "...", "room_id": "...", "message": {...}}`). Keep the envelope's top two fields (`type`, `room_id`) as the stable contract; Step 51 is expected to add new `type` values (e.g., an AI streaming chunk type) that may carry a different payload key alongside this same envelope — that's fine and requires no redesign here, only additive JSON fields later.
- **Existing conventions to follow**: `handleMessageError`/`handleRoomError`-style error-to-status mapping (see `server/internal/interface/handler/message_handler.go`'s `handleMessageError`) — mirror that pattern for `Handle`'s pre-upgrade error responses rather than inventing a new error-response shape; reuse the existing `ErrorResponse{Message: "..."}` DTO (`server/internal/interface/handler/dto.go`) for all `401`/`403`/`404`/`500` JSON bodies emitted *before* the upgrade succeeds (nothing can be written as a JSON body after `websocket.Accept` succeeds — the connection has switched protocols).
- **DI wiring reality check.** As of this writing `server/cmd/api/main.go` constructs everything directly in `main()` (see the file for the exact current shape); Step 1 is expected to have introduced a DI container/registrar split before this step lands, and Step 7 is expected to have already added `hub := event.NewInProcessHub()` there and threaded it into `msgusecase.NewMessageUsecase(msgRepo, roomRepo, llmClient, hub)`. Wherever that construction actually lives by the time you implement this step, add the ticket issuer and WebSocket handler next to it and pass in the **same `hub` variable** already in scope — do not construct a second hub instance.
- **GoDoc**: every new exported symbol (`wsticket.Issuer`, `NewIssuer`, `Issue`, `Validate`, `WebSocketHandler`, `NewWebSocketHandler`, `IssueTicket`, `Handle`) needs a GoDoc comment describing what/why/constraints/error behavior, per `CLAUDE.md`.
- **conflictNotes**: this step adds exactly one new handler file (`websocket_handler.go`) plus its test, one new package (`wsticket`), one new `Config` field, and a small number of additive route-registration/DI lines wherever those live. It does not touch `server/internal/interface/middleware/auth.go` or (per the parallel-step boundary) any file Step 13 is expected to add under `server/internal/interface/middleware/` (e.g., `rbac.go`) — if such a file already exists when you implement this step, do not modify it; this step's authorization need is fully satisfied by `RoomUsecase.GetRoom`'s existing membership check.
