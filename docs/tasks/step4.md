# Step 4: Web BFF auth + data-plane proxy: httpOnly cookies, middleware guard, typed HTTP client

## Meta
- **Type**: refactor
- **Components**: web
- **Wave**: 1 (parallel group — all steps of the same wave can run concurrently)
- **Depends on**: None
- **Unlocks**: Step 9: Web data layer migration: TanStack Query, RSC prefetch, per-feature API modules | Step 10: Playwright E2E harness + seeded compose test stack + LLM stub
- **Size**: 1 PR (a few hours for one AI agent)

## Context
Phase 1 shipped a working web frontend, but `RealApiClient` in `web/src/lib/api.ts` stores the JWT in `localStorage` and attaches it as a Bearer header from client-side JavaScript — the exact pattern the plan's binding decisions call out for replacement with server-side, httpOnly-cookie auth. Every data call (`listRooms`, `sendMessage`, `sendAIMessage`, `listModels`, ...) also talks to the Go API directly from the browser via `NEXT_PUBLIC_API_URL`, which both exposes the token to XSS and bakes the API origin into the client bundle at build time. This step moves the JWT server-side: Next.js route handlers become a thin BFF (Backend-For-Frontend) that proxies auth and all data calls, so the token never reaches browser JavaScript, while keeping the app 100% functional (rooms, messages, AI send/regenerate, model listing) for the two waves of work that land before Step 9 replaces `lib/api.ts` with TanStack Query.

## Goal
After this PR, the browser never sees a JWT. `POST /api/auth/{login,register}` route handlers call the Go API's `/auth/login` and `/auth/register`, then set an httpOnly, `sameSite=lax` `access_token` cookie on the Next.js response; `POST /api/auth/logout` clears it. A catch-all `app/api/proxy/[...path]` route handler reads that cookie server-side, forwards every method (GET/POST/PUT/PATCH/DELETE), path, query string, and JSON body to the Go API with an `Authorization: Bearer <token>` header, and streams the upstream status/body back unchanged. `web/src/lib/http-client.ts` provides the shared fetch core (`ApiRequestError { status, body }`, a proxy-prefixed `apiRequest`, and an auth-prefixed `authRequest`) that `RealApiClient` now uses exclusively — `localStorage` token handling is deleted entirely. `web/src/middleware.ts` redirects unauthenticated visitors away from `(main)` routes and authenticated visitors away from `(auth)` routes, based solely on cookie presence (mock mode bypasses the guard so the existing demo flow keeps working). Rooms, messages, AI send/regenerate, and model listing all continue to work end-to-end through the new proxy.

## Implementation notes
- Real files to read before editing (for exact current shapes): `web/src/lib/api.ts`, `web/src/lib/mock-data.ts`, `web/src/hooks/use-auth.ts`, `web/src/types/api.ts`, `web/src/features/auth/components/LoginForm.tsx`, `web/src/features/auth/components/RegisterForm.tsx`, `web/src/features/rooms/components/RoomList.tsx`, `web/src/features/messages/components/ChatRoom.tsx`, `web/src/features/rooms/components/CreateRoomForm.tsx`, `web/src/components/mock-badge.tsx`.
- Go API route shapes are all defined at the top level in `server/cmd/api/main.go` (no `/api` prefix): `POST /auth/register`, `POST /auth/login` (public), then under the `JWTAuth` group: `POST /rooms`, `GET /rooms`, `GET /rooms/:roomId`, `PUT /rooms/:roomId`, `DELETE /rooms/:roomId`, `POST /rooms/:roomId/messages`, `GET /rooms/:roomId/messages`, `POST /rooms/:roomId/messages/ai`, `POST /rooms/:roomId/messages/:messageId/regenerate`; `GET /models` is public (top-level, not in the auth group) — the proxy must not require a cookie to forward requests, it should simply omit the `Authorization` header when there is none and let the Go API's own middleware decide.
- `TokenResponse`/`ErrorResponse` shapes come from `server/internal/interface/handler/auth_handler.go` (`{access_token, token_type}` on success, `{message}` on error) — these match `AuthResponse`/`ApiError` already declared in `web/src/types/api.ts`; reuse those types in the new route handlers instead of redefining them.
- `server/internal/interface/auth/simple_jwt.go` sets `tokenExpiry = 24 * time.Hour` — keep the cookie `maxAge` in lockstep via the shared constant in `web/src/lib/auth-cookie.ts` described above.
- Next.js 16 App Router route handlers use async dynamic APIs: `const { path } = await context.params` for the catch-all, and `const cookieStore = await cookies()` from `next/headers`. Use `NextRequest`/`NextResponse` from `next/server` in the proxy and `Request`/`NextResponse` in the simpler auth routes.
- Because `next.config.mjs` sets `output: "standalone"` and the Docker runtime stage only sets `HOSTNAME`/`PORT` env vars (see `web/Dockerfile`), a plain (non-`NEXT_PUBLIC_`) env var like `API_URL` is read at request time in Node and works correctly in the standalone server — unlike `NEXT_PUBLIC_*` vars, which are inlined into the client bundle at build time and would require a rebuild per environment. This is why the proxy/auth route handlers must use `process.env.API_URL`, not `NEXT_PUBLIC_API_URL`.
- Preserve the existing per-endpoint paths and query-string construction used today in `web/src/lib/api.ts` (e.g. `listMessages` builds `?cursor=...&limit=...`) — only the transport (`apiRequest`/`authRequest` instead of raw `fetch`) changes, not the URLs passed to it.
- Chakra UI / component code (`LoginForm.tsx`, `RegisterForm.tsx`, `RoomList.tsx`) needs no visual changes; follow `.claude/rules/chakra-ui.md` only if any JSX is touched incidentally.
- Conflict notes: this step rewrites the request core of `lib/api.ts`; Step 9 later replaces `lib/api.ts` wholesale with TanStack Query + per-feature modules on top of the same `/api/proxy/*` contract, and Step 10's smoke spec is expected to exercise rooms/messages/models through this proxy before Step 9 lands. Step 5 (same wave) is unaffected because it only authors MSW handlers pinned to the `/api/proxy/*` contract and does not touch `lib/api.ts`, `use-auth.ts`, or `middleware.ts`.
