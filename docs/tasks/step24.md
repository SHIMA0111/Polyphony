# Step 24: Server: per-room AI provider/model settings

## Meta
- **Type**: feature
- **Components**: server
- **Wave**: 5 (parallel group — all steps of the same wave can run concurrently)
- **Depends on**: Step 13: Go 5-tier RBAC domain + authorization middleware + ModelUsecase; Step 23: Server: AI context control (soft delete, exclude flag, cutoff, context builder)
- **Unlocks**: Step 32: Server: room fork (async batch copy); Step 36: Web room settings drawer
- **Size**: 1 PR (a few hours for one AI agent)

## Context
`MessageUsecase.SendAIMessage`/`RegenerateAIMessage` (`server/internal/usecase/message/usecase.go`) currently fall back to a single package-level constant, `const defaultModel = "gpt-5-mini"`, whenever the caller omits a model — there is no notion of a room-level default at all. Phase 6 of `phases.md` ("Multi-provider (Anthropic)") calls for "Provider/model selection in room settings" backed by new `ai_provider`/`ai_model` columns on `rooms`, so that a room master/admin can pin a room to a specific provider+model (e.g. all AI replies in a "support" room use `claude-opus`) without every sender having to pass `model` on each request. This step adds that per-room default and a `request > room > global default` resolution order, giving Step 36's room settings drawer a real endpoint to call and Step 32's room fork something concrete to copy alongside the rest of a room's configuration.

## Goal
`rooms` gains nullable `ai_provider`/`ai_model` columns, settable via a new `PATCH /rooms/:roomId/settings` endpoint restricted to admin/master (reusing Step 13's `RequireRole`/`Authorize` RBAC primitive with `domainroom.ActionManageRoom`). A new, single-purpose model-resolution helper picks the effective model for an AI request using the order **explicit request model > room's configured `ai_model` > global default from `Config`** (provider is stored for display/consistency but the resolver's contract is model-string resolution, matching the existing `ai.CompletionRequest.Model` shape). `MessageUsecase.SendAIMessage`/`RegenerateAIMessage` call this helper in place of the hardcoded `defaultModel` fallback via a minimal, one-line-per-call-site change; the global default itself moves out of the package constant and into `config.Config` so it's configurable per deployment.

## Out of scope
- `SendAIMessage`/`RegenerateAIMessage` privacy plumbing, read filters, and any exclude/cutoff-aware context assembly changes — all Step 41's territory; this step's touch to those two methods is limited to the model-fallback line(s).
- Room fork copying `ai_provider`/`ai_model` to the new room (Step 32 consumes these columns but implements the copy itself).
- Web room settings UI to edit these fields (Step 36).
- Validating `ai_model`/`ai_provider` against the LLM Gateway's live `/models` list (e.g. rejecting an unknown model at write time) — accepted as free-form strings in this step; cross-checking against `ModelUsecase.ListModels` is a future hardening concern, not required here.
- Anthropic/Gemini adapter implementations in the LLM Gateway (Phase 6/7 Rust-side work) — this step only adds the Go-side room configuration and resolution order, independent of which providers the gateway actually supports.
- Any change to `ai.LLMGateway`, `ai.CompletionRequest`, or `internal/domain/ai/*` — the resolver produces a plain model string consumed exactly as `CompletionRequest.Model` is today.
- Context summarization, streaming, or token estimation (Phases 18/19, later steps).

## Implementation notes
- Follow Clean Architecture layering per `CLAUDE.md`: `server/internal/usecase/message/model_resolution.go` must depend only on `domain/room` (for reading `Room.AIModel`) and plain strings — no `echo`, no `pgx`, no config package import (pass `globalDefault` as a parameter, sourced by the usecase constructor from `Config` at wiring time in `container.go`).
- Reuse Step 13's RBAC primitives exactly as `RoomUsecase.UpdateRoom` already will: `internal/interface/middleware/rbac.go`'s `Authorize(role domainroom.Role, action domainroom.Action) error` for the usecase-layer check inside `UpdateSettings`, and `middleware.RequireRole(roomRepo, domainroom.ActionManageRoom)` for the route-level gate in `routes_room.go` — the same `ActionManageRoom` action `UpdateRoom` uses, since "admin can manage room settings but not delete the room" is exactly the rule Step 13 defines.
- Keep the new settings handler in its own file (`room_settings_handler.go`) rather than growing `room_handler.go` — `RoomHandler` is a shared receiver, so adding a method in a sibling file avoids merge conflicts with any other same-wave step that might touch `room_handler.go`'s existing CRUD methods.
- `NewMessageUsecase`'s signature change (`msgRepo, roomRepo, llmGateway, defaultAIModel string`) is the only touch to `MessageUsecase`'s constructor; do not add unrelated fields.
- DB shape: `rooms.ai_provider VARCHAR(50) NULL`, `rooms.ai_model VARCHAR(100) NULL` — see `server/schema.sql`'s existing `rooms` table (lines 15-22) for the column-style convention (uppercase types, no inline comments). Generate the migration via `task migrate:generate -- add_room_ai_settings` (see `Taskfile.yml`'s `migrate:generate` task, which shells into `server/` and runs `atlas migrate diff <name> --env local`), matching the pattern Step 13 used for its `room_members.role` CHECK constraint migration.
- Conflict note (merge-order only, not a logical dependency): Step 23 also edits `server/schema.sql`'s `rooms` table in the same wave, adding `ai_context_cutoff_at` (per `phases.md` Phase 5). Both steps' schema edits are additive and touch disjoint columns, but rebase onto Step 23's merged `schema.sql` before generating this step's migration so the two Atlas migrations apply in a consistent order and `atlas.sum` doesn't diverge. Same-wave note re: Step 41 — that step owns `SendAIMessage`'s privacy/read-filter plumbing; this step owns only the new model-resolution helper file and the settings handler, and the shared `usecase.go` edit is the single coordinated one-line fallback replacement described above.
- Existing DTO/response conventions to preserve: `RoomResponse` in `dto.go` is a flat struct built field-by-field in every `RoomHandler` method (`Create`, `Get`, `List`, `Update`) — when adding `AIProvider`/`AIModel` to it, update all of those existing construction sites too (not just the new `UpdateSettings` handler) so every room-returning endpoint consistently reports the new fields.
- Error mapping: reuse `handleRoomError` (`internal/interface/handler/room_handler.go`) unchanged — `UpdateSettings` should return the same `domain.ErrNotFound`/`domain.ErrForbidden` errors `UpdateRoom` already returns so no new mapping logic is needed.
