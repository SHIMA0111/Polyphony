# Step 51: Go: consume gateway stream + WS chunk forwarding

## Meta
- **Type**: feature
- **Components**: server
- **Wave**: 6 (parallel group — all steps of the same wave can run concurrently)
- **Depends on**: Step 15: Server WebSocket endpoint + realtime delivery | Step 23: Server: AI context control (soft delete, exclude flag, cutoff, context builder) | Step 42: Server: token balance management | Step 43: Rust: streaming SSE for all providers + stream endpoint
- **Unlocks**: Step 54: Web: streaming AI rendering
- **Size**: 1 PR (a few hours for one AI agent)

## Context
`phases.md` Phase 19 ("Streaming AI Responses") requires AI output to appear token-by-token instead of only after the full completion returns. By the time this step runs, `llm-gateway` exposes `POST /completions/stream` (Step 43), which streams unnamed SSE `data:` frames each carrying one JSON-encoded chunk, terminated by a literal `data: [DONE]` sentinel on success, or chunk frames followed by exactly one `event: error` frame on a mid-stream provider failure (per Step 43's SSE contract); a synchronous dispatch failure (bad model, etc.) is still returned as an ordinary JSON/HTTP-status response, never as an SSE body. The Go API's `MessageUsecase` (`server/internal/usecase/message/usecase.go`) only knows how to call the gateway's unary `POST /completions` via `ai.LLMGateway.Complete` (`server/internal/interface/gateway/llm_client.go`), and its context-building logic runs through the `ai.ContextBuilder` interface Step 23 froze in `server/internal/domain/ai/context_builder.go`. The realtime transport Step 15 already built — `GET /rooms/:roomId/ws`, subscribed to `domain/event.MessageHub` (`server/internal/domain/event/hub.go`), forwarding `RoomEvent`s as JSON frames via `server/internal/interface/handler/websocket_handler.go` — is the only delivery path connected clients have; this step is what actually puts token deltas onto it. This is the Go-side half of Phase 19; the web frontend's rendering of these frames is a separate, later step.

## Goal
After this PR, `ai.LLMGateway` gains a `Stream` method and `server/internal/interface/gateway/llm_client.go` implements it by POSTing to the gateway's `/completions/stream` endpoint and parsing its SSE frames into a channel of incremental results, mapping a non-2xx initial response to the same `domain.ErrLLMGateway`-wrapped error `Complete` already produces. `MessageUsecase` gains `SendAIMessageStream`, which applies Step 42's pre-call balance guard (`BillingGuard.CheckBalance`, HTTP 402 on insufficient balance) exactly like `SendAIMessage`, persists the human message and an AI placeholder message (`status="streaming"`) synchronously and returns immediately, then continues in a background goroutine: it assembles context via the existing `ai.ContextBuilder` (unmodified, per Step 23's frozen contract), calls `llmGateway.Stream`, and for each incremental delta publishes a new `event.EventTokenChunk` `RoomEvent` carrying the AI message's ID and the delta text via `MessageHub.Publish` — which `websocket_handler.go`'s existing forwarding loop (extended additively in this step) relays to every WebSocket-connected room member as a `token_chunk` frame. Once the gateway's stream ends, the assembled message is persisted via the existing `MessageRepository.UpdateAIResponse` with `status="completed"`, and an `EventMessageUpdated` event carrying the final message is published (mirroring `RegenerateAIMessage`'s existing update-then-publish pattern); a mid-stream provider failure instead persists whatever content was assembled so far with `status="failed"` and publishes the same event type, so `RegenerateAIMessage` can retry it exactly like today's non-streaming failure path. A successful stream's final `Usage` chunk is billed through Step 42's `BillingGuard.RecordUsage`, mirroring the non-streaming path's fire-and-forget usage recording. A new `POST /rooms/:roomId/messages/ai/stream` endpoint triggers this flow and returns `202 Accepted` with the human message and the AI placeholder immediately, without waiting for the stream to finish. The non-streaming `SendAIMessage`/`RegenerateAIMessage` paths and the unary `/completions` client are untouched.

## Out of scope
- Any change to `llm-gateway/` — this step only consumes the already-shipped `POST /completions/stream` endpoint (Step 43) via a plain HTTP client; no Rust files are touched.
- Implementing summarization itself — Step 50 (same wave) owns `assembleAIContext`, the summary cache, and the summarization prompt. The contract is pinned: `assembleAIContext`'s `usedSummary` return value is the only summary-usage signal; this step merely threads that boolean into `StreamChunkEvent.SummaryUsed` (no decorator interface, no `SummaryAwareContextBuilder` — an earlier draft's decorator idea was dropped by decision).
- Any change to `ai.ContextBuilder.Build`'s method signature, or to `server/internal/domain/ai/context_builder.go` itself — this step only calls `Build`, exactly as `SendAIMessage` already does.
- The web frontend's rendering of `token_chunk` WebSocket frames, typing indicators, or any streaming UI (Step 54).
- gRPC streaming between the Go server and the gateway — this step uses the gateway's REST `/completions/stream` endpoint only, consistent with the plan's REST-now/gRPC-later swap point.
- Client-initiated stream cancellation (e.g. a "stop generating" button/endpoint) — not built here; the background goroutine runs to completion, failure, or its own bounded timeout regardless of client WebSocket disconnects.
- Graceful draining of in-flight background streams on server shutdown (e.g. via a `sync.WaitGroup` in the DI container) — an in-flight stream may be abandoned mid-way if the process exits during shutdown; acceptable for this locally-run scope, revisit later if it becomes a problem.
- Billing partially-streamed usage: a mid-stream failure (or a stream that never delivers a `Usage`-bearing final chunk) records no `token_transactions` row, because the gateway reports usage only on successful completion — an accepted, documented gap (the pre-call `CheckBalance` guard still gates every streaming send, so a depleted balance cannot keep streaming indefinitely).
- Estimating the cost of an in-flight stream before it completes — same boundary as Step 42's non-streaming guard (`balance > 0` check only).
- Retry/backoff of a stream after it has started — identical boundary to Step 43's gateway-side behavior: a mid-stream failure surfaces once as a terminal error, it is not silently retried by this step.
- `schema.sql` / Atlas migrations — no DB changes are needed (`messages.status` is an unconstrained `VARCHAR(20)`; verify this against `server/schema.sql` before writing any migration, and do not add one if it's still true by the time this step lands).
- `docker-compose.yml` / `Taskfile.yml` / `.env.example` changes — no new environment variables or services are introduced.

- **`ai.LLMGateway.Stream`'s signature is an additive interface change** — every existing implementer/mock must gain a `Stream` method or the build breaks; the Scope section above enumerates the two known test-double locations (`mockLLMGateway`, `mockLLMForHandler`) as of this repo snapshot, but grep for any others (`grep -rn "ai.LLMGateway" server/`) before finishing, in case a same-wave step introduced another one.
- **SSE parsing contract**: the gateway's chunk frames are always single-line JSON `data:` (axum's `Event::json_data` serializes compactly), and `error` frames are a single-line plain-text `data:` (`domain_err.to_string()`) — the framing described in Scope (accumulate `event:`/`data:` lines until a blank line, joining multiple `data:` lines with `\n` only in the general case) is written defensively to match the SSE spec, but in practice a single `data:` line per frame is what this step's own gateway emits.
- **Why a decoupled background context**: `SendAIMessageStream` returns to the HTTP handler (and thus the request's `context.Context` is cancelled by Echo once the response is written) well before the LLM stream finishes; using `ctx` directly for the background work would cancel in-flight generation the instant the `202` response is flushed, which would break delivery to every *other* room member still connected over WebSocket. Use `context.WithTimeout(context.Background(), 5*time.Minute)` (or a similar bounded, request-independent context) for the goroutine and for the `hub.Publish`/`msgRepo.UpdateAIResponse` calls it makes.
- **`RoomEvent.Chunk`/`RoomEvent.Message` mutual exclusivity**: `websocket_handler.go`'s frame-building code is the only place that needs to branch on which is set; `domain/event.InProcessHub` itself is agnostic to `RoomEvent`'s payload shape and requires no changes (verified by the new hub test case in Scope).
- **English-only code/comments/docs, GoDoc on every new/changed exported symbol**, per `CLAUDE.md`.
