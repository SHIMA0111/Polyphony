# Step 29: Web send pipeline UX: optimistic send, AI thinking, retry, infinite scroll

## Meta
- **Type**: ui
- **Components**: web
- **Wave**: 4 (parallel group — all steps of the same wave can run concurrently)
- **Depends on**: Step 18: Web message list rendering upgrade + ChatRoom decomposition
- **Unlocks**: Step 35: Web WebSocket client + live cache merge | Step 38: Web AI context UI: exclude toggle, delete, token meter | Step 45: Web: image upload + attachment UI + Vision send
- **Size**: 1 PR (a few hours for one AI agent)

## Context
Step 18 decomposed `ChatRoom.tsx` into a `useChatRoom` hook plus `MessageList`/`MessageGroup`/`MessageBubble` subcomponents, and gave the transcript markdown rendering, grouping, day separators, and smart auto-scroll — but the send/regenerate mutations themselves still behave the way they did on day one: `handleSend`/`handleSendWithAI` `await` the mutation before the message appears at all (no optimistic echo, no visible "sending" state, no failure recovery beyond a silently-swallowed `// TODO: handle error`), the whole history is fetched in a single `listMessages(roomId, undefined, 100)` call with no way to reach older messages, and `handleRegenerate` finds the human message to resend by scanning backwards through the in-memory `messages` array by array index instead of using the `in_response_to_message_id` link that Step 7 already stores on every AI message. This step closes that gap so the send pipeline feels instant and honest — matching the "Web complete version" binding decision that the whole app must behave like a production chat product, not a wave-1 prototype — and gives Step 35's realtime merge, Step 38's per-message controls, and Step 45's attachment send a stable, non-racy foundation to extend instead of a fetch-then-forget effect.

## Goal
Sending a message immediately renders it in the transcript in a "sending" visual state (no round-trip wait), and reconciles to the real persisted message (or a failed/retry state with the original input preserved) when the mutation settles. Sending with AI additionally shows an animated "thinking" placeholder in place of the not-yet-arrived AI reply. Any send failure surfaces a toast, restores the user's typed content into the input so nothing is lost, and offers a retry affordance on the failed bubble. The transcript loads via cursor-based infinite scroll: only the most recent page is fetched up front, and scrolling to the top of the history loads the next older page from `next_cursor` while preserving the reader's scroll anchor (no jump). Regenerate resolves its target human message directly from the AI message's `in_response_to_message_id` field instead of scanning the local array.

## Implementation notes
- **Files this step owns for wave 4** (per the plan's `MessageList`/`MessageInput` ownership rotation, `18 -> 29 -> 38 -> 45`): `web/src/features/messages/components/MessageInput.tsx`, `web/src/features/messages/components/MessageList.tsx`, `web/src/features/messages/components/MessageBubble.tsx`, `web/src/features/messages/components/MessageGroup.tsx`, plus new files (`ThinkingBubble.tsx`, the two new hooks). Do not touch `ChatRoomHeader.tsx`, `MarkdownContent.tsx`, `CodeBlock.tsx`, `DaySeparator.tsx`, `group-messages.ts` beyond wiring — those are Step 18's stable surface.
- **Cursor pagination contract** (Go server, unchanged by this step — see `server/internal/interface/handler/message_handler.go`'s `List` handler and `server/internal/interface/repository/postgres/message_repository.go`'s `ListByRoom`): `GET /rooms/:roomId/messages?cursor=&limit=` returns `{ messages: MessageResponse[], next_cursor: string | null }` where `messages` is **newest-first** (`ORDER BY sequence DESC`), `cursor` (when supplied) is the `id` of the oldest message already fetched, and `next_cursor` is the cursor to pass to fetch the *next older* page; `next_cursor` is `null` when there is no more history. This is exactly a backward/upward pagination shape — do not reorder it server-side.
- **Regenerate endpoint contract, still unchanged** (see `server/internal/usecase/message/usecase.go`'s `RegenerateAIMessage`): `POST /rooms/:roomId/messages/:messageId/regenerate` takes the **human** message's id as `:messageId` and updates the existing AI message in place (same AI message id, sequence, and slot); the response is the updated `MessageResponse`. `ChatRoom.tsx`'s current `handleRegenerate` receives the **AI** message's id from the "Regenerate" button and must resolve the corresponding human message id itself — today that resolution is a backward array scan; after this step it is `aiMessage.in_response_to_message_id`.
- **`in_response_to_message_id` provenance**: added to the server's `messages` table, `MessageRepository`, and `MessageResponse` DTO by Step 7 (`server/internal/interface/handler/dto.go`'s `MessageResponse`, `server/internal/interface/handler/message_handler.go`'s `toMessageResponse`) — nil for human messages, set to the human message's id for AI messages. Confirm the field is present on the `Message`/`MessageResponse` shape reaching the web client (`web/src/features/messages/types.ts`, per Step 9's per-feature types split) before wiring `handleRegenerate` to it; add the field to that type if it is missing (a type-only addition, no fetcher/DTO shape change needed since the server already serializes it).
- **Optimistic cache shape**: the infinite query's cache is `{ pages: MessagePage[], pageParams: (string | undefined)[] }` with `pages[0]` being the newest page. Optimistic sends and their reconciliation must only ever touch `pages[0]`'s `messages` array (prepend synthetic entries there in newest-first order, i.e. push to the front since the page itself is newest-first) — never touch `pages[1..]`, which represent already-loaded older history.
- **Reuse, don't reinvent**: `web/src/components/ui/toaster.tsx` (`toaster.create({...})`, already wired app-wide via `web/src/components/ui/provider.tsx` or `layout.tsx`) for the failure toast; `web/src/components/ui/tooltip.tsx` if any new hover affordance needs one (unlikely for this step); the existing `Spinner`/`RefreshCw` (`lucide-react`) icon patterns already used in `MessageBubble.tsx`'s regenerate button for the retry button on failed human messages, for visual consistency.
- **Chakra v3 conventions** (`.claude/rules/chakra-ui.md`): implement `ThinkingBubble`'s dot animation with Chakra's `Box` style props (`animation`, `@keyframes` via the `css` prop or a small shared `keyframes` helper) rather than a new CSS file or Tailwind classes; keep using Compound Components / style props throughout — no new UI library dependency is needed for this step (do not add `framer-motion` or similar just for three dots).
- **English-only** identifiers/comments throughout, per `CLAUDE.md`. Document the client-only `"sending"` status value clearly since it does not exist server-side.
- **Conflict notes**: this step depends on Step 18 for `MessageList`/`ChatRoom`/`MessageBubble`/`useChatRoom`'s existence and shapes — if Step 18 landed with different file names or a different `useChatRoom` return shape than assumed here, adapt the concrete paths but keep the query-key (`["rooms", roomId, "messages"]`) and prop-contract stability guarantees (`onRegenerate`, `isRegenerating`) intact, since Step 35 depends on this step's query key and Step 38/45 depend on `MessageList`/`MessageInput` staying composable. Do not modify `ChatRoomHeader.tsx`, `MarkdownContent.tsx`, `CodeBlock.tsx`, `DaySeparator.tsx`, or `group-messages.ts` — those remain Step 18's stable output for this wave.
